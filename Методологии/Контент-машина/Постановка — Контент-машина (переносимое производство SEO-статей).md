# Постановка — Контент-машина (переносимое производство SEO-статей)

Автор: Claude по запросу и решениям Дмитрия, 25.10.2026. Источник: запрос Дмитрия в чат канона 25.10.2026,
разбор чата контента первого потребителя от 25.10.2026, решения Дмитрия (1)–(3) от 25.10.2026.
Решение владельца: **ждёт** — принята / уточнить / отклонена.

Объём по [Стандарту — Цепочка постановки](<../Стандарт — Цепочка постановки (постановка, спецификация, план).md>):
строим систему — три файла. Эта постановка описывает систему целиком, а критерии готовности даёт для волны 1.
Следующие шаги — спецификация и план волны 1. Спецификация на все десять систем пишется после выпуска волны 1,
отдельным шагом (решение Дмитрия (1)).

## Проблема

Дмитрий ведёт SEO-контент в нескольких проектах: в компании, в личных и на новых сайтах. Работающая
контент-машина есть только у первого потребителя — компании, где в блоге опубликовано около 400 статей.
Её механики проверены, но перенести их в другой проект нельзя: домены, автор, CDN, продукт в мосте, таблица и
номера её колонок, вёрстка CMS зашиты константами в каждый скрипт. Для нового проекта машину приходится
собирать заново.

Чего машина первого потребителя не умеет сейчас (разбор 25.10.2026):

- **Не видит, что тема уже закрыта своей страницей.** Единого реестра «страница ↔ ключи» нет: есть три неполные
  замены, и маршрут статьи не ссылается ни на одну. Чекер каннибализации сравнивает основы слов без стоп-слов и
  без нормализации «ё» и коротких основ, поэтому даёт ложные тревоги по общим словам и пропускает словоформы.
  Поиск по эмбеддингам сверяет темы с банком тем и реестром смыслов, а не с телами статей, и в гейт не входит.
  **Провал 23.10.2026:** агент предложил тему «вентиляция для газового котла» без прогона гейта; гейт показал, что
  её уже закрывает опубликованная статья о печи и камине — разделом о газовом котле и двумя вопросами FAQ. В
  реестре смыслов суть той статьи о котле не говорит ни слова: поймать пересечение мог только поиск по телам статей.
- **Спрос собирается руками.** Очередь тем — markdown-файл и банк тем; автоматического сбора из Search Console и
  Яндекс.Вебмастера нет, запас тем в днях не считается.
- **Гейт темы — семь шагов, часть из них руками и моделью.** Одной командой без модели он не запускается.
- **Против карты модулей К. Васина** не хватает ещё: разбора топ-3 в числа, кэша выдачи, библиотеки фактов со
  сроком годности, IndexNow и переобхода, сверки «доехало до сайта», мониторинга позиций и быстрых побед,
  недельного аудита, дожима по расписанию, проверки цитирования в ИИ-поиске. Это волны 2 и 3.

## Нужный результат

**Вся система:** пакет канона `content_engine`. Он ставится в любой проект одним профилем настроек и ведёт
статью от спроса до замера: семантика → тема с гипотезой → анти-дубли и бронь → подготовка → текст и вычитка →
гейт → публикация → индексация → замер и наблюдение. Ядро нейтрально. Внешние сервисы подключаются адаптерами:
выдача и семантика, публикация, генератор картинок.

| Волна | Что входит | Когда |
|---|---|---|
| 1 | Реестр «страница ↔ ключи» с бронью кластера до написания; анти-дубли; семантика из Search Console, Яндекс.Вебмастера и Keys.so в единую очередь тем; гейт без модели одной командой; выпуск в первый проект | Сейчас: постановка → спецификация → план → код → выпуск |
| 2 | Подготовка по топ-3, публикация двумя режимами (ручная вставка и прямая публикация агентом), индексация, сверка «доехало» | После волны 1 |
| 3 | Мониторинг, недельный аудит, дрифт, дожим, проверка цитирования в ИИ-поиске, панель с вердиктом дня | После волны 2 |

### Что считать готовым в волне 1

1. **Пакет.** `_Движок\Пакеты\content_engine\` устроен по
   [ADR-0003](<../../_Движок/0 — System Docs/ADR-log/0003-code-systems-source-in-canon-releases-in-projects.md>),
   как `growth_engine`: `pyproject.toml`, версия, тесты зелёные, строка в
   [манифесте пакетов](<../../_Движок/Пакеты/_manifest.md>), строка в CHANGELOG движка, метка версии.
2. **Профиль проекта** — один файл настроек: свои домены, разделы блога и продающих страниц, регион и поисковик
   выдачи, подключённые источники, режим публикации, пороги анти-дублей, ритм выпуска. В коде пакета нет имён,
   доменов и данных компаний; тесты идут на синтетическом проекте.
3. **Реестр «страница ↔ ключи»** — единственный источник правды о том, какая страница какой спрос закрывает.
   Собирается из живого сайта: список страниц, тексты, запросы из консолей. На каждую страницу — тип (статья или
   продающая), смысловой ключ, ключи, кластер, статус. Новая тема **бронирует кластер до написания**; ключи чужой
   страницы новая статья может только упомянуть со ссылкой, но не взять целевыми.
4. **Анти-дубли — кодом, до вызова модели:**
   - смысловой ключ — множество нормализованных основ (стоп-слова, «ё» → «е», словоформы); сверка с реестром,
     очередью и бронями;
   - поиск по **телам** опубликованных статей, а не только по заголовкам и сути;
   - совпадение топ-10 по выдаче Keys.so — кластер объединяет запросы с общими адресами в выдаче;
   - лимит живых статей на один головной запрос;
   - конфликт с продающей страницей; коммерческая выдача уводит тему в очередь продающих страниц, а не в блог;
   - белый список ложных срабатываний — с причиной и датой.
   Пороги — параметры профиля. Исходные значения автора (см. раздел о Васине) калибруются на корпусе первого
   потребителя, доля ложных тревог замеряется и называется числом.
5. **Единая очередь тем.** Адаптеры Search Console, Яндекс.Вебмастера и Keys.so сливают спрос в одну очередь:
   дедупликация, отсев уже закрытого через анти-дубли, приоритет, **запас в днях** при ритме выпуска из профиля.
   У темы есть поля гипотезы: ожидание, порог провала, окна замера 90 и 180 дней. Заполняет и решает по ним
   Движок роста, очередь их только несёт.
6. **Гейт без модели — одна команда.** Для темы: анти-дубли, бронь, тип выдачи. Для готовой статьи: структура,
   длины title и description, слаг, дубль заголовка среди живых статей, FAQ, ссылки на продающие страницы,
   разметка. Результат — «пропуск» или «черновик» с причиной и кодом выхода; тема при отказе не теряется.
7. **Источник выдачи — адаптером.** Keys.so — первая реализация. Второй источник подключается без правки ядра;
   доказательство — тестовый адаптер-заглушка проходит те же тесты (решение Дмитрия (2)).
8. **Проверка на живом корпусе первого потребителя:**
   - реестр собран по всем живым страницам блога: число страниц в реестре сходится с картой сайта раздела,
     расхождения объяснены поимённо;
   - известные пересечения находятся: тема «вентиляция для газового котла» останавливается статьёй о печи и
     камине; статьи «вентиляция в хрущёвке» и «не работает вентиляция» помечаются пересечением;
   - очередь тем не пустая, запас назван в днях;
   - доля ложных тревог на корпусе замерена.
   Набор известных ответов и данные корпуса хранятся у первого потребителя, в канон не попадают.
9. **Выпуск в первый проект с паспортом** (`kos_release.py issue` и `check`). Подключает выпуск к маршруту
   статьи чат контента первого потребителя.
10. **Независимая приёмка** до выпуска — навыком `maker-checker` или второй моделью (`second-agent`).

В волну 1 **не входят**: подготовка по топ-3, тексты, картинки, публикация, индексация, мониторинг. Адаптеры
публикации и генератора картинок проектируются в волне 2.

## Что берём у К. Васина и что своё

Источник — гайд К. Васина «SEO-машина», версии 3.1–3.2 (PDF, 54 страницы, август 2026;
<https://vasinki.ru/guides/seo-mashina/>) и карта модулей <https://vasinki.ru/ceh/sistema> (пакет 1.28.4 от
08.10.2026). Берём идеи и архитектуру со ссылкой. Тексты, промпты и чек-листы автора не копируем: материал
авторский и частично платный. Кейсы автора — его заявления, не проверено.

**Берём (идея → где у автора):**

| Идея | Источник | Как берём |
|---|---|---|
| 10 систем: шесть — путь статьи, четыре — наблюдение; фундамент из правил отдельно от кода | PDF, с. 3, 8, 18 | Каркас волн; правила — ссылкой на канон |
| Реестр «страница ↔ ключи» как единый источник правды; бронь кластера до написания | PDF, с. 33 | Ядро волны 1. Механика брони у автора не раскрыта — проектируем сами |
| Дедупликация и каннибализация — разные защиты; слои до модели, еженедельная попарная сверка живых страниц | PDF, с. 4, 32–33 | Волна 1 — слои до модели; еженедельный аудит — волна 3 |
| Пороги: ≥70 % слов ключа, ≥3 общих адреса в топ-10, конфликт с продающей 0,75, не больше 6 статей на головной термин; белый список | Карта модулей, блок 4 | Исходные значения параметров, не нормы; калибруем на своём корпусе |
| Одна очередь тем из консолей, Wordstat и доноров; запас «хватит на N дней»; пустая очередь — поломка сбора | PDF, с. 25–27, 37 | Волна 1 — консоли и Keys.so |
| Отсев до модели; бюджет-гейт перед платным шагом, ночью — остановка, а не вопрос | PDF, с. 26 | В ядро |
| Гейт без модели; не прошло — черновик, тема не теряется | PDF, с. 5–6, 31 | Волна 1 |
| Разбор топ-3 в числа, кэш выдачи, библиотека фактов со сроком годности | PDF, с. 27–30 | Волна 2 |
| Публикация адаптером под стек; по умолчанию «только файлы»; «доехало» — по ответу сайта; IndexNow и переобход | PDF, с. 5, 35–36 | Волна 2 |
| Мониторинг, дрифт против эталонного снимка, отчёт по дельте, «не подключено» вместо нуля, ритм по дням недели | PDF, с. 36–45 | Волна 3 |
| Не включать всё сразу | PDF, с. 44–45 | Порядок волн |

**Не берём:** выбор модели-писателя в обход маркировки ИИ-текста; пульт с кнопками вместо панели-витрины;
список провайдеров автора — модели выбираются по навыку `llm-pipeline-economy`.

**Своё — должно войти в ядро** (проверено у первого потребителя):

- тема рождается из гипотезы Движка роста — с ожиданием и порогом провала;
- замер на 90-й и 180-й день от дня выкладки; день сборки и день выкладки — разные поля;
- деньги страницы — по CRM через Ядро данных, а не по целям веб-аналитики; «мы уже ранжируемся» — ещё не стоп,
  стоп — если эта страница зарабатывает;
- поиск пересечений по телам статей; «эмбеддинги ищут, модель судит из пяти ближайших, спорное решает человек» —
  порог по косинусу в узкой нише не работает;
- независимая вычитка фактов отдельным агентом без контекста автора;
- граница честности в мосте к продукту: где продукт не помогает — так и пишем;
- запись во внешнюю таблицу — план, затем применение, затем сверка чтением;
- каждое число — с периодом, источником и статусом.

## Кого и какие системы касается

- **Дмитрий** — владелец результата: принимает постановку и спецификацию, ставит машину в проекты.
- **Чат канона** — исполнитель: спецификация, план, код пакета, выпуск.
- **Чат контента первого потребителя** — первый потребитель: подключает выпуск к своему маршруту статьи, держит
  набор известных ответов.
- **Канон:** [Движок роста](<../Движок роста/_manifest.md>) (гипотеза и решение по замеру) и
  [Ядро данных](<../Ядро данных/_manifest.md>) (деньги страницы) — content_engine читает их адаптерами и не
  дублирует; навыки `keysso`, `seo-niche-research`, `topvisor`, `jev`, `text-editor`, `image-edit`,
  `llm-pipeline-economy`, `maker-checker`; [Методология — Текст и редактура](<../Методология — Текст и редактура (информационный стиль, Ильяхов).md>).
- **Внешние сервисы волны 1:** Keys.so API (выдача по регионам и семантика), Google Search Console,
  Яндекс.Вебмастер — только чтение. CMS — с волны 2.

## Ограничения

- Данные первого потребителя в канон не попадают: в коде, тестах и фикстурах — только синтетика.
- Тексты, промпты и чек-листы гайда К. Васина не копируются; ссылка на источник обязательна.
- **Квоты Keys.so.** Суточный лимит «анализируемых объектов» общий на весь аккаунт; выдача по нескольким тысячам
  фраз съедает его большую часть, кластеризатор и проекты тратят месячные лимиты (навык `keysso`). Съём выдачи
  по корпусу — с бюджетом квот до запуска и кэшем выдачи.
- XMLRiver сейчас не подключается (решение Дмитрия (2)).
- Гейт волны 1 — без модели. Любой платный вызов (модели, эмбеддинги) — с названной ценой и после «да» Дмитрия.
- Внешние системы в волне 1 — только чтение.
- Код — пакетом канона по ADR-0003; выпуск в проекте руками не правится.
- Не больше двух субагентов одновременно. Push на GitHub — только по команде Дмитрия.
- Срок не задан.

**Факты со слов инициатора:** решения (1)–(3); состав волн; провал 23.10.2026; перечень недостающего против
карты модулей; сильные стороны машины первого потребителя. **Проверено агентом 25.10.2026:** гайд прочитан

**Предположения агента:** состав профиля проекта, поля реестра, ответы «по умолчанию» на открытые вопросы.
