# Плейбук — Подключить Контент-машину к проекту

> id: `content-engine-connect`. Запрос в чате проекта: «Подключи Контент-машину к этому проекту по плейбуку
> `D:\Knowledge-OS\Методологии\Контент-машина\Плейбук — Подключить Контент-машину к проекту.md`».

## Краткая суть

- **Машина ставится целиком.** Пять контуров — Спрос, Решение, Производство, Выпуск, Доказательство — и основание
  работают только вместе: без Спроса нет очереди, без Решения статьи дублируют друг друга, без Доказательства
  никто не знает, какие статьи принесли деньги. Взять «пару пунктов семантики и аналитики» — не подключение.
- **Каждый модуль получает состояние.** В паспорте подключения у всех 26 модулей карты и у основания стоит одно из
  трёх: «подключён», «отложен — причина, что нужно, решение владельца», «неприменим — опция». Пустая строка —
  подключение не закончено.
- **Проектное — в профиле и адаптерах инстанса, не в пакете.** Пакет правится только в каноне с тестом и новым
  выпуском; находка привязки к одному проекту — ошибка машины, а не правка выпуска.
- **Готово**, когда паспорт заполнен, `check --contours` сходится с паспортом, первая статья доехала, а расписание
  включает доказательство.

> Для быстрого знакомства человеку может хватить блока выше.
> Для агентов, правок и разрешения расхождений обязателен полный текст.

## Место в системе

- **Отвечает на:** как поставить Контент-машину в проект целиком и доказать, что ни один модуль не потерян.
- **На входе:** проект, подключённый к канону ([плейбук подключения](<../../_Движок/Сценарии/Плейбук — Подключить проект к канону.md>)),
  ниша со спросом — от навыков `seo-niche-research` и `keysso`.
- **На выходе:** выпуск пакета, профиль, паспорт подключения и первая статья → дальше работа машины навыком
  `content-engine` по [каталогу операций](<Методология — Контент-машина, каталог операций (для навыка и сервера MCP).md>).
- Соседи и пробелы — по [карте методобазы](<../Справочник — Карта методобазы- задача, документ, навык.md>), строка
  «Органика и контент».

## Цель и когда применять

Новый проект — новый сайт или сайт с историей — получает работающую машину от спроса до замера в деньгах. Применять:
первое подключение; повторное — после перевода профиля на новую версию; аудит, когда машина работает частично.
Не применять для работы машины в уже подключённом проекте — это навык `content-engine` по каталогу операций.

Что прочитать до начала, полностью: [Карту Контент-машины](<Справочник — Карта Контент-машины (контуры, связи, ритм).md>)
(модули и петли), [методологию каталога операций](<Методология — Контент-машина, каталог операций (для навыка и сервера MCP).md>)
(маршрут, ✋, деньги, запись вовне), навык `content-engine`.

## Что нужно от проекта

Вопросы владельцу — по одному, с вариантом по умолчанию; блокирующие — первыми.

| Что | Обязательно | Без этого |
|---|---|---|
| Ниша: кластер 10–15 запросов с сотнями показов; регион не узкий; в топе не только маркетплейсы | да, блокирует | машина забирает спрос, а не создаёт; ниши нет — машину не ставим |
| Источник выдачи: Keys.so (`KEYSO_API_KEY`) или Yandex Search API (`YANDEX_SEARCH_API_KEY`, `YANDEX_FOLDER_ID`) | да, блокирует | `cluster` выходит с кодом 3: нет кластеров, карты спроса и очереди |
| Корпус: все опубликованные тексты папкой markdown с шапкой (slug, title, url) — `corpus import` по карте сайта | для сайта с историей — да, блокирует | анти-дубли не видят живых страниц |
| Раздел статей: чистые адреса латиницей, рубрики, карта сайта | да | статьям некуда выходить |
| Режим публикации: ручная вставка или публикатор (`static_repo`, `cms_api`, свой `module:`) и сборщик страницы под CMS | да, решение владельца | пакет статьи не собрать под сайт |
| Консоли: Search Console (файл сервисного аккаунта), Вебмастер (`YANDEX_WEBMASTER_TOKEN`) | для сайта с историей — сразу; для нового — со дня запуска | нет спроса по своим показам, пульса, индексации |
| Wordstat (через Yandex Cloud) | желательно | годность ниши и заморозка без частот |
| Источник денег по страницам и за окно ставки (Ядро данных, CRM, CSV по шаблону) | для контура Доказательство — да | ставка, экономика и закрытие направления — «нет данных» |
| Источник гипотез Движка роста (карточки файлом или хранилище Движка) | для ставок — да | ставка только вручную, итог не возвращается в выбор тем |
| Генератор картинок и хранилище — свои, не чужого проекта | по решению владельца | картинки по шаблону или без картинок |
| Мессенджер для сводки, устройство или сервер для расписания | желательно | панель только файлом; доказательство не идёт само |
| Файл секретов вне git | да | — |

Секреты — только именами переменных; значения не печатаются и не попадают в профиль.

## Сценарий по шагам

### Шаг 1. Проект подключён к канону

Если у проекта нет паспорта, журнала действий и базы инцидентов — сначала
[Плейбук — Подключить проект к канону](<../../_Движок/Сценарии/Плейбук — Подключить проект к канону.md>).

### Шаг 2. Выпуск пакета

```text
py -3 D:\Knowledge-OS\_Движок\Инструменты\kos_release.py issue --package D:\Knowledge-OS\_Движок\Пакеты\content_engine --into <проект>\<папка скриптов>\content_engine --first
py -3 D:\Knowledge-OS\_Движок\Инструменты\kos_release.py check --into <тот же путь> --package D:\Knowledge-OS\_Движок\Пакеты\content_engine
```

Рядом с `content_engine\` — папка инстанса (`content_instance\`): профиль, `data\`, `reports\`, адаптеры проекта.
Команды машины — из родительской папки: `py -3 -m content_engine <операция> --profile <инстанс>\profile.yaml`.
Путь выпуска и инстанса — строкой в паспорт проекта. Подробно о выпусках —
[Плейбук — Система с кодом](<../../_Движок/Сценарии/Плейбук — Система с кодом- версия, выпуск, новый пакет.md>).

### Шаг 3. Корпус

Сайт с историей — `py -3 -m content_engine corpus import --profile <профиль> [--sales]` (с выпуска 1.6.0): страницы
разделов статей (и продающие с `--sales`) по карте сайта `site.sitemap_url` или `site.sitemap_file`, включая индекс
карт, — в папку `corpus/site` инстанса с шапкой `slug`, `title`, `url`, `date`; отчёт «записано N — прочитано N» и
готовая строка `corpus.folders` для профиля. Прочитать пару файлов глазами: текст статьи, а не меню. Страницы, которых
нет в карте сайта, или CMS, отдающая текст скриптом, — выгрузка скриптом инстанса, файлом в репозитории проекта.
Новый сайт — пустая папка корпуса и `queue.pace.domain_since`: тогда пустой корпус в самопроверке жёлтый.

### Шаг 4. Профиль

`py -3 -m content_engine profile template > <инстанс>\profile.yaml` и заполнить. Каждое поле обязательно:
молчаливых значений нет. Решения, которые принимает владелец, — вопросом с вариантом по умолчанию:

- домены, разделы статей и продающих страниц, регион, базы выдачи;
- источники спроса и выдачи, корпус, ценность страниц (`sources.value`);
- роли моделей — псевдонимы «-latest», вычитка фактов — второй моделью без контекста автора;
- разметка — `schema_format: microdata` для проектов под Яндекс (правило SEO-канона), `json-ld` — для Google;
- направления и квоты, ритм выпуска, бюджет и курс валюты;
- права на запись — ступень `files` везде; выше — только «да» владельца и строка в журнале действий;
- `bets.min_step: 1`, если итог ставки должен опираться только на деньги (по умолчанию 2 — допускает «заявки × чек»).

`profile check` — профиль проходит.

### Шаг 5. Самопроверка и годность ниши

`check` → `onboard`. Красное однозначное — чинится сразу; остальное — в паспорт подключения со следующим шагом.
`onboard` задаёт два решения владельца: режим вычитки фактов и ритм выпуска (`onboard --answer`).
Новый сайт: пустой корпус даёт красный пункт «корпус» — это ожидаемо до первой статьи, в паспорт так и пишется.

### Шаг 6. Подключить все модули — паспорт подключения

Пройти таблицу сверху вниз. Для каждой строки — состояние в паспорт подключения (шаблон ниже). Модуль, который
проект пока подключить не может, — «отложен» с причиной и тем, что нужно; решение отложить принимает владелец.

| Модуль | Что подключить | Признак «подключён» |
|---|---|---|
| Основание: профиль, секреты, права | шаги 4–5 | `profile check` зелёный; ступени прав названы |
| Основание: роли моделей, бюджет, учёт расхода | `models`, `budget` | `check`: роли моделей, вычитка, судья — зелёные |
| Основание: известные ответы | свои пары «вход → ожидаемое решение» проекта | `known-answers` — совпало M из M |
| А1 Сбор спроса | `sources.gsc`, `webmaster`, `keysso`, `demand_file`, `wordstat`, `suggest`, `client_questions` | `demand collect`: записано N — прочитано N, N > 0 |
| А2 Кластеры | `sources.keysso` или `serp_order` с `yandex_search` | `cluster` — код 0 |
| А3 Карта спроса и заморозка | `map build`; история спроса — `freeze scan --fetch` (платно, с ценой и «да») | карта собрана по всему корпусу |
| А4 Пробелы, конкуренты, «поле шире» | `search.competitors`, `field.file` | `competitors snap` дал первый снимок |
| Б1 Ставка | `sources.growth`; ставка каждой теме — `queue bet` до взятия | `check`: ставки из гипотез — зелёный |
| Б2, Б4 Анти-дубли, гейт, бронь | `thresholds`, `stop_words`, `brand_words`, деньги страниц | `gate topic` на известных ответах совпадает |
| Б3 Судья | роль `judge`; эмбеддинги — по желанию, платно | `judge task` на «спорной» теме |
| Б5 Очередь | `queue`, `directions` | `queue status`: запас не ниже нормы |
| В1–В2 Разбор топа, бриф | `prepare`, `brief` | первый бриф утверждён владельцем |
| В3–В4 Текст, критика, вычитка | `write`, `facts`, `niche` | вычитка второй моделью прошла |
| В5 Картинки | `images` — провайдеры и хранилище проекта | `images plan` и `make` на первой статье |
| В6 Сборка | `assemble.adapter`: `html`, `markdown` или сборщик проекта | `assemble contract` выполнен |
| В7 Гейт статьи | `gate_article` | первая статья — «годна» |
| Г1 Публикация | `publish.mode`, `adapter`, `hosts`, `allow` | первая статья на сайте |
| Г2 «Доехало» | `publish verify`; браузер — по желанию | «доехало» по первой статье |
| Г3 Индексация | `indexing` (IndexNow, Вебмастер, Search Console), `indexing.allow` | заявка или статус по первой статье |
| Г4 Записи | `records`, `paths.published_dir`, `publish.journal_path` | книга ставок: день выкладки и даты замеров |
| Д1 Пульс | консоли, `monitor`, `notify` | первый `pulse run`; сводка — по праву |
| Д2 Замер ставки | `bets.money` (файл или адаптер), `bet backfill` | `check`: деньги за окно ставки — зелёный |
| Экономика статьи | `economics` | первый отчёт без «нет данных» по цене |
| Д3 Аудит недели | `audit checklist --apply`, затем `audit run` | первый аудит, свежесть в пульсе |
| Д4 Дожим | `refresh` | первый `refresh scan` |
| Д5 ИИ-видимость | `ai score`; цитирование — `ai_visibility.citations`, `max_quota` | первый балл пригодности |
| Д6 Поведение (опция) | `behavior.kind: metrika`, имена переменных счётчика | первый `behavior scan` или «неприменим» |
| Ритм: расписание, план недели | `schedule.kind`, `schedule install --apply` по «да»; `week plan` | `schedule list`; запуски в `data/schedule_runs.jsonl` |

### Шаг 7. Первая статья машиной целиком

`demand collect` → `cluster` → `map build` → `queue build` → `queue bet` → `queue refill` → `queue take` →
`prepare top` → `prepare brief` → `prepare check` → `prepare approve` ✋ → `write task` → `review task` →
`review check` → `gate article` → `images` → `gate article` → `assemble build` → публикация → `publish verify` →
`index submit`. Развилки и ✋ — поле `next` каталога выпуска. Каждая ручная сборка в обход машины — строка в паспорт:
что не сработало и почему.

### Шаг 8. Включить доказательство

В день первой выкладки: `bet backfill`, `pulse run`, `audit checklist --apply`, `schedule install --apply` по «да»
владельца. Без расписания контур Доказательство не запускается сам: статьи выходят, а замера нет.

### Шаг 9. Приёмка

- `check --contours`: по каждому контуру «работает» или «не подключено» — и это совпадает с паспортом подключения.
- Паспорт подключения: ни одной пустой строки; у каждого «отложен» — причина, что нужно и решение владельца.
- `kos_release check` — выпуск совпадает с паспортом выпуска.
- Строка в журнал действий проекта: что подключено, что отложено, как проверить.
- Правки пакета, которых потребовал проект, — в канон с тестом (чат канона), не в выпуск проекта.

## Паспорт подключения — шаблон

Файл `<инстанс>\Паспорт подключения машины.md`, обновляется при каждом подключении или откладывании модуля.

```markdown
# Паспорт подключения Контент-машины — <проект>

Выпуск: <версия> · профиль версии <N> · дата: ГГГГ-ММ-ДД · `check --contours`: <итог>

| Модуль | Состояние | Чем подключён / что нужно | Решение владельца | Дата |
|---|---|---|---|---|
| А1 Сбор спроса | подключён | Вебмастер, Keys.so, Wordstat | — | |
| Д2 Замер ставки | отложен | нужен файл денег по страницам | отложить до CRM, 2027-01 | |
| Д6 Поведение | неприменим | опция, Метрики нет | не нужно | |
```

## Частые ошибки

- **Частичная установка.** Поставили Спрос и Производство, «Доказательство потом» — и потом не наступает: машина
  пишет, но не знает, что сработало. Модуль без состояния в паспорте — не подключён.
- **Нет источника выдачи.** Очередь пуста, и это выглядит как «писать нечего».
- **Корпус не выгружен.** Машина предлагает темы, которые уже закрыты живыми страницами.
- **Ставки нет.** Тема без ставки проходит путь, но через 90 дней её не с чем сравнить: ставка — до взятия.
- **Расписание не поставлено.** Пульс, замер и аудит не идут сами.
- **Проектное в пакете.** Правка выпуска руками под проект — отказ `kos_release check` и потеря правки при обновлении.
- **Права подняты агентом.** Ступень выше `files` — только словами владельца и строкой в журнале.
