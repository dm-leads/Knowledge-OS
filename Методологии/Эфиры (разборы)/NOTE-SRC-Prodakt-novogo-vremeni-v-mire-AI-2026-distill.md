# NOTE-SRC — Продакт нового времени: кто он в мире AI (Торбичев × Красинский, 2026)

## Источник

- Эфир: **«Продакт нового времени: кто он в мире AI?»**, YouTube `cTIbcYj0JvI`.
- Участники: **Илья Красинский** (Product Heroes / Heroes Camp, GAP-теория, юнит-экономика) и **Андрей Торбичев** (ведущий, продуктовый эксперт).
- Формат: живой разговор + демонстрации экрана + ответы на вопросы зала (~84 чел.).
- Разметка ниже: `[Красинский]` / `[Торбичев]` — чьё утверждение; `[вывод]` — моя интерпретация; `[применение]` — как ложится на нас. Таймкодов в транскрипте нет — адрес = тема.

## Краткая суть (7 пунктов)

- Прорыв не в новых моделях, а в **харнессе** вокруг них: пул агентов, скиллы, критики, графы. `[Красинский]`
- Длинные продуктовые процессы (релиз→метрики→аналитика→гипотезы→дизайнер→разработчик, ~12 шагов) **схлопываются до дней**: вместо найма людей — «найм» хороших агентов с GitHub. `[Красинский]`
- **Аналитика перестаёт быть «средней»:** graphify строит граф по коду + событиям + тикетам + касаниям, и агент по нему за 2-3 вопроса находит **корневые причины** там, где данные размазаны по 5-7 системам. `[Красинский]`
- Главный контрапункт: **«сделать можно всё — вопрос ЧТО делать»**; сеньорность и фундамент (математика, методология, архитектура) стали важнее, а не менее важны. Разница sinior/agent — 50-100× по **работающим** вещам, не по строкам кода. `[Торбичев]`+`[Красинский]`
- **Скиллы победили MCP и текстовые правила:** 90% скиллов делают **исполняемыми** (скрипт + гейты + валидация), потому что текст агент каждый раз читает по-разному. `[Красинский]`
- **Агенты-критики** (фальсификация/опровержение себя) — самое важное, с чего начинать. `[Торбичев]`+`[Красинский]`
- **Порядок на диске = SSOT**: одна папка `.agents`, остальные (Claude/Codex/Cursor) — симлинки на неё; агенты не должны путаться между несколькими местами. `[Красинский]`

## 1. Харнесс и схлопывание процессов

- `[Красинский]` Вдохновляет не Sonnet/Codex/Claude сами по себе (прирост есть, стали чуть умнее), а **рост харнесса** в индустрии — много популярных фреймворков.
- `[Красинский]` Классический процесс теряет смысл на каждом из ~12 шагов (постановка → дизайн → интервью → сборка). Теперь схлопывается **до дней** без дизайнера/маркетолога/копирайтера — вместо них «найм» хорошо написанных агентов с GitHub. Это стало **регулярной системной историей** (не сотни, но уже десятки кейсов).
- `[Красинский]` Рабочий режим: обычно **~10 чатов в Codex, в каждом 5-7 субагентов**, параллельно в коде. Внутренний рейтинг сложности задач 1-3 / 4-6 / 7-9 / 10 — под сложность по-разному ведётся процесс.
- `[применение]` У нас уже есть пул субагентов/воркфлоу; валидирует наш подход и планку «10 чатов × 5-7».

## 2. Аналитика индивидуального уровня (ядро эфира)

- `[Красинский]` Раньше считали **в среднем** (конверсия, средний чек, сегменты), потому что миллион людей глазами не осмотреть. Теперь — можно.
- `[Красинский]` Берём код-базу + **все события, всех пользователей, все касания** (звонки, транскрибация, задачи из Jira, переписка Telegram) → гигантский **стабильный граф** (пример: 2,5 млн пользователей, куча параметров). Если граф грамотный и **избыточный**, то по малому числу симптомов **моментально находятся корневые причины**.
- `[Красинский]` Кейс LinkedIn Hero: 2/3 постов роботов **убивают** жёсткими чекерами. Поиск корневых причин и скорость исправления сжались **до секунд**; всплывали неочевидные вещи (нарезка на чанки, запись в БД, corner case, который из кода не видно).
- `[Красинский]` Кейс платёжного шлюза (клиент 2-3 млн польз., >$1M): теряется 60-70% на оплате. За 2-3 вопроса локализовали: ошибка банка (Visa/MC) **не была обработана — потому что не спроектирована**, пользователя редиректили на главную. Нашли через граф: кто словил ошибку — почти не возвращался; граф связал ошибку → экраны → код → тикеты. Обычно эта информация **размазана по 5-7 системам**.
- `[вывод]` Ценность не в «красивой визуализации для человека», а в **навигируемом причинно-следственном графе для агента**, который добегает до корня (как в Теории ограничений Голдратта / root-cause analysis).

## 3. graphify — что именно делает (подробно)

- `[Красинский]` graphify (~100k★ на GitHub, «правда очень хороший инструмент», перепробовал кучу RAG — лайт/большие/маленькие). Строит не просто граф связей, а **дописывает каждой связи причинно-следственную цепочку/тег**: «этот пост написан на основе этого видео», «этот код — на основе этого», «эти объекты коррелируют / связаны / в непонятной связи».
- `[Красинский]` **Визуализация нужна не человеку, а агенту** — по ней агент хорошо «раскапывает» до корневых причин.
- `[Красинский]` Что подцепляет нодами: тикеты Jira со всеми метаполями; **проиндексированную код-базу** (методы, функции, фронт/бэк, что в каком порядке вызывается); **все события и их параметры**; обращения в поддержку. Первично — **граф по коду**, затем поверх — события/аналитика.
- `[Красинский]` Магия = **связать поведение человека в конкретном состоянии с кодом**, который в этом состоянии исполняется. Дальше можно спросить агента: «сопоставь граф с экранами пользователя, свяжись с тикетами, найди баги/дефекты» и «а в тикетах мы это вообще упоминали/делали?».
- `[применение]` Это ровно наша будущая **сквозная аналитика**: если описать модель (система → сущность → поле → метрика) и подсунуть события/тикеты/код интеграций, graphify даёт агенту карту, где видно, **где в цепочке до прибыли рвётся логика**. Уже разобран у нас: [[graphify-ocenka]] (карточка в волте «Экосистема инструментов»). Приватность: код — локально; доки/данные — уходят в бэкенд → на ПДн только локальный бэкенд.

## 4. «Сделать можно всё — вопрос ЧТО делать» (контрапункт Торбичева)

- `[Торбичев]` Пиетет поубавился: сейчас **сделать можно что угодно** (граф на 2,7 млн — не проблема). Проблема — **что делать; этого почти никто не понимает**.
- `[Торбичев]` Кейс: товарищ вайб-кодингом написал билетную систему — работает через раз. Агенты сказали «БД не нужна, пиши в файлах», и каждый новый пользователь перезаписывал предыдущего → **данных нет**. Полгода — под переписывание. Сделано **без понимания структуры/архитектуры**.
- `[Торбичев]` Руководитель разработки в крупной компании «полгода не видел ни строчки кода» → это пугает.
- `[применение]` Анти-паттерн, ровно наш риск с самописью: сначала архитектура/модель, потом код. Совпадает с нашим правилом «запрет в коде, а не в промпте» и «никаких разовых скриптов».

## 5. Сеньорность, фундамент, порядок операций

- `[Красинский]` Разница sinior / middle+ / agent — **50-100× по производительности**, и это не фигура речи. Производительность = **число работающих без человека вещей**, а не строк кода и не «изображает, что работает».
- `[Красинский]` Федеральное агентство: пишет 3 релиза за 2 часа вместо 1/день — но их **и раньше никто не читал, и сейчас**. → локальная оптимизация ненужной работы + **много плохого кода**; метрики/конверсия не растут.
- `[Красинский]` Сеньор знает, где «10 раз отмерить». Когда агент неделю выдаёт хрень — ошибка всегда в **как спроектировано/сделано/собрано**. «Недостаток часа на планирование компенсируется месяцем отладки по ночам».
- `[Красинский]` **Фундаментальные навыки стали важнее.** Сам инвестирует в матанализ и **теорию категорий** (процессы на языке математики), GAP-теорию, теорию групп — «любая работа агента = работа операций».
- `[Красинский]` **Порядок операций критичен** («сначала снял штаны, потом пописал»). Мы все стали топ-менеджерами: **каждый день «нанимаем» агентов с GitHub** по чек-листам/стандартам, получая min middle+ в слабых зонах.
- `[Красинский]` Массовый кризис: люди думали, что хорошие специалисты, а на фоне агентов прилетает, сколько они не знают (СТО, продакты, аналитики, дизайнеры) — смотрели только внутри своего окружения, не Global.

## 6. Скиллы, MCP, критики, инциденты (техника харнесса)

- `[Красинский]` **Скиллы победили MCP** в смысле: MCP = сервер поверх API → быстро вырастает в **монолит** (50-60 ручек). Скилл = **микромодульная автономная** единица поверх API; внутри — скрипты или текст.
- `[Красинский]` **90% скиллов делаем исполняемыми** (YAML + минимальные инструкции: какие скрипты запускать и что делать дальше). Причина: чисто текстовый скилл агент **каждый раз читает/интерпретирует по-разному**, текст разрастается. Скилл: инпут → **стейт-машина** (`workflow.yaml`: жёсткие входы, проверки, этапы, **гейты** = как хук, останавливает агента на браке и заставляет переделать) → валидация результата (нет брака, переиспользуемо).
- `[Красинский]` **3 самых полезных скилла:** (1) **«Вопросы»** — любую непонятную задачу начинаю с него: разбирает по Job-to-be-Done, зовёт лучших экспертов, задаёт 7-20 вопросов по важности, вытаскивает из тебя **бриф** → вход любому агенту (лечит «болезнь чистого листа», брифует как арт-директор). (Остальные — критик и outcome-дизайнер, см. ниже.)
- `[Красинский]` **Самокритик** (Product Games): после любой работы определяет **5 лучших мировых экспертов** в теме (Боб Маэста, Кристенсен…), их «глазами» находит 5 недостатков + 5 конкретных улучшений; ты соглашаешься выборочно, несколько циклов — улучшают любой результат. Первое действие критика — **фальсификация/опровержение** себя. Работает **вместе с человеком**: агент предлагает, решаешь ты.
- `[Красинский]` **GEPA**: прогнать все JSON-логи чатов Claude/Codex → спросить агента, где он зацикливался/ошибался → **улучшить собственные скиллы/промпты**, чтобы инцидентов не было. Инциденты агент **копит и проверяет** (за неск. дней ~8 при 10 чатах × 5-7 агентов) → на следующей итерации улучшает качество скиллов/кода.
- `[Красинский]` **Outcome-дизайнер** — агент, который ставит **цепочку задач**; DoD-матрица лендинга: text, offer, proof, analytics, form, mobile design, tag, next-action; статус «светофором»; baseline/target для активации.
- `[применение]` Прямо наше: у нас уже есть ToV-критик и гейты `check_structure.py`. Стоит: (а) добавить **фальсифицирующего** критика; (б) сделать скилл «Вопросы» как вход в любую новую задачу; (в) наши навыки держать **исполняемыми** (мы это и делаем — совпадает с [[guard-in-code-not-in-prompt]]).

## 7. SSOT на диске (.agents + симлинки)

- `[Красинский]` Один **source of truth** — папка `.agents` (~2 десятка агентов, 320 скиллов, хуки). Папки Claude/Codex/Cursor — **симлинки** на неё. Агенты не должны иметь несколько мест → **строгий порядок на диске**, иначе стабильно ошибаются.
- `[применение]` У нас скиллы дублируются в проект и в глобальную (`~/.claude/skills`) — см. [[skills-install-dual-scope]], [[claude-skills-mirror]]. Симлинк-подход = кандидат убрать дубли и держать один источник. Согласуется и с нашей матрицей уровней (глобальный/проектный).

## 8. Люди, эмпатия, персонализация

- `[Торбичев]` Эмпатия/понимание людей — агенты **далеко** позади. Юмор: провёл баттл ИИ vs стендап-комик; **победил человек**, хотя часть зала: «ИИ шутил лучше, но голосовал за человека». Юмор адресован узкой группе, нужен свой прожитый опыт.
- `[Торбичев]` Анти-тренд усиливается: **глубоко понимать своих потребителей и конкурентов** (агентами — смотреть, как действуют конкуренты, и делать иначе).
- `[Красинский]` Персонализация: под разных людей роботы уже **пишут по-разному** (кому — чёткость, кому — простые слова, кому — предсказуемость шагов). Не идеально под каждого, но «достаточно хорошо, чтобы человек сказал вау». Ключ — **память**, которую человек не удержит (как продажник помнит «не звоните до 11»).
- `[Торбичев]` Легко предсказать большую группу, трудно — конкретного человека.

## 9. AI-native организация (меньше совещаний, документы-артефакты)

- `[Красинский]` Скинуть всю переписку/Google-файлы → за 1-2 недели агент **структурирует порядок в папках**; добавить слой «что такое хорошо спроектировано»; подгрузить Jira по MCP, Telegram/Slack; код — **индексировать графом** (для безопасности, чтобы не утекло).
- `[Красинский]` Тогда **совещание = неэффективная форма**: приходим с **артефактом-документом**, учитывающим все позиции (маркетинг/продажи/продакт/безопасники). Пример: воркфлоу «портрет безопасника → его JTBD → юр-документ, изучивший нашу код-базу»; банки: «лучший документ, ни один юрист так не напишет».
- `[Торбичев]` **AI-native = команда, работающая с ИИ с нуля.** Прикрутить ИИ к старым процессам тем труднее, чем крупнее компания; настоящих AI-native старых/крупных компаний он не видел, только малые новые (3-7 чел., МФТИ 25-27 лет, обороты в млн $, мало сопротивления).
- `[Красинский]` **AI-native = 90% работы делает агент.**

## 10. Профессии, дизайн, вкус

- `[Красинский]` Узкая специализация закончилась; **двурукие/фулстек победили**. Маркетолог с агентами получает арт-дирекшен и за 2 недели запускает продукт от $5k (но **не в одиночку** — в одиночку теряешь деньги, «видишь только то, что видишь»). Верит в команду-«баскетбол» суперпрофи, пасующих через агентов.
- `[Торбичев]` Наоборот, **суперсила/насмотренность дорожает**: «средний класс» вымывается → есть богатые и бедные, то же в профессиях, но быстрее. Джуном войти за 3 дня, но кто глубоко разбирается (типографика, вкус) — ценнее.
- `[Красинский]`+`[Торбичев]` **Design MD** (Google, ~месяц) хорошо структурирует работу агента (токены отдельно, меньше бардака в HTML/CSS) — но в ней **нет вкуса/чуйки**. Смотреть Superdesign, Penso (по референсу). Dribbble/Behance красиво, но **не работает** (плохие метрики). Читать **Кандинского «Точка и линия на плоскости»** — с агентом (он «начинает видеть вместе с тобой»). **TRIZ** в агент — генерит идеи.
- `[Красинский]` **Нельзя экстраполировать**: 10 человек ставят задачу агенту — у 1 выходит гениально, у 9 нет; агент ужасно **персонализирован** под твою память/стиль/методологию.

## 11. Методология и обмен скиллами

- `[Красинский]` **Методология = воспроизводимый способ получать качественный результат вне зависимости от того, кто ставит задачу.** «Только в IT кажется, что методология не важна». В индустрии много легаси — подходы 10-15-летней давности, «а сейчас 2026».
- `[Красинский]` **«Перекрёстное опыление»**: команды обмениваются скиллами/харнессом/кусками (как бактерии ДНК) → безумная скорость эволюции (изменчивость+размножение+отбор+наследуемость).
- `[Красинский]` Начать с агентов-критиков (20-30), которые **опровергают себя**, а не как плохой джун доказывают, что всё хорошо.

## Как применяем у нас (приоритеты)

1. **Сквозная аналитика через graphify** — главный кандидат: описать модель интеграций (Roistat↔amoCRM↔МойСклад), подсунуть события/тикеты/код → агент ищет, где рвётся цепочка до прибыли. Запрос в тот чат уже отдан; graphify — слой понимания поверх модели.
2. **Агент-критик с фальсификацией** — расширить наш ToV-критик: пусть **опровергает** результат (5 экспертов → 5 недостатков), а не подтверждает. Дёшево, повышает качество каждого артефакта.
3. **Скилл «Вопросы»** — вход в любую новую задачу (JTBD-бриф, 7-20 вопросов) → убивает «чистый лист». Кандидат сделать себе.
4. **Apify** — сразу в дело в проекте **Авито-демпинг** (путь C: универсальный скрапинг, авто-кастдев по площадкам). Пересекается с нашим аудитом.
5. **Исполняемые скиллы + гейты** — держим курс (у нас `check_*.py` = гейты); совпадает с «запрет в коде, а не в промпте».
6. **SSOT на диске (симлинки)** — рассмотреть, чтобы убрать дубли скиллов проект/глобальная.
7. **Методология-первой / порядок операций** — сначала модель и архитектура, потом прогон; ровно наши грабли с самописью.

## Про graphify как навык для коллег (ответ на вопрос)

- **Где graphify реально показывает ценность:** когда есть (а) код/структурированные артефакты И (б) события/аналитика/тикеты/касания для корреляции, и нужно, чтобы **агент быстро нашёл корневую причину** в размазанных по системам данных. Это техническо-аналитические контексты (наша сквозная аналитика, разбор пайплайнов, дефекты воронки).
- **Как коллеги могли бы использовать:** обернуть в **исполняемый скилл** (как у Красинского): «дай папку/репо → `graphify .` → `graph.json` + отчёт → агент отвечает на вопросы о корневых причинах». Коллега просто указывает проект.
- **Честный предел применимости:** для сотрудника с одним лендингом/текстом — избыточно; ценность появляется при данных+коде. Плюс семантический режим шлёт содержимое в бэкенд → **для ПДн только локальный бэкенд (Ollama)**. Поэтому это навык для **аналитики/разработки**, не универсальный для всех.
- **Рекомендация:** оформить как **проектный** навык (не глобальный), с чётким «когда применять» в описании, и сначала обкатать на нашем кейсе (сквозная аналитика или разбор одного репо), а уже потом делиться с коллегами с инструкцией. Держать в рамке нашей [[graphify-ocenka]] и матрицы подключения.
