# Методология — Работа с ИИ-агентами в проекте

## Краткая суть

- **Путь внедрения: чтение → вручную → автономно.** Сразу автономно — никогда. Первый результат —
  помощник, которым пользуются, и один плановый отчёт. Автономия — только после N прогонов без ошибок на
  реальных данных.
- **Своё пространство — не боевой контур клиента.** Инструменты, навыки и память агента живут в месте
  владельца. К системам клиента агент только подключается, по умолчанию на чтение.
- **Несколько чатов — диспетчер и потоки.** Один чат — один поток. Результат существует, только если лежит
  файлом. Конфликты решает диспетчер сверкой с файлами.
- **Постановка задачи — семь полей:** цель, артефакт, источники, что считать фактом, что нельзя выдумывать,
  что делать при нехватке данных, формат. Агент синтезирует поверх данных и не заменяет их.
- **Контекст — нужное, без лишнего.** Два–пять файлов вместо всей папки. Повторяемое — в правила проекта.
  После большого исследования — сжатая выжимка, дальше работа от неё.
- Правила работы агента (язык, лимиты субагентов, проверка, git) — в `agent-rules.md` канона. Здесь — как
  строить работу с агентами в проекте.

> Для быстрого знакомства человеку может хватить блока выше.
> Ниже начинается полный каноничный текст документа.
> Для агентов, правок, анализа, ревью и разрешения расхождений обязателен полный текст.

## 1. Внедрение агента в проект

### Принципы

1. **Чтение → вручную → автономно.** Каждый переход — через ворота, а не по ощущению.
2. **Сначала интерактив.** Первый отгружаемый результат — помощник, которым человек пользуется, и один
   плановый отчёт. Рой автономных ботов — потом, по мере доверия: начать с узкой задачи и расширяться после
   доказанного результата.
3. **Своё пространство — не боевой контур клиента.** Инструменты, навыки и память агента живут в
   контролируемом месте: свой репозиторий, свой сервер. Системы с кодом — пакетом канона: ссылкой или выпуском
   ([ADR-0003](<../_Движок/0 — System Docs/ADR-log/0003-code-systems-source-in-canon-releases-in-projects.md>)).
4. **Данные читаются у источника.** Маркетинговые данные живут в облаках (аналитика, реклама, CRM) и берутся
   через API и токены. Доступ к серверу нужен, только когда данные — файлы, логи или база на сервере.

### Фазы

| Фаза | Что делаем | Ворота выхода |
|---|---|---|
| **0. Доступ и осмотр** | Доступ на чтение к источникам. Ничего не меняем. Карта «что есть / чего нет» | Карта данных записана |
| **1. Минимальный мозг** | Точка входа (`CLAUDE.md` проекта — [подключение к канону](<../_Движок/Сценарии/Плейбук — Подключить проект к канону.md>)), карта систем и доступов, три–пять правил проекта. Большую базу знаний сознательно не строим | Новый чат называет правила и источники |
| **2. Данные через MCP, только чтение** | Подключаем только то, что нужно первому результату | Агент видит реальные данные и не выдумывает |
| **3. Первый результат** | Помощник (2–3 повторяемых навыка) + один плановый отчёт на чтение, который смотрит человек | Отчёт используется |
| **4. Автономия по триггеру** | Только для доказанного навыка. Изменения — через подтверждение человека. Мониторинг обязателен | N прогонов подряд без ошибок на реальных данных, назначен судья результата, определено, что считать сбоем |
| **5. Сопровождение** | Кто следит; что делать при смене API или модели | Долг сопровождения заложен сразу |

### Из разовой задачи в автономию

1. Задача повторяется? Если нет — автономия не нужна.
2. Оформить её навыком или самодостаточным планом: перезапуск без контекста из чата.
3. Прогнать вручную N раз, проверить качество и стабильность.
4. Только потом — расписание (cron или агентный рантайм на своём сервере) и уведомление человеку.

### Доступы и безопасность

- По умолчанию — только чтение. Запись — позже, точечно, под конкретную автоматизацию, с защитой в коде.
- Секреты — в переменных окружения: не в коде, не в git, не на сервере клиента.
- Автономный агент работает в своём рантайме, а не на боевом сервере клиента.

## 2. Несколько чатов: диспетчер и потоки

Нужно, когда в проекте больше трёх рабочих чатов одновременно. Иначе чаты дублируют работу и противоречат
друг другу.

- **Диспетчер** читает общий контекст (карта, план, методологии), сам работу потоков не делает. Готовит
  задания для потоков, сводит статусы, решает конфликты, точечно правит структуру.
- **Поток** — один чат, одно доминирующее направление. Читает общий контекст и свои файлы, работает в своей
  зоне.

**Правила:**
1. Один чат — один доминирующий поток.
2. Результат — только файлом в репозитории или трекере. Что не записано, того нет, даже если чат уверенно
   пишет «готово».
3. Закрывая сессию — короткая запись: что сделали, что в работе, где остановились.
4. Раз в неделю — обход чатов и срез «закрыто / в работе / следующий шаг».
5. Конфликты — через диспетчер, сверкой с файлами, а не внутри потока.
6. Новая папка, переименование, перенос файла, новый поток — только по согласованию.
7. Чату доверяю после проверки файлов: он источник работы, а не истины о состоянии файлов.
8. Чат не видит другие чаты. Общую картину держат диспетчер и журнал.
9. В общих репозиториях: перед записью — `git status`, коммит только своих путей.

**Масштаб.** Новый чат нужен, когда появилось новое доминирующее направление, текущий перегружен, нужна
параллельная работа или сменился тип задачи. Не нужен для задачи из существующего потока и для быстрого
продолжения. Чат, в который не возвращались больше двух недель, лучше заменить новым с передачей контекста.
Больше семи чатов — объединить смежные потоки или перейти на доску задач.

## 3. Постановка задачи агенту

**Агент полезен** для структурирования материалов, синтеза поверх собранных данных, брифов, сравнения
документов, превращения сырого исследования в документ, повторяемых преобразований.

**Агент — не источник истины** для метрик, которых нет в источниках, фактов выдачи без выгрузок, свойств
продукта, финансовых цифр, юридически чувствительных формулировок, секретов.

**Семь полей постановки:**

```text
Цель:
Нужный артефакт:
Файлы и источники:
Что считать фактом:
Что нельзя выдумывать:
Что делать при нехватке данных:
Формат вывода:
```

**Синтез или данные.** Агент группирует, делает выводы и приоритизирует поверх уже собранных данных. Просить
его «прикинуть» частотности, конверсии или выручку без источника нельзя. Нет данных — так и написать,
перечислить, что нужно, и перевести в исследование.

**Исследование без засорения контекста.** Два–пять релевантных файлов, а не вся папка. Исследование и рабочий
артефакт — раздельно. После большого исследования — сжатая выжимка, дальше работа от неё.

**Проверка перед запуском:** понятен ли артефакт; есть ли источники; ясно ли, что нельзя выдумывать; нужен ли
новый чат; не смешаны ли направления. Два «нет» — поставить задачу заново. Проверить бриф по семи правилам
постановки — навык `claude-brief`.

## 4. Передача контекста в новый чат

```text
Работаем только по [поток / направление] проекта [проект].

Цель: [что собрать или обновить], не смешивая с другими задачами.

Ключевые файлы:
- [путь к плану или задачам]
- [пути к нужным методологиям канона]

Правила:
- не выдумывай цифры, конверсии, CAC/CPL, выручку, маржу, данные CRM;
- нет данных — пиши «нет данных» и что нужно добрать;
- отделяй факт от вывода и гипотезы;
- многосоставная задача — сначала короткий план.

Формат ответа: сначала вывод и решение, потом артефакт; без вступлений и ухода в смежные темы.
```

Для конкретной задачи, а не направления, добавить: источник данных, горизонт проверки, нужный артефакт.

## 5. Гигиена контекста

1. **Контекст важнее формулировки.** Контекст — это чат, файлы, правила проекта и настройки. Качество растёт
   от полноты и падает от шума. Нужное дать, лишнее убрать.
2. **Модель предсказывает текст и не гарантирует факты.** Уверенная выдумка возможна всегда, поэтому факт из
   источника, вывод и гипотеза разделяются явно.
3. **Режим под задачу:** чтение и поиск без правок; план с согласованием; исполнение. Выбор режима — большая
   часть успеха.
4. **Повторяемое — в правила,** а не в каждый запрос: `CLAUDE.md` проекта и навыки. Правила грузятся в каждую
   сессию — держать их короткими.
5. **Документ — источник правды.** Дубли и мусор в контексте хуже одного актуального файла.
6. **Модель — под тип задачи:** глубокий разбор, черновики, много мелких операций — не одна «самая умная» на
   всё.
7. **MCP-сервер, плагин и навык — разные слои.** Сервер подключает внешнюю систему, плагин приносит набор
   команд, навыков и серверов, навык — инструкция под задачу. Токены — через переменные окружения, в общем
   конфиге проекта живых секретов нет. Подробнее — в
   [реестре инструментов](<../Экосистема инструментов/_manifest.md>).
