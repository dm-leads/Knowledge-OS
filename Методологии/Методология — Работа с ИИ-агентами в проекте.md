# Методология — Работа с ИИ-агентами в проекте

## Краткая суть

- **Путь внедрения: чтение → вручную → автономно.** Сразу автономно — никогда. Первый результат —
  помощник, которым пользуются, и один плановый отчёт. Автономия — только после N прогонов без ошибок на
  реальных данных. Процесс, который агент забирает целиком, работает параллельно со старым, пока не пройдёт ворота.
- **Агенту — типовая работа, человеку — суждение.** Эффект считают до старта с полными затратами; ускорение без
  контроля качества переносит узкое место, поэтому мерят инциденты и конверсию до и после.
- **Своё пространство — не боевой контур клиента.** Инструменты, навыки и память агента живут в месте
  владельца. К системам клиента агент только подключается, по умолчанию на чтение.
- **Несколько чатов — диспетчер и потоки.** Один чат — один поток. Результат существует, только если лежит
  файлом. Конфликты решает диспетчер сверкой с файлами.
- **Постановка задачи — семь полей:** цель, артефакт, источники, что считать фактом, что нельзя выдумывать,
  что делать при нехватке данных, формат. Агент синтезирует поверх данных и не заменяет их.
- **Контекст — нужное, без лишнего.** Два–пять файлов вместо всей папки. Повторяемое — в правила проекта.
  После большого исследования — сжатая выжимка, дальше работа от неё.
- **Внедрение — через доставку.** Потери между системами, а не в них: чинить связи, а не переписывать. Первый ход
  — дайджест в чат, где человек уже живёт; задача агенту кончается доставкой результата людям.
- Правила работы агента (язык, лимиты субагентов, проверка, git) — в `agent-rules.md` канона. Здесь — как
  строить работу с агентами в проекте.

> Для быстрого знакомства человеку может хватить блока выше.
> Ниже начинается полный каноничный текст документа.
> Для агентов, правок, анализа, ревью и разрешения расхождений обязателен полный текст.

## 1. Внедрение агента в проект

### Принципы

1. **Чтение → вручную → автономно.** Каждый переход — через ворота, а не по ощущению.
2. **Сначала интерактив.** Первый отгружаемый результат — помощник, которым человек пользуется, и один
   плановый отчёт. Рой автономных ботов — потом, по мере доверия: начать с узкой задачи и расширяться после
   доказанного результата.
3. **Своё пространство — не боевой контур клиента.** Инструменты, навыки и память агента живут в
   контролируемом месте: свой репозиторий, свой сервер. Системы с кодом — пакетом канона: ссылкой или выпуском
   ([ADR-0003](<../_Движок/0 — System Docs/ADR-log/0003-code-systems-source-in-canon-releases-in-projects.md>)).
4. **Данные читаются у источника.** Маркетинговые данные живут в облаках (аналитика, реклама, CRM) и берутся
   через API и токены. Доступ к серверу нужен, только когда данные — файлы, логи или база на сервере.

### Фазы

| Фаза | Что делаем | Ворота выхода |
|---|---|---|
| **0. Доступ и осмотр** | Доступ на чтение к источникам. Ничего не меняем. Карта «что есть / чего нет» | Карта данных записана |
| **1. Минимальный мозг** | Точка входа (`CLAUDE.md` проекта — [подключение к канону](<../_Движок/Сценарии/Плейбук — Подключить проект к канону.md>)), карта систем и доступов, три–пять правил проекта. Большую базу знаний сознательно не строим | Новый чат называет правила и источники |
| **2. Данные через MCP, только чтение** | Подключаем только то, что нужно первому результату | Агент видит реальные данные и не выдумывает |
| **3. Первый результат** | Помощник (2–3 повторяемых навыка) + один плановый отчёт на чтение, который смотрит человек | Отчёт используется |
| **4. Автономия по триггеру** | Только для доказанного навыка. Изменения — через подтверждение человека. Мониторинг обязателен. Замена процесса целиком — параллельно со старым (ниже) | N прогонов подряд без ошибок на реальных данных, назначен судья результата, определено, что считать сбоем; при замене процесса — качество не хуже старого на одном проверочном наборе |
| **5. Сопровождение** | Кто следит; что делать при смене API или модели | Долг сопровождения заложен сразу |

### Из разовой задачи в автономию

1. Задача повторяется? Если нет — автономия не нужна.
2. Оформить её навыком или самодостаточным планом: перезапуск без контекста из чата.
3. Прогнать вручную N раз, проверить качество и стабильность.
4. Только потом — расписание (cron или агентный рантайм на своём сервере) и уведомление человеку.

**Замена процесса агентом — параллельный запуск** (Гурбанов, конференция «Клиенты из нейросетей», 11.2026 —
[выжимка](<_исходные-заметки/Конференция — клиенты из нейросетей (2026-11)/Выжимка — часть В (Спиридонов, Гурбанов).md>),
тезис Г-2). Когда агент забирает процесс целиком, а не помогает в одном шаге, новый процесс строят рядом со старым.
До переключения агент работает в **теневом режиме**: читает те же входы и готовит результат, но внешних действий не
выполняет — иначе будут два сообщения клиенту, две заявки или повторный платёж. Если нужен боевой пилот — отдельные,
непересекающиеся случаи, один исполнитель на случай и защита от повторных операций. Старый не трогают, пока новый
не прошёл ворота фазы 4:

1. **Проверочный набор** — реальные случаи старого процесса с известным правильным результатом; на нём сравнивают
   оба процесса.
2. **N прогонов подряд без ошибок** на этом наборе и на живых случаях; качество нового **не хуже старого** по
   заранее записанному критерию.
3. **Старый выключает владелец результата**, а не агент: человек остаётся владельцем результата и после замены
   ([Модель риска автономии](<Методология — Модель риска автономии агента.md>)).

Срок параллельной работы задаёт N прогонов, а не календарь: «3–6 месяцев» у спикера — без источника. Для малой
компании первый ход по-прежнему дешёвый и в зоне человека (раздел 7, п. 1, 8, 9). Параллельный запуск — форма
ворот для полной замены процесса, а не обязательная перестройка всех процессов «с нуля».

### Доступы и безопасность

- По умолчанию — только чтение. Запись — позже, точечно, под конкретную автоматизацию, с защитой в коде.
- Секреты — в переменных окружения: не в коде, не в git, не на сервере клиента.
- Автономный агент работает в своём рантайме, а не на боевом сервере клиента.

## 2. Несколько чатов: диспетчер и потоки

Нужно, когда в проекте больше трёх рабочих чатов одновременно. Иначе чаты дублируют работу и противоречат
друг другу.

- **Диспетчер** читает общий контекст (карта, план, методологии), сам работу потоков не делает. Готовит
  задания для потоков, сводит статусы, решает конфликты, точечно правит структуру.
- **Поток** — один чат, одно доминирующее направление. Читает общий контекст и свои файлы, работает в своей
  зоне.

**Правила:**
1. Один чат — один доминирующий поток.
2. Результат — только файлом в репозитории или трекере. Что не записано, того нет, даже если чат уверенно
   пишет «готово».
3. Закрывая сессию — короткая запись: что сделали, что в работе, где остановились. Форму и место записи
   предлагает черновик [Стандарт — Непрерывность работы с агентами](<Стандарт — Непрерывность работы с агентами.md>)
   (10.2026): точка возврата потока. До принятия владельцем это предложение, а не правило.
4. Раз в неделю — обход чатов и срез «закрыто / в работе / следующий шаг».
5. Конфликты — через диспетчер, сверкой с файлами, а не внутри потока.
6. Новая папка, переименование, перенос файла, новый поток — только по согласованию.
7. Чату доверяю после проверки файлов: он источник работы, а не истины о состоянии файлов.
8. Чат не видит другие чаты. Общую картину держат диспетчер и три файла проекта — паспорт, журнал действий,
   база инцидентов ([Стандарт — Три файла проекта](<Стандарт — Три файла проекта (паспорт, журнал действий, база инцидентов).md>)).
9. В общих репозиториях: перед записью — `git status`, коммит только своих путей.

**Масштаб.** Новый чат нужен, когда появилось новое доминирующее направление, текущий перегружен, нужна
параллельная работа или сменился тип задачи. Не нужен для задачи из существующего потока и для быстрого
продолжения. Чат, в который не возвращались больше двух недель, лучше заменить новым с передачей контекста.
Больше семи чатов — объединить смежные потоки или перейти на доску задач.

## 3. Постановка задачи агенту

**Агент полезен** для структурирования материалов, синтеза поверх собранных данных, брифов, сравнения
документов, превращения сырого исследования в документ, повторяемых преобразований.

**Агент — не источник истины** для метрик, которых нет в источниках, фактов выдачи без выгрузок, свойств
продукта, финансовых цифр, юридически чувствительных формулировок, секретов.

**Семь полей постановки:**

```text
Цель:
Нужный артефакт:
Файлы и источники:
Что считать фактом:
Что нельзя выдумывать:
Что делать при нехватке данных:
Формат вывода:
```

**Синтез или данные.** Агент группирует, делает выводы и приоритизирует поверх уже собранных данных. Просить
его «прикинуть» частотности, конверсии или выручку без источника нельзя. Нет данных — так и написать,
перечислить, что нужно, и перевести в исследование.

**Исследование без засорения контекста.** Два–пять релевантных файлов, а не вся папка. Исследование и рабочий
артефакт — раздельно. После большого исследования — сжатая выжимка, дальше работа от неё.

**Проверка перед запуском:** понятен ли артефакт; есть ли источники; ясно ли, что нельзя выдумывать; нужен ли
новый чат; не смешаны ли направления. Два «нет» — поставить задачу заново. Проверить бриф по семи правилам
постановки — навык `claude-brief`.

**Семь полей — задание агенту на один шаг.** Работа крупнее мелочи ведётся файлами, а не одним сообщением:
постановка → спецификация → план, переходы принимает человек. Когда это нужно и в каком объёме —
[Стандарт — Цепочка постановки](<Стандарт — Цепочка постановки (постановка, спецификация, план).md>), навык `task-chain`.

## 4. Передача контекста в новый чат

```text
Работаем только по [поток / направление] проекта [проект].

Цель: [что собрать или обновить], не смешивая с другими задачами.

Ключевые файлы:
- [путь к плану или задачам]
- [пути к нужным методологиям канона]

Правила:
- не выдумывай цифры, конверсии, CAC/CPL, выручку, маржу, данные CRM;
- нет данных — пиши «нет данных» и что нужно добрать;
- отделяй факт от вывода и гипотезы;
- многосоставная задача — сначала короткий план.

Формат ответа: сначала вывод и решение, потом артефакт; без вступлений и ухода в смежные темы.
```

Для конкретной задачи, а не направления, добавить: источник данных, горизонт проверки, нужный артефакт.

## 5. Гигиена контекста

1. **Контекст важнее формулировки.** Контекст — это чат, файлы, правила проекта и настройки. Качество растёт
   от полноты и падает от шума. Нужное дать, лишнее убрать.
2. **Модель предсказывает текст и не гарантирует факты.** Уверенная выдумка возможна всегда, поэтому факт из
   источника, вывод и гипотеза разделяются явно.
3. **Режим под задачу:** чтение и поиск без правок; план с согласованием; исполнение. Выбор режима — большая
   часть успеха.
4. **Повторяемое — в правила,** а не в каждый запрос: `CLAUDE.md` проекта и навыки. Правила грузятся в каждую
   сессию — держать их короткими.
5. **Документ — источник правды.** Дубли и мусор в контексте хуже одного актуального файла.
6. **Модель — под тип задачи:** глубокий разбор, черновики, много мелких операций — не одна «самая умная» на
   всё.
7. **MCP-сервер, плагин и навык — разные слои.** Сервер подключает внешнюю систему, плагин приносит набор
   команд, навыков и серверов, навык — инструкция под задачу. Токены — через переменные окружения, в общем
   конфиге проекта живых секретов нет. Подробнее — в
   [реестре инструментов](<../Экосистема инструментов/_manifest.md>).

## 6. Обвязка агента и петля инцидентов

Агент без обвязки приходится вести за руку. Обвязка ведёт его сама. По разбору Красинского
([Доп8](<_Красинский — полный разбор (2026-07)/Доп8 — AI-native компания (воркшоп, как её построить).md>)) и
нашей практике:

1. **Стандарты и навыки — разные слои.** Стандарт — методология: что такое хорошо и плохо, контракт результата,
   где брать актуальную API. Меняется медленно, лежит локально в каноне. Навык — узкая операция на 200–300 строк,
   собранная по стандарту. Меняется быстро. Длинный навык агент читает выборочно, поэтому длинное уходит в
   стандарт или справочник.
2. **Навык из удачного чата:** после хорошего результата — «прочитай этот чат и собери из него навык».
3. **Задача — как состояние, а не как действие:** «приведи в точку Б и докажи, где не дошёл». Агент плохо
   выполняет расплывчатое, но хорошо считает разрыв между целевым состоянием и сделанным, а этот разрыв — следующая
   задача.
4. **Восходящая петля:** один агент делает, другой (проверяющий, `maker-checker`) перепроверяет ссылки,
   документы, результат. Без неё брак.
5. **Успех — «воспользовался и получил ценность»,** а не «сделано». Работа — гипотеза: проверяется, дала ли она
   результат.
6. **Петля инцидентов.** Каждый раз, когда результат не получен, — запись в базу инцидентов проекта (что ждали,
   что вышло, класс ошибки из [Справочника классов ошибок](<Справочник — Классы ошибок данных и автоматизации.md>);
   формат — в стандарте трёх файлов проекта).
   Регулярно — разбор корневой причины, правка навыков, хуков, правил, счёт инцидентов по сценариям в следующий
   период. Так растёт время работы агента без присмотра.
   **Журнал решений человека** (Гурбанов, конференция «Клиенты из нейросетей», 11.2026 — выжимка, тезис Г-7).
   Инцидент — сбой. Журнал решений — обычная работа: в повторяющемся процессе каждый отказ человека от результата
   агента или его правка записывается строкой — что предложил агент, что решил человек, причина («холодные
   предложения из мессенджера не берём», «ролик снят: обещание без доказательства»). Причина повторилась —
   правило в навык или стандарт; ловится кодом — проверка в коде (п. 7). Журнал ведут там же, где результат
   процесса, а не в переписке. Правило владельца вне процесса («учитывай») по-прежнему записывается сразу в
   паспорт или память (`agent-rules.md`).
7. **Хуки и запреты в коде** на повторяющиеся ошибки (создание файлов не там, дубли документов), а не просьбы в
   промпте.
8. **Процессы, которые должен исполнять код, — в исполняемом виде** (YAML, конфигурация, проверяемая скриптом), а
   не только прозой.
9. **Сложность в шагах:** задача на 1–3 шага по силам простой модели, на 10 шагов — только сильнейшей. Длинную
   задачу разбивать на шаги-разрывы. Красинский (конференция «Клиенты из нейросетей», 11.2026 —
   [выжимка](<_исходные-заметки/Конференция — клиенты из нейросетей (2026-11)/Выжимка — часть Б (Илья Красинский).md>),
   тезисы 11, 13, 18): агент надёжно держит 2–3 шага, а 10–15 — только по записанному процессу. Длинный процесс
   ведут по чек-листу шагов, и каждый шаг проверяется по чек-листу качества: агент плохо исполняет расплывчатое, но
   неплохо перепроверяет себя по ясному списку. Улучшают чек-лист, а не длину промпта. Проверка — п. 4 и навык
   `maker-checker`; «готово» — таблицей «ожидание — факт» (`agent-rules.md`, «Достоверность»).
10. **Отчуждаемость с первого дня** ([Доп9](<_Красинский — полный разбор (2026-07)/Доп9 — Дорожки между системами и дайджест как первый ход (стрим о внедрении агентов).md>)).
    Навык или скрипт, который нужен не только мне, сразу пишется так, чтобы его запустил другой агент в другой
    среде по описанию — без автора и не на его машине. Навык «только для себя» — будущая работа по передаче.
    Отчуждаемость — не автономия: работа без присмотра по-прежнему только через ворота раздела 1. Проверка —
    запуск агентом с чистым контекстом в другой среде без вопросов к автору.
11. **Свой MCP-сервер — последним выбором.** Свой сервер быстро становится монолитом с легаси. Сначала готовый
    поддерживаемый сервер или навык со скриптом; свой — только когда они не справляются. Существующие серверы
    это правило не отменяет.
12. **Ускорение без контроля качества переносит узкое место** (Красинский, конференция «Клиенты из нейросетей»,
    11.2026 — выжимка части Б, тезисы 10, 16, 18). Агенты ускоряют разработку сайтов, ботов и процессов, но узкое
    место было не там: оно уходит в контроль качества, управление и оркестрацию. По наблюдению спикера (без
    опубликованных данных), у команд, которые много делают агентами без проверки, конверсия к продаже падает, а на
    каждое исправление появляются 2–3 новые проблемы. «Если у вас хаос, агенты дадут автоматизированный хаос».
    Поэтому скорость не служит мерой внедрения. Мера — **инциденты и конверсия до и после**: перед внедрением
    записать базу (инциденты по видам за неделю — п. 6, конверсия шага, который меняют), после — сравнить на том же
    определении ([Стандарт — Консистентность метрик](<Стандарт — Консистентность метрик.md>)). Выросли инциденты
    или упала конверсия — стоп и разбор корневой причины, а не следующее ускорение.

## 7. Как менять компанию вместе с агентами

Узкое место сместилось: диагностика стала дешёвой, дорого стоит изменение. Анализ звонков или кода сам не
двигает ни одной метрики, пока люди не поменяли поведение и процессы.

1. **Хороший ход** даёт мгновенный локальный выигрыш всем, кого касается, и удешевляет следующие ходы. Доступ к
   данным получают, предложив снять с людей ручную работу: автозаполнение CRM, шаблоны договоров, бот вместо
   портала.
2. **Не спорить, а убирать работу.** Рациональное убеждение вызывает сопротивление. Люди меняются, когда новое
   сразу легче старого.
3. **Внутренняя продажа = внешняя.** Узнать, что человек хочет и чего боится (служба безопасности, юристы,
   продажи), и заранее ответить на его чек-лист.
4. **Вирус изменений.** Начать с двух–трёх людей рядом, готовых меняться; союзники подтягивают следующих. Ноль
   совещаний и разрешений там, где решение в своей зоне. Не уговаривать, а показать на 10–20 реальных случаях
   человека; сначала автоматизировать то, что его раздражает, — так получают доверие (Доп9). Своя зона — чтение
   и дайджест в свой чат; запись в чужие системы и первая отправка коллеге — по «да»
   ([Модель риска автономии](<Методология — Модель риска автономии агента.md>)).
5. **Результат, а не активность:** мерить изменения (метрики, поведение), а не число артефактов, релизов и
   презентаций. Работа без изменения — «работа в стол».
   **Диаграмма накопленного потока (CFD)** — диагноз потока задач одной картинкой: по оси времени накоплено задач
   в каждом статусе. Расстояние между линиями «взято» и «сделано» — сколько в работе; наклон «сделано» — скорость;
   расстояние по горизонтали — время от взятия до результата; расходятся линии — берём больше, чем успеваем
   закрыть. Данные: у каждой задачи — дата каждой смены статуса. Без истории статусов диаграмму не построить:
   сначала завести историю, потом строить.
6. **Отстрел лишнего:** до работы — оценка денежного смысла юнит-экономикой. Большинство задач не стоит делать.
   **Эффект считают до старта, затраты — полные** (Гурбанов, конференция «Клиенты из нейросетей», 11.2026 —
   [выжимка](<_исходные-заметки/Конференция — клиенты из нейросетей (2026-11)/Выжимка — часть В (Спиридонов, Гурбанов).md>),
   тезисы Г-16, Г-17). Эффект — деньги или часы за год в строке юнит-экономики (навык `unit-economics`). Затраты —
   не только лицензия: люди на построение и проверку, время сотрудников на ввод данных и проверку результата,
   сбор и подготовка данных, лицензии и API, поддержка (смена API или модели, фаза 5 раздела 1). Ориентир спикера —
   **эффект не меньше 10× затрат на внедрение**. Это его мнение без источника, не норма канона: порог задаёт
   владелец решения, но эффект меньше затрат — отказ. Пример спикера: автоматизация юротдела из двух человек
   экономит 1 млн ₽ в год при 5 млн ₽ на построение — отказ.
7. **Одна связанная система — для агента, чат — для людей.** Данные, тикеты, переписки, звонки — в одном месте с
   версиями, без фильтрации (фильтр убирает слабые сигналы). Вместо встречи — вопрос агенту, который видит всё.
   Людям новых систем не добавлять: нужное приходит им в чат, где они уже живут (Доп9).
8. **Дайджест — первый ход внедрения** ([Доп9](<_Красинский — полный разбор (2026-07)/Доп9 — Дорожки между системами и дайджест как первый ход (стрим о внедрении агентов).md>)).
   Дайджест — одно сообщение с картинками и ссылками, прочитав которое человек понимает, что сделать, чтобы
   разблокировать себя или другого. Это самое дешёвое изменение: точка входа (чат) не меняется, а человек
   получает пользу сразу. Он же заменяет поток уведомлений и снимает микроменеджмент: к ежедневному дайджесту
   прогресса и инцидентов привыкают за недели.
   Порядок под роль: роль → что человек делает с утра и в каких системах ищет следующий шаг → два-три вопроса
   («что я блокирую», «кого разблокировать», «где деньги или риск сегодня») → источники на чтение → одно
   сообщение → в его чат. Сначала вручную несколько раз, потом по расписанию. Первая отправка коллеге — по «да»
   (п. 4); расписание без присмотра — через ворота раздела 1.
   Работает, если через две недели человек действует по дайджесту, не просит отключить и реже ходит в исходную
   систему. Не читают — менять вопросы, а не частоту.
9. **Чинить связи, а не переписывать системы** (Доп9). Потери возникают между системами, а не в них. Системы
   наследуют структуру управления (закон Конвея), поэтому новая своя система переносит старые разрывы и нанимает
   людей их закрывать. Перед «напишем свою CRM, кабинет, регистрацию» — карта: какой сценарий человека не
   выполняется, между какими системами разрыв, есть ли API. Особенно в проклятых местах: самописная CRM,
   регистрация и авторизация, биллинг, личные кабинеты, задачи и тикеты. Мера — в сколько систем человек ходит
   каждый день: после автоматизации число не должно расти.
10. **Человек наблюдает систему, задача кончается доставкой** (Доп9). Задача агенту, результат которой нужен
    людям, заканчивается доставкой: кому и куда. Человек не запускает агентов руками каждый день, а смотрит, где
    система тратит лишние усилия, и вносит точные изменения: навык, хук, связь. Главное в любом изменении —
    внедрение и активация людей, а не код.
11. **Что отдавать агенту и где это искать** (Гурбанов, конференция «Клиенты из нейросетей», 11.2026 — выжимка
    части В, тезисы Г-5, Г-14, Г-15). Агенту отдают **типовую работу по правилам**, даже сложную: сверку, разбор,
    сборку документа по шаблону, контроль по чек-листу. Пример — сверка оплат со счетами поставщиков на чтение
    находит двойные оплаты. **Решения с суждением** (рынок, люди, переговоры, вкус) остаются за человеком: агент
    готовит данные и варианты, решает человек. Начинают с частых процессов с малым числом шагов (раздел 6, п. 9).
    Кандидатов ищут **по следам работы, а не опросом**: на вопрос «чем вам поможет ИИ» люди называют мелочи. Следы —
    переписки, повторяющиеся пересылки одного файла, ручные перекладки между системами, тикеты, звонки. Следы
    содержат персональные данные: чтение переписок и звонков — только в рамках
    [Политики ПДн и доступа](<Политика — Персональные данные, секреты и доступ к внешним системам.md>), на чтение,
    наружу — агрегат. Сплошное чтение переписки сотрудников и запись экранов — только по решению владельца и юриста
    с уведомлением сотрудников.
