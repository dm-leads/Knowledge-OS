# Справочник — Выгода, налог, COGS, CJM операций

## Краткая суть

Модуль 8 вводит принцип «Выгода vs Налог»: все метрики юнит-экономики зависят от того, понял ли пользователь, что ему дают. Выгода — это факт, сценарий или чувственный опыт, налог — абстрактная оценка. Модуль 9 закрывает пробел в AMPPU: вводит COGS 1st sale — себестоимость первой сессии с клиентом, которую невозможно посчитать без CJM операционных процессов. Эти два модуля дополняют друг друга: без понимания выгоды не будет конверсии, без корректного COGS — не будет честной маржи. (источник → К8-tax txt сегм. ~59 200; К9-cogs файл участника лист «подвиг 2», B2)

## Выгода и налог

### Концепция

«Все наши юнит-экономические метрики зависят от того, понял человек выгоду или нет, а выгоду он понимает только если понял, что вы ему даёте.» (источник → К8-tax txt, сегм. ~59 200)

- 90% работы по изменению конверсии в первую покупку зависит от активации JTBD-сценария. (источник → К8-tax txt, сегм. ~58 900)
- Первый чек (ледневчек) и возвращение пользователя в продукт — оба зависят от активации сценария. (источник → К8-tax txt, сегм. ~59 000)
- Самый дешёвый способ повысить конверсию в первую сессию — попросить пользователя о действии: оставить номер телефона, оформить заявку, нажать на кнопку. (источник → К8-tax txt, сегм. ~58 800)

### Определения

| Понятие | Определение | Источник |
|---|---|---|
| **Выгода** | Факт, история, сценарий с чувственным опытом, конкретное число, социальное доказательство — то, что читатель может примерить на себя | К8-tax txt, сегм. ~84 000–87 000 |
| **Налог (текстовый)** | Оценочные суждения, абстракции, впаривание без опоры на факты; всё, что читатель не может проверить или пережить | К8-tax txt, сегм. ~86 000–87 000; pdf «оценочные суждения» |
| **Оценка (Ильяхов)** | Характеристика, описывающая субъективное ощущение автора; не доносит мысль и не создаёт доверие | К8-tax pdf «оценочные суждения», стр. 5 |

### Принцип Ильяхова: факты vs оценки

- «Оценка — это яд. Она не доносит нужные мысли и не создаёт доверие.» (источник → К8-tax pdf «оценочные суждения», стр. 2)
- «Самая прочная оценка — та, которую вы даёте сами на основании собственного опыта.» (источник → К8-tax pdf «оценочные суждения», стр. 3)
- «Без исследования и фактов любой текст — пустой трёп.» (источник → К8-tax pdf «оценочные суждения», стр. 8)
- Список сигналов-оценок (стоп-слов): авторитетный, актуальный, безупречный, качественный, уникальный, эффективный и 100+ аналогов. (источник → К8-tax pdf «оценочные суждения», стр. 13–14)

### Алгоритм анализа текста на выгоду / налог

1. Распечатать текст лендинга или скрипт продаж.
2. Выделить выгоды жёлтым маркером: факты, числа, конкретные сценарии.
3. Выделить налоги чёрным маркером: оценочные суждения, абстракции, впаривание.
4. Подсчитать соотношение. Если выгод менее 30% — текст неэффективен.
5. Метод «5 почему»: докрутить до «сердечка пользователя» — самой глубокой мотивации.
6. Если самостоятельно не получается — провести КСDI (кастомер-девелопмент-интервью). (источник → К8-tax txt, сегм. ~90 000–93 000; ~84 000–87 000)

### Примеры «Нет/Да»

| Налог (нет) | Выгода (да) |
|---|---|
| «Копи деньги быстро» | «Наши пользователи, вложившие 200 тысяч рублей в прошлом году, заработали в среднем 300 тысяч рублей» |
| «Суперквалифицированные инженеры» | «Восстанавливаем данные из взорвавшихся и простреленных телефонов» |
| «Успешный предприниматель» | «Основал Facebook, состояние $35,7 млрд» |
| «Дивиденды по акциям X%» | Добавить: для кого это выгодно, в каком сценарии, на какую сумму |

(источник → К8-tax txt, сегм. ~92 000–96 000; К8-tax pdf «оценочные суждения», стр. 9–10)

## Воронка продаж и AAB-тест

### Ключевые принципы

- С конца воронки оптимизировать выгоднее: в конце — «прямые деньги», там часто дыра 50%. (источник → К8-tax txt, сегм. ~71 500, ~73 000)
- Конверсию за неделю считать через ×7/31, а не делить на 4. (источник → К8-tax xlsx лист «Юнит-экономика Freedom24», строка B24; txt сегм. ~74 000)
- Для AAB-теста трафик делится на 3 группы: пользователей в неделю ÷ 3. (источник → К8-tax xlsx B25; txt сегм. ~74 500)

### Формулы воронки и AAB-теста

```
# Недельный трафик из месячного:
C_week = C_month × 7 / 31          — [xlsx Ведущий B23]
C_week = C_month × 7 / 30          — [xlsx исходный C39]

# Группа AAB-теста:
C_group = C_week / 3               — [xlsx исходный C45; xlsx Ведущий B29]

# Доверительный интервал конверсии (формула Вилсона, приближение):
DI = ±2 × √(p × (1 − p) / n)      — [xlsx исходный F34, F40, F45; xlsx Ведущий D24]

# Нижняя и верхняя граница:
min = p − DI                        — [xlsx Ведущий G24]
max = p + DI                        — [xlsx Ведущий H24]
```

(источник → К8-tax xlsx правки формулы F34, F40, F45; xlsx Ведущий D24, G24, H24)

Условие признания варианта B лучшим: его конверсия должна выйти за верхнюю границу доверительного интервала текущей конверсии. (источник → К8-tax txt, сегм. ~76 000)

| Метрика | Формула | Ячейка / источник |
|---|---|---|
| C1 (конверсия в покупателя) | `= Buyers / Users` | К8-tax xlsx D13; К9-cogs xlsx F13 |
| Доля не купивших | `= 1 − C1` | К8-tax xlsx D14 |

| Метрика | Формула | Ячейка / источник |

### Блок 3 — На 1-го привлечённого

| Метрика | Формула | Ячейка / источник |
|---|---|---|
| AMPU / LTV | `= AMPPU × C1` | К8-tax xlsx S13; К9-cogs xlsx U13 |
| CAC | `= Acq.Costs / Buyers` | К8-tax xlsx O13; К9-cogs xlsx Q13 |
| CPUser / CPLead | `= Acq.Costs / Users` | К8-tax xlsx R13; К9-cogs xlsx T13 |
| CPO / SPS | `= Acq.Costs / Payments` | К8-tax xlsx P3/O3 (определение) |

### Блок 4 — Финансовые метрики потока

| Метрика | Формула | Ячейка / источник |
|---|---|---|
| Gross Profit | `= AMPPU × Buyers` | К8-tax xlsx Y13; К9-cogs xlsx AA13 |

## COGS и CJM операционных процессов

### Концепция

COGS 1st sale и CJM взаимосвязаны: чтобы посчитать себестоимость первой сессии с клиентом, нужно сначала построить CJM операционных процессов, измерить touchtime по каждому шагу и распределить работу по ролям. (источник → К9-cogs файл ведущего, лист «Customer Journey Map и процесс»)

«Решаем проблему с конца: COGS продукта и CJM операционных продуктов.» (источник → К9-cogs файл участника лист «подвиг 2», B2)

Ключевые принципы:
- **leadtime vs touchtime:** реальное время этапа с ожиданием в ~10 раз длиннее фактического рабочего времени. (источник → К9-cogs файл участника, лист «подвиг 2», B7, B10)
- **Пропускная способность команды = узкому месту:** максимальное число параллельных проектов определяется самой загруженной ролью (MIN по всем ролям). (источник → К9-cogs файл участника H28; файл ведущего F22)
- После перехода на модель «команда заботы» Users и C1 перестают быть главными метриками — buyers ограничен пропускной способностью команды. (источник → К9-cogs файл участника лист «подвиг 2», B48)

### Структура CJM операционных процессов

**Строки** — шаги обслуживания клиента от «Есть продажа» до «Взять деньги за следующий месяц».

**Колонки метрик по шагу:**

| Колонка | Содержание |
|---|---|
| leadtime | Полное время шага с ожиданием (дни) |
| touchtime мин | Минимальное рабочее время (часы) |
| touchtime макс | Максимальное рабочее время (часы) |
| touchtime средний | (мин + макс) / 2 |
| число циклов | Сколько раз шаг повторяется в 1 проекте |

**Строки ролей:**

| Колонка | Содержание |
|---|---|
| число людей | Количество сотрудников в роли |
| зарплата | Зарплата в месяц |
| часы на 1 проект | SUM touchtime_средний × циклы по всем шагам |
| touchtime часов в месяц | Доступный фонд = 22 × 4 = 88 ч |
| пропускная способность | (число_людей × 88) / часы_на_проект |

(источник → К9-cogs файл участника, лист «подвиг 2»; файл ведущего, лист «Customer Journey Map и процесс»)

### Формулы COGS и CJM

```
# Touchtime средний по шагу:
touchtime_avg = (touchtime_min + touchtime_max) / 2
# Ячейка H13: =(H11+H12)/2
```
(источник → К9-cogs файл участника (PHs14), лист «подвиг 2», H13)

```
# Touchtime на шаг с учётом циклов:
touchtime_шаг = touchtime_avg × число_циклов
# Ячейка H24: =H13*H14
```
(источник → К9-cogs файл участника (PHs14), лист «подвиг 2», H24)

```
# Часы на 1 проект по роли:
hours_per_project_role = SUM(touchtime_шаг по всем шагам CJM)
# Ячейка E23: =SUM(H23:T23)
```
(источник → К9-cogs файл участника (PHs14), лист «подвиг 2», E23)

```
# Доступный фонд touchtime в месяц:
touchtime_fund = 22 рабочих дня × 4 часа = 88 часов
# Ячейка F23: =22*4
```
(источник → К9-cogs файл участника (PHs14), лист «подвиг 2», F23)

```
# Пропускная способность роли:
throughput_role = (число_людей × 88) / hours_per_project_role
# Ячейка G23: =IFERROR(C23*F23/E23)
# Файл ведущего F16: =IFERROR(B16*E16/D16)
```
(источник → К9-cogs файл ведущего, лист «Customer Journey Map», F16)

```
# Пропускная способность команды (узкое место):
throughput_team = MIN(throughput_role1, throughput_role2, ...)
# Ячейка G28: =MIN(G23:G27)
```
(источник → К9-cogs файл участника (PHs14), лист «подвиг 2», G28)

```
# Суммарный ФОТ команды:
ФОТ = SUM(зарплата_роли × число_людей_роли)
# Ячейка D27: =(D26*C26)+(D25*C25)+(D23*C23)+(C24*D24)
```
(источник → К9-cogs файл участника (PHs14), лист «подвиг 2», D27)

```
# COGS 1st sale:
COGS_1st_sale = ФОТ_команды / throughput_team
# Файл ведущего C22: =C20/F22
# Файл участника D28: =IFERROR(D27/G28)
```
(источник → К9-cogs файл ведущего, лист «Customer Journey Map», C22)

```
# AMPPU_new (после М9):
AMPPU_new = Av.Price × Margin × Av.Payment Count − COGS_1st_sale
# Файл ведущего I40: =J40*O40-N40
# где N40 = ссылка на COGS_1st_sale из листа CJM
```
(источник → К9-cogs файл ведущего, лист «Экономика», I40)

### Алгоритм расчёта COGS 1st sale через CJM

1. Составить список шагов операционного процесса (CJM) — от «Есть продажа, деньги получены» до «Взять деньги за следующий месяц».
2. Для каждого шага определить leadtime (общее время с ожиданием) и touchtime (мин и макс в часах).
3. Посчитать touchtime средний = (мин + макс) / 2.
4. Определить число циклов для каждого шага (сколько раз шаг повторяется в одном проекте).
5. Заполнить таблицу ролей: роль, число людей, зарплата в месяц.
6. Распределить touchtime по ролям (кто из сотрудников выполняет каждый шаг). Ячейки = touchtime_avg × число_циклов.
7. Рассчитать часы на 1 проект по каждой роли = SUM touchtime по всем шагам.
8. Рассчитать touchtime часов в месяц (доступный фонд) = 22 × 4 = 88 часов.
9. Рассчитать пропускную способность каждой роли = (число_людей × 88) / часы_на_проект.
10. Пропускная способность команды = MIN по всем ролям (узкое место).
11. Рассчитать суммарный ФОТ команды.
12. COGS 1st sale = суммарный ФОТ / пропускная способность команды.
13. Подставить COGS 1st sale в новую формулу AMPPU.
14. Переформулировать экономику — buyers ограничен пропускной способностью, а не трафиком. (источник → К9-cogs файл участника (PHs14), лист «подвиг 2», B4–B28)

### Потолок CAC через выгоду клиента

«Обычно за маркетинг бизнесы готовы платить CAC до 30% от Gross Profit. Это та цена, за которую ты можешь продавать свой продукт.» (источник → К9-cogs файл участника (PHs14), лист «подвиг 1», B25)

```
# Gross Profit клиента с одной сделки (которую помог совершить ваш продукт):
Gross Profit клиента = Users × C1_клиента × Av.Price_клиента × Margin_клиента

# Потолок CAC:
CAC_потолок = Gross Profit_клиента × 30%
# Файл ведущего P24: =Z24*30%
```

Алгоритм оценки выгоды клиента для ценообразования:
1. Взять параметры клиента: Users его сайта, C1 при использовании вашего продукта, Av.Price его сделки, Margin.
2. Посчитать Gross Profit клиента от одной продажи, которую помог совершить ваш продукт.
3. CAC потолок = Gross Profit клиента × 30%.
4. Ваш средний чек ≤ CAC потолка. (источник → К9-cogs файл ведущего, лист «Экономика», A23–P25)

Оптимизация через перераспределение ролей: перенос задач между членами команды может увеличить пропускную способность без найма новых людей. (источник → К9-cogs файл ведущего, лист «Customer Journey Map», C26)

## Диагностика воронки и антипаттерны

### Антипаттерны в юнит-экономике

| Антипаттерн | Почему неправильно | Источник |
|---|---|---|
| Чарнрейт как метрика конверсии | Устаревший метод; крайне чувствителен к притоку новых пользователей — при росте трафика растёт искусственно, даже при том же качестве удержания | К8-tax txt, сегм. ~22 000–30 000 |
| DAU/MAU как ретеншн | Та же шумность, что и чарнрейт; не отражает когортную динамику | К8-tax txt, сегм. ~26 000 |
| Формулы lifetime = 1/churn rate | Работает только для телеком с churn ~3%; в остальных случаях — «почти всегда вранье» | К8-tax txt, сегм. ~30 500 |
| Считать метрики суммарно | Маскирует реальные тренды; правильно — когорты с C2/C3/C4... | К8-tax txt, сегм. ~30 000 |
| Путать Install и User | AppsFlyer и Firebase дают разные цифры; конверсия из установки ≠ 100% | К8-tax txt, сегм. ~18 000–21 000 |
| Оптимизировать начало воронки, игнорируя конец | Сначала закрыть дыру в конце, потом работать с верхом | К8-tax txt, сегм. ~71 000–73 000 |
| Наращивать трафик без закрытия дыр в конце воронки | Потраченные бюджеты на рекламу при 50% потере на финале — деньги на ветер | К8-tax txt, сегм. ~73 000 |
| Игнорировать COGS 1st sale при расчёте AMPPU | После М9 формула меняется; без учёта COGS маржа завышена | К9-cogs файл участника лист «подвиг 2», B46 |
| Считать пропускную способность по «средней» роли | Правильно — по узкому месту (MIN); иначе план по buyers нереален | К9-cogs файл ведущего лист «Customer Journey Map», F22 |
| Не считать buyers lost | Потеря дохода, которую видно только как отдельный сегмент | К9-cogs файл участника лист «подвиг 1», B9, B15 |

### Антипаттерны в коммуникации (Ильяхов)

| Антипаттерн | Правило | Источник |
|---|---|---|
| Оценочные прилагательные вместо фактов («вкусный», «эффективный», «качественный») | Заменить или дополнить фактами; оценки не несут информации | К8-tax pdf «оценочные суждения», стр. 1–5 |
| Ложное ощущение проделанной работы | Автор написал оценку и считает, что раскрыл тему, хотя читатель ничего конкретного не понял | К8-tax pdf «оценочные суждения», стр. 7 |
| Креативные / рифмованные заголовки | Жертвовать понятностью ради красоты — ошибка; заголовок должен называть тему, а не интриговать | К8-tax pdf «Заголовки. Ильяхов», стр. 2–6 |
| «Волшебные формулы» заголовков | Работают только если статья реально полезна; сама по себе магия не работает | К8-tax pdf «Заголовки. Ильяхов», стр. 9 |

## Глоссарий

| Термин | Определение | Источник |
|---|---|---|
| **Выгода** | Факт, история, сценарий с чувственным опытом, число — то, что читатель может примерить на себя | К8-tax pdf Ильяхов |
| **Налог (текстовый)** | Оценочное суждение без фактической опоры | К8-tax pdf Ильяхов |
| **AMPPU / CLTV** | Маржа на 1 платящего = Av.Price × Margin × Av.Payment Count | К9-cogs xlsx J13 |
| **AMPPU_new** | Маржа на 1 платящего с учётом COGS 1st sale = AMPPU − COGS_1st_sale | К9-cogs xlsx Ведущий I40 |
| **AMPU / LTV** | Маржа на 1 привлечённого = AMPPU × C1 | К8-tax xlsx S13 |
| **CAC** | Стоимость привлечения платящего = Acq.Costs / Buyers | К8-tax xlsx O13 |
| **CPUser / CPLead** | Стоимость привлечения пользователя = Acq.Costs / Users | К8-tax xlsx R13 |
| **CPO / SPS** | Стоимость заказа = Acq.Costs / Payments | К8-tax xlsx P3 |
| **Gross Profit** | Валовая прибыль = AMPPU × Buyers | К8-tax xlsx Y13 |
| **Profit net** | Чистая прибыль = Revenue − Gross Profit (или GP − Acq.Costs) | К8-tax xlsx V; К9-cogs xlsx X13 |
| **C1** | Конверсия поток → покупатель = Buyers / Users | К8-tax xlsx D13 |
| **COGS 1st sale** | Себестоимость первой сессии/проекта с клиентом = ФОТ_команды / throughput_team | К9-cogs файл ведущего C22 |
| **touchtime** | Фактическое рабочее время на операцию без ожидания (в часах) | К9-cogs файл участника B6 |
| **leadtime** | Полное время прохождения операции с ожиданием и блокировками (~10× touchtime) | К9-cogs файл участника B7 |
| **пропускная способность** (throughput) | Максимальное число параллельных проектов команды; определяется узким местом (MIN по ролям) | К9-cogs файл участника H28 |
| **число циклов** | Количество повторений шага CJM в одном проекте | К9-cogs файл участника B14 |
| **CAC потолок** | 30% от Gross Profit клиента — максимум, который бизнес готов платить за привлечение | К9-cogs файл участника лист «подвиг 1», B25 |
| **AAB-тест** | Тест с тремя вариантами (A1, A2 — контрольные, B — экспериментальный) | К8-tax xlsx B44–B47 |
| **Доверительный интервал конверсии** | ±2√(p(1−p)/n) — минимальный прирост, чтобы быть статистически заметным | К8-tax xlsx F34 |
| **Чарнрейт** | Число пользователей, не перешедших в следующий период; устаревший показатель; не использовать | К8-tax txt, сегм. ~22 000 |
| **JTBD** | Job To Be Done — «работа», которую пользователь нанимает продукт выполнять; сценарий использования | К8-tax txt, сегм. ~57 000 |
| **North Star Metric** | Одна метрика-цель для фокусировки всей команды; само по себе не фреймворк юнит-экономики | К8-tax txt, сегм. ~16 500 |
| **buyers lost** | Клиенты, переставшие платить; «деньги, которые сервис теряет каждый месяц» | К9-cogs файл участника лист «подвиг 1», B9, B15 |
| **Project Success Manager** | Роль в команде заботы; отвечает за онбординг и внедрение продукта у клиента | К9-cogs файл ведущего лист «Customer Journey Map» |
| **фиче-кат** | Вырезание функций без сценарного анализа → риск поломки сценариев платящих пользователей | К8-tax txt, сегм. ~51 000 |
