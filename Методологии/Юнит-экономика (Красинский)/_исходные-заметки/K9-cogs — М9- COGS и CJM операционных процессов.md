## 1. Концепции и идеи

- **COGS и CJM — взаимосвязаны:** чтобы посчитать себестоимость одной сессии (проекта) с клиентом, нужно сначала построить CJM операционных процессов, измерить touchtime по каждому шагу, распределить работу по ролям — и только тогда считать COGS 1st sale. (источник → файл ведущего, лист «Customer Journey Map и процесс»)
- **«Решаем проблему с конца»:** подзаголовок 2-го подвига — COGS считается после понимания операционного процесса, не до. (источник → файл участника, лист «подвиг 2», строка B2)
- **leadtime vs touchtime:** реальное время прохождения этапа с ожиданием (leadtime) в ~10 раз длиннее, чем фактическое рабочее время (touchtime). (источник → файл участника, лист «подвиг 2», строка B7)
- **Пропускная способность команды = узкому месту:** максимальное число проектов в месяц ограничено самой загруженной ролью (MIN по всем ролям). (источник → файл участника и ведущего, строка B28 / H28)
- **Оптимизация через перераспределение ролей:** перенос задач между членами команды может увеличить пропускную способность без найма новых людей. (источник → файл ведущего, лист «Customer Journey Map», C26: «интересно как переносом задач между членами команды можно увеличить пропускную способность =)»)
- **CAC ≤ 30% от Gross Profit клиента:** стандартный потолок, который бизнес готов платить за маркетинг/привлечение. (источник → файл участника, лист «подвиг 1», строка B25)
- **Выгода клиента → основа ценообразования:** сколько клиент зарабатывает с помощью продукта — именно это определяет, сколько с него можно просить. (источник → файл ведущего, лист «Экономика», A23: «2. Сколько зарабатывает наш клиент с помощью нас»)
- **Ссылка на «Формулу системы»:** Красинский рекомендует статью Бюро Горбунова как методологический фундамент; конкретное содержание статьи в источнике не раскрыто. (источник → Формула системы.docx)

## 2. Точные определения

- **touchtime средний** — время (обычно в часах) на выполнение операции без простоя; например, время, чтобы написать сценарий для рассылки. Считается как среднее арифметическое минимального и максимального touchtime. (источник → файл участника, лист «подвиг 2», строки B6, B13)
- **leadtime** — общее время прохождения этапа с учётом простоя, ожидания, блокировок. Примерно в 10 раз длиннее touchtime. (источник → файл участника, лист «подвиг 2», строки B7, B10)
- **COGS 1st sale** — затраты на 1-ю сессию (проект) с клиентом; считается через сумму зарплат ролей, умноженных на часы работы на 1 проект. (источник → файл участника, лист «подвиг 2», строки B16, B28)
- **Пропускная способность** (throughput) — максимальное число проектов, которое команда может вести параллельно; определяется самой «узкой» ролью (MIN). (источник → файл ведущего, лист «Customer Journey Map», F22)
- **AMPPU** (Average Margin Per Paying User) = CLTV при нескольких платежах. Формула: AMPPU = Av. Price × Margin × Av. Payment Count. (источник → файл участника, лист «подвиг 1», J3 + формула J13)
- **CAC** (Customer Acquisition Costs) — стоимость платящего клиента = Acq. Costs / Buyers. (источник → файл участника, лист «подвиг 1», Q3, формула Q13)
- **CPUser / CPLead** — стоимость привлечения пользователя = Acq. Costs / Users. (источник → файл участника, лист «подвиг 1», T3, формула T13)
- **AMPU** (Average Margin Per User) = AMPPU × C1. (источник → файл участника, лист «подвиг 1», U3, формула U13)
- **число циклов** — сколько раз данный шаг CJM повторяется в одном проекте (некоторые шаги выполняются 2 и более раз). (источник → файл участника, лист «подвиг 2», строка B14)

```
(источник → файл участника (PHs14), лист «подвиг 1», J13)

```
Payments (H) = Buyers (G) × Av. Payment Count (P)
# Ячейка H13: =G13*P13
```
(источник → файл участника (PHs14), лист «подвиг 1», H13)

```
C1 (F) = Buyers (G) / Users (C)
# Ячейка F13: =G13/C13
```
(источник → файл участника (PHs14), лист «подвиг 1», F13)

```
Revenue (Z) = Av. Price (K) × Buyers (G)
# Ячейка Z13: =K13*G13
```
(источник → файл участника (PHs14), лист «подвиг 1», Z13)

```
Gross Profit (AA) = AMPPU (J) × Buyers (G)
# Ячейка AA13: =J13*G13
```
(источник → файл участника (PHs14), лист «подвиг 1», AA13)

```
CAC (Q) = Acq. Costs (AB) / Buyers (G)
# Ячейка Q13: =AB13/G13
```
(источник → файл участника (PHs14), лист «подвиг 1», Q13)

```
CPUser (T) = Acq. Costs (AB) / Users (C)
# Ячейка T13: =AB13/C13
```
(источник → файл участника (PHs14), лист «подвиг 1», T13)

AMPU (U) = AMPPU (J) × C1 (F)

```
(источник → файл участника (PHs14), лист «подвиг 1», U13)

Profit (Y) = Users (C) × (AMPU (U) − CPUser (T))

### Формулы CJM и COGS (лист «подвиг 2» / «Customer Journey Map»):

```
touchtime средний (H13) = (touchtime мин + touchtime макс) / 2
# Ячейка H13: =(H11+H12)/2
```
(источник → файл участника (PHs14), лист «подвиг 2», H13)

```
touchtime на шаг с учётом циклов (H24) = touchtime средний (H13) × число циклов (H14)
# Ячейка H24: =H13*H14
```
(источник → файл участника (PHs14), лист «подвиг 2», H24)

```
Часы на 1 проект по роли (E) = SUM по всем шагам CJM
# Ячейка E23: =SUM(H23:T23)
```
(источник → файл участника (PHs14), лист «подвиг 2», E23)

```
Touchtime часов в месяц (F) = 22 рабочих дня × 4 часа = 88 часов
# Ячейка F23: =22*4
```
(источник → файл участника (PHs14), лист «подвиг 2», F23)

```
Пропускная способность роли (G) = (число людей × touchtime часов в месяц) / часы на 1 проект
# Ячейка G23: =IFERROR(C23*F23/E23)
```
(источник → файл ведущего, лист «Customer Journey Map», F16: =IFERROR(B16*E16/D16))

```
Пропускная способность команды (G28) = MIN по всем ролям
# Ячейка G28: =MIN(G23:G27)
```
(источник → файл участника (PHs14), лист «подвиг 2», G28)

```
Суммарные затраты на зарплаты (D27) = сумма (зарплата × число людей) по всем ролям
# Ячейка D27: =(D26*C26)+(D25*C25)+(D23*C23)+(C24*D24)
```
(источник → файл участника (PHs14), лист «подвиг 2», D27)

```
COGS 1st sale (D28) = суммарные затраты (D27) / пропускная способность (G28)
# Ячейка D28: =IFERROR(D27/G28)
```
(источник → файл ведущего, лист «Customer Journey Map», C22: =C20/F22)

## 4. Пошаговые процедуры / алгоритмы

### Алгоритм расчёта COGS 1st sale через CJM:
(источник → файл участника (PHs14), лист «подвиг 2», B4–B28)

1. Составить список шагов операционного процесса (CJM) от «Есть продажа, деньги получены» до «Взять деньги за следующий месяц».
2. Для каждого шага определить **leadtime** (общее время с ожиданием) и **touchtime** (мин и макс в часах).
3. Посчитать **touchtime средний** = (мин + макс) / 2.
4. Определить **число циклов** для каждого шага (сколько раз шаг повторяется в одном проекте).
5. Заполнить таблицу ролей: список сотрудников, число людей, зарплата в месяц.
6. Распределить touchtime по ролям (кто из сотрудников выполняет каждый шаг). Ячейки = touchtime_среднего × число_циклов.
7. Рассчитать **часы на 1 проект** по каждой роли = SUM touchtime по всем шагам.
8. Рассчитать **touchtime часов в месяц** (доступный фонд) = 22 × 4 = 88 часов.
9. Рассчитать **пропускную способность** каждой роли = (число_людей × 88) / часы_на_проект.
10. Пропускная способность **команды** = MIN по всем ролям (узкое место).
11. Рассчитать суммарный фонд оплаты труда команды.
12. COGS 1st sale = суммарный ФОТ / пропускная способность команды.
13. Подставить COGS 1st sale в формулу AMPPU: AMPPU_new = Av.Price × Margin × Av.Payment.Count − COGS_1st_sale.
14. Переформулировать экономику — теперь Users и C1 менее важны; buyers определяются пропускной способностью.

### Алгоритм выхода на Gross Profit 1 млн р.:
(источник → файл участника, лист «подвиг 1», B42–B45; лист «подвиг 2», B49)

1. Зафиксировать исходную экономику (buyers new, AMPPU, Fix Costs).
2. Скопировать строку и изменить одну ключевую метрику (Users, C1, Av.Price, Margin, Av.Payment.Count, COGS, Fix Costs).
3. Проверить Gross Profit — подобрать значение метрики до достижения 1 млн р.
4. Либо повысить пропускную способность команды (нанять/перераспределить роли), либо сократить COGS 1st sale.

### Алгоритм оценки выгоды клиента (для ценообразования):
(источник → файл ведущего, лист «Экономика», A23–P25)

1. Взять параметры клиента: Users сайта, C1 (конверсия при использовании продукта), Av.Price сделки, Margin клиента.
2. Посчитать Gross Profit клиента от 1 продажи, которую помог совершить наш продукт.
3. CAC потолок = Gross Profit клиента × 30% (то есть сколько клиент готов платить за привлечение 1 покупателя).
4. Наш средний чек ≤ CAC потолка.

## 5. Фреймворки / модели

### CJM операционных процессов (Customer Journey Map сервиса)
(источник → файл ведущего, лист «Customer Journey Map и процесс»; файл участника, лист «подвиг 2»)

Структура таблицы:
- **Строки:** шаги процесса обслуживания клиента (горизонтально)
- **Колонки метрик:** leadtime, touchtime мин / макс / средний, число циклов
- **Строки ролей:** продажник, Project Success Manager, маркетолог, разработчик (+ менеджер клиента, руководитель в расширенной версии)
- **Колонки ролей:** число людей, зарплата, часы на 1 проект, touchtime часов в месяц, пропускная способность
- **Итог:** COGS проекта, пропускная способность команды (MIN)

Пример шагов CJM (кейс CarrotQuest):
1. Начало: Есть продажа, деньги получены
2. Определить цели и бизнес-процессы клиента (leadtime 1–3 дня; touchtime 0.5–3 ч)
3. Разместить скрипт на сайте клиента (1 день; 0.2–3 ч)
4. Спроектировать сценарии триггерных рассылок (1–2 дня; 2–8 ч)
5. Согласовать сценарии с клиентом (2–7 дней; 0.5–2 ч)
6. Настроить сбор данных о пользователях (3 дня; 0.1–1 ч)
7. Настроить триггеры (2–3 дня; 0.1–0.5 ч)
8. Написать контент для сценариев (2–3 дня; 2–4 ч; 2 цикла)
9. Согласование контента (2 дня; 0.5–1 ч; 2 цикла)
10. Обучение клиента (1 день; 1–2 ч)
11. Запуск рассылок (1 день; 0.2–0.5 ч)
12. Ожидание аналитики (14 дней; —)
13. Подготовка отчёта с выгодой клиента (2 дня; 0.1–0.2 ч; 2 цикла)
14. Клиент ознакомился с выводами и получил выгоду (1–7 дней; 0.2–0.5 ч; 2 цикла)
15. Конец: Взять деньги за следующий месяц (цель: С2 > 50%)

## 10. Термины в глоссарий

- **touchtime** — фактическое рабочее время на операцию без ожидания (в часах)
- **leadtime** — полное время прохождения операции с ожиданием и блокировками (~10× touchtime)
- **COGS 1st sale** — себестоимость первой сессии/проекта с клиентом (зарплаты ÷ пропускная способность)
- **пропускная способность** (throughput) — максимальное число параллельных проектов команды; определяется узким местом (MIN по ролям)
- **число циклов** — количество повторений шага CJM в одном проекте
- **CAC потолок** — 30% от Gross Profit клиента; максимум, который бизнес готов платить за привлечение
- **AMPU** (Average Margin Per User) = AMPPU × C1
- **AMPPU** (Average Margin Per Paying User) = Av.Price × Margin × Av.Payment.Count
- **CPUser / CPLead** — стоимость привлечения одного пользователя
- **Gross Profit** — валовая прибыль = AMPPU × Buyers
- **Project Success Manager** — роль в команде заботы; отвечает за онбординг и внедрение продукта у клиента
- **buyers lost** — клиенты, переставшие платить; «деньги, которые сервис теряет и недозарабатывает каждый месяц»

## 11. Типичные ошибки / антипаттерны

- **Игнорировать COGS 1st sale при расчёте AMPPU:** классическая ошибка на ранних модулях. После M9 формула меняется: AMPPU_new = Av.Price × Margin × LifeTime − COGS_1st_sale. (источник → файл участника (PHs14), лист «подвиг 2», B46: «Теперь у тебя добавились COGS 1st sale — значит старая формула AMPPU должна измениться»)
- **Считать пропускную способность по «средней» роли:** правильно — по узкому месту (MIN). Иначе план по buyers окажется нереальным. (источник → файл ведущего, лист «Customer Journey Map», F22 + H28)
- **Не считать buyers lost:** потеря платящих клиентов — это потеря дохода, которую видно только если считать отдельно сегмент buyers lost. (источник → файл участника (PHs14), лист «подвиг 1», B9, B15)
- **Верить, что C1 и Users — главные метрики после перехода на модель «команда заботы»:** в этой модели buyers определяются пропускной способностью команды, а не трафиком. (источник → файл участника (PHs14), лист «подвиг 2», B48)
- **Добавлять фичи без приоритизации гипотез:** правильный порядок — выписать все идеи в мозговой штурм, оценить метрику влияния, сложность (1–5), веру в успех (%), приоритет. (источник → файл участника (PHs14), лист «подвиг 2», B30–B37)
