# Гайд — Применение юнит-экономики в Директе (viklimat)

## Краткая суть

Юнит-экономика описывает, как деньги приходят от пользователей: «вход — поток пользователей, выход — поток денег» (М0 → транскрипт, ~65 000 симв.). Весь процесс покрывается 4–5 метриками. Этот гайд объясняет, как «приземлить» эти метрики на Директ viklimat.ru: какое событие Метрики ставить как цель оптимизации, как правильно считать CPL→CAC, где реально находится узкое место воронки и в каком порядке работать с точками роста.

> [гипотеза] Применимость метода к конкретным цифрам viklimat подтвердится только после сбора когортных данных из amoCRM.

---

## Для кого и что узнаешь

Документ для Дмитрия (маркетолог viklimat.ru). После прочтения:
- понятно, чем CPL отличается от CAC и как один перевести в другой;
- понятно, почему текущий target CPL 500–700 ₽ — промежуточный, а не конечный ориентир;
- есть алгоритм выбора целевого события в Метрике для оптимизации кампаний;
- есть последовательность диагностики узких мест воронки (не «где светло», а системно).

## 1. Базовые метрики и формулы (словарь)

Все определения — по курсу Красинского; обозначения сохранены дословно.

**Юнит** — то, что масштабируется. Для viklimat.ru юнит — **платящий клиент** (физлицо или организация, оплатившая заказ). (М0 → транскрипт, ~50 000 симв.)

**AMPPU (Average Margin Per Paying User)** — средняя маржа с платящего клиента за lifetime:
```
AMPPU = Средний чек × Маржинальность(%) × Среднее число повторных покупок (APC)
```
(М0 → транскрипт, ~64 000 симв.; М1 → транскрипт, устный вывод)

**AMPU (Average Margin Per User)** — средняя маржа с привлечённого пользователя (включая неконвертировавших):
```
AMPU = Конверсия × AMPPU
```
(М0 → транскрипт, ~66 000 симв.; М2 → txt, кейс FlowWow)

**Gross Profit** — два эквивалентных способа расчёта:
```
Gross Profit = Buyers × AMPPU
Gross Profit = Users × AMPU
```
(М0 → транскрипт, ~67 000 симв.)

**Cost per User (CPU)** — стоимость привлечения одного пользователя:
```
CPU = Расходы на привлечение / Число пользователей
```
CPU определяется конкуренцией в канале и компетенцией команды; **не зависит от продукта** — пользователь видит рекламу до того, как увидел продукт. (М2 → txt, раздел про CPU)

> [важно] CPU ≠ CAC. CAC — производная метрика, зависящая от CPU и конверсии: `CAC = CPU / Конверсия`. В публичных материалах часто путают — это выгодно для инвесторов, но неверно для управления продуктом. (М2 → txt, антипаттерн №3)

**Profit per User** — сходимость юнит-экономики на одном пользователе:
```
Profit per User = AMPU − CPU
               = Конверсия × AMPPU − CPU
```
(М0 → транскрипт, ~90 000 симв.)

**Полная прибыль**:
```
Profit = Поток пользователей × (AMPU − CPU) − Fixed Costs
```
(М2 → txt, кейс FlowWow)

## 2. Три уровня сходимости — диагностический чеклист

Перед работой с Директом проверить все три уровня последовательно. Не переходить к следующему, пока предыдущий не сходится. (М0 → транскрипт, ~91 000 симв.; М2 → txt, раздел три критерия)

| Уровень | Условие | Что это значит для viklimat |
|---|---|---|
| 1. На платящем клиенте | AMPPU > 0 (маржа > COGS) | Каждая продажа прибыльна; не продаём в убыток |
| 2. На привлечённом пользователе | AMPU > CPU | Директ окупается на горизонте lifetime клиента |
| 3. На финансах | Profit > 0 (с учётом Fixed Costs) | Бизнес прибылен с учётом всех постоянных расходов |

> [вывод] Target CPL 500–700 ₽ — ориентир уровня 2, но только при известных AMPPU и Конверсии. Без этих данных CPL — слепая цель.

## 3. CPL → CAC: перевод для viklimat

**CPL (Cost per Lead)** в Метрике — стоимость целевого события (лид, заявка, звонок). Это **не CAC**.

Связь через формулу:
```
CAC = CPL / Конверсия_лид_в_оплату
```
где `Конверсия_лид_в_оплату` = доля лидов из Директа, дошедших до статуса «Оплачен» в amoCRM.

Пример логики (цифры — [гипотеза], нужны реальные данные из CRM):
- CPL = 600 ₽ (в рамках target)
- Конверсия лид → оплата = 20%
- CAC = 600 / 0,20 = **3 000 ₽**
- Если AMPPU = 8 000 ₽, то Profit per Paying User = 8 000 − 3 000 = **+5 000 ₽** → экономика сходится

> [факт] Большинство бизнесов разоряются не потому, что не смогли сделать продукт, а потому что не смогли привлечь достаточно платящих пользователей. (М1 → транскрипт, раздел «Почему разоряются бизнесы»)

**Воронка amoCRM для конверсии:**
Лид в работе → КП → Заказ создан → Оплачен.
`Конверсия_лид_в_оплату` = Оплаченные / Лиды за тот же когортный период.

> [важно] Часть конверсий идёт через звонок/почту/мессенджер, не через форму на сайте. Счётчик Метрики `105977811` фиксирует только онлайн-касания. Коллтрекинг отключён намеренно (~26.05.2026). Это означает, что реальная конверсия лид→оплата выше, чем показывает Метрика по онлайн-целям — [гипотеза] занижение может быть существенным для дорогой климатической техники.

## 4. Выбор целевого события Метрики для оптимизации Директа

### Принцип

«Вы всегда получаете то, что измеряете. Какую цель поставили — то и увидите в отчётах.» (М0 → транскрипт, ~46 000 симв.)

Алгоритм выбора — от нижней воронки к верхней, останавливаясь на первом событии с достаточной статистикой:

```
1. Оплата (идеал) — если ≥ 10–20 конверсий/нед. из Директа
2. Заказ создан — если оплат мало, но создание заказа коррелирует с оплатой
3. Отправка заявки / форма — если заказов недостаточно
4. Микроконверсия (звонок при включённом коллтрекинге, корзина, карточка товара)
   — только как вспомогательная цель, не основная для оптимизации ставок
```

> [факт] Слабая активация в первой сессии характерна для дорогой техники: пользователь приходит, изучает, уходит и возвращается позже. Это снижает конверсию первого касания. Оптимизировать по событиям нижней воронки предпочтительнее, но требует накопления статистики. (М1 → транскрипт, раздел «Три исключения» — обратный пример: заказ такси/еды конвертируется высоко, потому что решение принято до открытия сайта; для климатической техники ситуация обратная)

### Применение к текущим кампаниям viklimat

Активные кампании: `707520747`, `707721234`. Кабинет `porg-o7qk2wim`.

- Кампания `707520747` настроена на оплату за несколько целей с каскадом и рекомендованными ценами 100/300/700 ₽. [факт из памяти проекта]
- [вывод] Каскадная оплата корректна методологически: нижняя воронка (оплата, 700 ₽) задаёт главный сигнал, верхние события (100/300 ₽) дают статистику для обучения.
- [гипотеза] Если кампании недобирают конверсий нижней воронки для обучения — приоритет временно смещается на «Заказ создан» как основное целевое событие.

### Узкое место «категория → карточка»

Воронка (кейс по аналогии с интернет-магазином из М2):
```
Пользователи категории (100%)
    ↓ [? %]
Карточка товара
    ↓ [? %]
Корзина / заявка
    ↓ [? %]
Оплата
```
(по аналогии с М2 → txt, пример воронки интернет-магазина: 5,4% → 1,8% → 0,55%)

> [факт] «По статистике автора, примерно 70% русскоязычных компаний имеют проблемы в конверсии.» И: «Конверсия — самая недооцениваемая и невезучая метрика.» (М2 → txt)

> [вывод] Узкое место категория→карточка — типичная точка роста. Однако прежде чем вкладываться в её улучшение, нужно проверить: не является ли маржинальность или средний чек более «плечистой» метрикой (см. раздел 5).

## 5. Диагностика узких мест: алгоритм

Реконструирован из М2 (txt, раздел алгоритм диагностики) с адаптацией к viklimat.

### Шаг 1. Считать юнит-экономику полностью

Слева-направо: Users → CPU → Conversion → Buyers → AMPPU → AMPU → Gross Profit → Profit.
Затем — кросс-проверка справа-налево. Если не сходится — найти ошибку в данных, не двигаться дальше. (М2 → txt)

Источники данных для viklimat:
- Users, расходы — Директ (кабинет `porg-o7qk2wim`)
- Конверсия лид→оплата — amoCRM (воронка по когортам)
- Средний чек, маржа — данные заказчика
- Повторные покупки — amoCRM, когортный анализ

### Шаг 2. Проверить кросс-чеки

```
Gross Profit = Buyers × AMPPU   ←→   Gross Profit = Users × AMPU
```
Расхождение = 0. Если не 0 — ошибка в данных или формулах. (М0 → транскрипт, ~97 000 симв.; М2 → txt)

> [антипаттерн] Брать конверсию из Метрики как единственный источник истины. Погрешность аналитических систем — до 30–40%. Надёжнее биллинг / amoCRM. (М2 → txt, антипаттерн №4)

### Шаг 3. Проверить три уровня сходимости (см. раздел 2)

### Шаг 4. Разбить по сегментам, не работать со средним

«Среднее лжёт. Усреднение скрывает точки роста и создаёт ложные выводы.» (М2 → txt)

Для Директа viklimat сегменты:
- По кампании: `707520747` vs `707721234`
- По устройству: десктоп vs мобайл
- По типу трафика: поиск vs РСЯ
- По продуктовой категории: мульти-сплит vs сплит-системы vs тепловые насосы

### Шаг 5. Найти «плечи метрик»

Поварьировать значения метрик в модели: изменение какой метрики на 10% даёт наибольший прирост прибыли? (М2 → txt, кейс FlowWow — вариирование комиссии/конверсии/среднего чека)

> [факт] «Там, где близки две цифры, которые вычитаются, — там спрятан кратный рост.» Если AMPU ≈ CPU — здесь работать в первую очередь. (М2 → txt)

### Шаг 6. Правильный порядок работы с метриками

«Правильная последовательность: сначала — маржинальность и средний чек, потом — конверсия, потом — поток пользователей.» (М1 → транскрипт, раздел «Кейс HotWiFi»)

Применительно к Директу viklimat:
1. Убедиться, что маржа на единицу продажи положительна и достаточна (AMPPU > 0 с запасом)
2. Убедиться, что конверсия лид→оплата измерена корректно (не из Метрики, а из CRM)
3. Только затем — масштабировать трафик через Директ

> [антипаттерн] «Сначала лить трафик, потом оптимизировать метрики: при плохой марже рост CPU вместе с ростом трафика немедленно даёт убыток.» (М1 → транскрипт)

### Шаг 7. Сформулировать гипотезы и приоритизировать по ROI

Формат гипотезы: «Если мы сделаем X, то ожидаем Y». Оценить трудозатраты в часах. Выбрать с наибольшим ROI по времени. (М2 → txt, раздел воршоп)

## 6. Нелинейные эффекты: что важно для масштабирования

### Эффект операции вычитания (неустойчивость модели)

«Модель юнит-экономики нелинейна из-за операции вычитания: малейшие колебания ключевой метрики приводят к кратному росту прибыли.» (М1 → транскрипт)

Пример (из М1, кейс HotWiFi): после роста среднего чека ×2 и комиссии ×3 прибыль выросла в 12+ раз — нелинейный эффект операции вычитания.

Для Директа: если AMPU и CPU близки — даже снижение CPU на 15% или рост конверсии на 2 п.п. могут дать не 15–20% прироста прибыли, а кратный.

### Нелинейность Acquisition Costs

«Первая позиция в аукционе Яндекса может давать в 5–7 раз больше пользователей, чем вторая.» (М2 → txt) Это означает, что ставки нелинейны: не стоит стремиться к первой позиции ради охвата, если AMPU не покрывает возросший CPU.

### Скидки уничтожают маржу нелинейно

```
Прибыль со скидкой = (Средний чек × (1 − Скидка%)) − Себестоимость
```
(М1 → транскрипт, раздел «Нелинейность скидок»)

Скидка 30% при узкой марже → прибыль в убыток. «Скидок не существует — есть сегментация по цене.» (М1 → транскрипт)

## 7. Типичные антипаттерны для Директа (применимые к viklimat)

Отобраны из М0, М1, М2 — только те, что прямо актуальны для контекстной рекламы интернет-магазина:

1. **Считать среднее CPL по всем кампаниям/сегментам** — маскирует убыточные сегменты. Разбивать по кампаниям, типу трафика, категории. (М0 → транскрипт, ~91 000 симв.; М2 → txt)

2. **Оптимизировать только конверсию, игнорируя маржу** — «Команда FlowWow год работала с конверсией, тогда как поднятие комиссии на 10 п.п. решило бы проблему быстрее.» (М2 → txt)

3. **Брать конверсию из Метрики, не из CRM/биллинга** — погрешность до 30–40%; данные amoCRM надёжнее. (М2 → txt, антипаттерн №4)

4. **Путать CPL и CAC** — CPL — стоимость лида, CAC — стоимость оплатившего клиента. Разница — в конверсии лид→оплата. Управлять нужно обоими. (М2 → txt, антипаттерн №3)

5. **Ставить одну метрику как цель без контроля смежных** — кейс авиакомпании: оптимизировали конверсию в целом, пропустили обвал у новых пользователей на Android. Следить за сегментами. (М0 → транскрипт, ~44 000 симв.)

6. **Масштабировать трафик до достижения положительной экономики** — при AMPU < CPU рост бюджета умножает убыток. (М1 → транскрипт)

7. **Запоминать пиковые CPL/конверсии как норму** — «Основатель запоминает конверсию 3% (достигнутую в праздник) и называет её нормой, хотя норма — 1,7%.» (М2 → txt)

8. **Не учитывать конверсии через звонок/мессенджер** — занижает реальный AMPU и искусственно ухудшает CPL. (контекст проекта + принцип из М0/М2)

## 8. Что не покрыто входными материалами

- Точные нормативы маржинальности и APC для климатической техники — **не покрыто во входных материалах**; нужны данные заказчика и amoCRM.
- Когортный анализ повторных покупок для viklimat — инструментарий описан в М1, но реальные данные не извлекались.
- Методика расчёта когортного AMPPU из amoCRM — описана концептуально в М1 (раздел «Когорты»), конкретный алгоритм для CRM — **не покрыто во входных материалах**.
- Детальная механика настройки целей в Метрике `105977811` — за пределами методологии Красинского; см. документацию Яндекса.

## Что дальше

1. **Получить из amoCRM:** конверсию лид→оплата, средний чек, долю повторных заказов — для расчёта реального AMPPU и AMPU.
2. **Посчитать юнит-экономику полностью** по формулам раздела 1; пройти кросс-чек.
3. **Определить уровень сходимости** (раздел 2) — на каком уровне сейчас находимся.
4. **Выполнить диагностику плеч метрик** (раздел 5, шаг 5) — что даёт наибольший прирост прибыли.
5. **Скорректировать целевые события Директа** (раздел 4) на основе реальной статистики конверсий.
6. **Зафиксировать решения** в ADR-log проекта (если меняем структуру целей или пересматриваем target CPL).
