# Гайд — Применение юнит-экономики в маркетинге

## Краткая суть

Юнит-экономика управляет финансами, а не наоборот: «Финансы предсказываются юнит-экономикой» (М1 → транскрипт, раздел «Связь финансов и юнит-экономики»). Маркетинг — это машина привлечения юнитов (платящих пользователей); его задача не «лить трафик», а удерживать связь `AMPPU − CPU > 0` и не масштабировать убыток.

Главная ловушка: большинство маркетинговых команд идут туда, «где светло» — в конверсию — потому что воронка видна сразу. В реальности около 70% русскоязычных компаний имеют проблему в конверсии, но корневые причины — в маржинальности, среднем чеке или экономике внимания (М2 → транскрипт, раздел «Конверсия»; K-dop → bWGCFiqdQ7k).

---

## Для кого и что узнаешь

Гайд предназначен для маркетолога, продакт-менеджера или основателя, который:
- хочет понять, какую метрику двигать первой, чтобы получить кратный рост;
- путается, почему рост трафика не даёт роста прибыли;
- не понимает, как связаны CAC, конверсия, средний чек и LTV на практике.

После прочтения ты сможешь: посчитать юнит-экономику слева-направо, найти «плечо метрик», расставить приоритеты работ и не спутать симптом с корневой причиной.

## 1. Базовая модель: CAC, LTV и связь с маркетингом

### 1.1 Ключевые метрики и формулы

**Юнит** — «то, что мы масштабируем»; в 99% бизнесов это платящий пользователь или клиент (М1 → транскрипт, раздел «Определение юнита»).

**AMPPU (Average Margin Per Paying User)** — «в АМПУ собраны все-все-все метрики, которые описывают некоторую ценность продукта на рынке» (М1 → транскрипт).

Базовая формула:
```
AMPPU = Средний чек × Маржинальность(%) × Среднее число повторных покупок
```
(М1 → транскрипт, устный вывод на примере Яндекс.Такси)

Расширенный вариант (из дополнительных вебинаров):
```
АМПУ = Средний_чек × (1 − Налог%) × Кол_во_месяцев − Издержки_на_подключение
```
Где издержки на подключение = разовые косты команды продаж/онбординга на первый месяц жизни клиента (K-dop → A3vXNpW9r2Y).

**AMPU (Average Margin Per User)** — средняя маржа на всех привлечённых пользователей (включая неплатящих):
```
AMPU = Конверсия × MPPU
```
(М2 → транскрипт, раздел разбора кейса FlowWow)

**CPU (Cost Per User)** — стоимость привлечения одного пользователя из канала. Критически важно: CPU не зависит от продукта — он определяется конкуренцией в канале, ёмкостью канала и компетенцией команды в нём. Пользователь видит рекламу до того, как увидел продукт (М2 → транскрипт).

```
CPU = Расходы на привлечение / Число пользователей
```

**CAC (Customer Acquisition Cost)** — производная метрика, зависящая от CPU и конверсии:
```
CAC = CPU / Конверсия
```
(K-dop → bWGCFiqdQ7k; M2 → транскрипт)

Важно: CAC ≠ CPU. Почти все публичные материалы по юнит-экономике считают через CAC — это выгодно для инвесторов, но неверно для операционного управления маркетингом (М2 → транскрипт).

**Формула прибыли:**
```
Прибыль = Поток пользователей × (AMPU − CPU)
```
(М1 → транскрипт, раздел «Расчёт прибыли»; М2 → транскрипт)

### 1.2 Нелинейность («неустойчивость модели»)

Модель юнит-экономики нелинейна из-за операции вычитания: малейшие колебания ключевой метрики дают кратный рост прибыли (М1 → транскрипт, раздел «Кратный рост»).

Пример — кейс HotWiFi/Архангельск (доставка еды):
- До: 50 000 пользователей × конверсия 10%, средний чек 600 руб., комиссия 5% → AMPPU ≈ 36 руб., CPU = 2 руб. → прибыль ~80 000 руб./мес.
- После: средний чек ×2 (другие рестораны), комиссия ×3 (перепереговорили) → AMPPU вырос в 6 раз → прибыль выросла в 12+ раз (нелинейный эффект).
- Плюс рост конверсии на 10 п.п. → ещё ~+1 млн руб. Плюс платный трафик → ещё +1,3–1,6 млн руб.
(М1 → транскрипт, раздел «Магия кратного роста»)

Эффект операционного рычага при росте среднего чека:
```
Если Выручка растёт, а Фикс_костры_подключения остаются прежними
→ Маржа растёт непропорционально быстрее Выручки
```
Пример: чек 30 тыс. → АМПУ 18 тыс.; чек 65 тыс. → АМПУ 51 тыс. (рост чека ×2,2 → рост АМПУ ×2,8) (K-dop → A3vXNpW9r2Y).

### 1.3 Типичная ошибка расчёта LTV

Формула «LTV = 1 / churn_rate» — ошибка; даёт завышение в 2–3 раза по сравнению с реальностью. Пример: по неправильной формуле LTV = $289; реальный = $112. Следствие: маркетинг тратит $300 на привлечение и думает, что окупается (K-dop → A3vXNpW9r2Y). Правильный расчёт — через когортный Average Payment Count.

```
APC = Суммарное число платежей когорты / Размер когорты
```
(М1 → транскрипт, раздел «Когорта 6000»)

## 2. Диагностика маркетинга через юнит-экономику

### 2.1 Три критерия сходимости

Юнит-экономика — замкнутая система. Метрики, посчитанные слева-направо, должны сходиться с посчитанными справа-налево (кросс-чеки). Три уровня проверки (М2 → транскрипт, раздел кейс FlowWow):

1. **Сходится на платящем клиенте:** MPPU > 0 (есть положительная маржа с продажи).
2. **Сходится на привлечённом пользователе:** AMPU > CPU (привлечение окупается).
3. **Сходится на финансах:** Profit > 0 с учётом Fixed Costs.

Если не проходите уровень 1 — маркетинг не поможет. Если не проходите уровень 2 — проблема в CAC или конверсии, не в продукте.

### 2.2 Алгоритм диагностики: от юнит-экономики к точке роста

1. Посчитать юнит-экономику полностью: слева-направо (от пользователей к деньгам) (М2 → транскрипт).
2. Проверить кросс-чеками. Если не сходятся — найти ошибку в данных, не двигаться дальше (М2 → транскрипт).
3. Разбить метрики по сегментам (каналы, устройства, регион, новые/старые клиенты). Не работать со средним: «нельзя усреднять; считаем в среднем только чтобы потом разбить на сегменты, когорты и JTBD-сценарии» (K-dop → bWGCFiqdQ7k).
4. Найти «плечи метрик» — поварьировать значения, найти, изменение какой метрики даёт наибольший прирост прибыли (М2 → транскрипт, кейс FlowWow).
5. Там, где AMPU и CPU близки по значению — здесь спрятан кратный рост (М2 → транскрипт): «нам очень везёт. Там, где близки две цифры, которые вычитаются, — там спрятан кратный рост».
6. Сформулировать гипотезы в формате «Если X, то Y» и оценить трудозатраты в часах (М2 → транскрипт, раздел воршоп).
7. Выбрать гипотезы с наибольшим ROI по времени.

### 2.3 Правильная последовательность работы с метриками

«Правильная последовательность: сначала — маржинальность и средний чек, потом — конверсия, потом — поток пользователей» (М1 → транскрипт, раздел «Кейс HotWiFi»).

Команды идут в обратную сторону, потому что воронка видна сразу. Но: «куда обычно идут команды? Туда, где проще, понятнее, где зона комфорта. Но скорее всего, там кратного роста нет» (М1 → транскрипт).

Кейс FlowWow: более года работали с конверсией, не дали результата выше ~3%. Что надо было делать:
1. Сначала поднять маржинальность (договориться с партнёрами о более высокой комиссии: >30% магазинов не ушли, ~30% комиссия приемлема).
2. Затем средний чек / конверсия.
3. Только потом — мобильное приложение (команда потратила год на разработку + год на acquisition, в итоге нуль пользователей).
(М2 → транскрипт)

### 2.4 Среднее лжёт: сегментируй каналы

Пример «средний по каналам»: 3 канала с конверсиями 60% / 7% / 45% и маржинальностью 30% / 34% / 24%. Среднее — 60% конверсии и 30% маржи — маскирует реальную картину. Маркетолог без сквозной аналитики принял бы неверное решение по каналам (М2 → транскрипт).

**Нелинейность acquisition costs:** первая позиция в аукционе Яндекса может давать в 5–7 раз больше пользователей, чем вторая (М2 → транскрипт).

### 2.5 Данные о конверсии: откуда брать

Погрешность записи меток в CRM — до 30–40%. CEO, инвестор, аналитик, маркетолог и продакт из одной компании называют разные конверсии из одних данных — это норма. Причины: разные источники (GA vs CRM vs биллинг), разные периоды, пиковые показатели запомнились как норма (М2 → транскрипт).

Правило: самые надёжные данные — биллинг. Использовать Bounce Rate из Яндекс.Метрики / GA как главную метрику — «устаревший подход, никак не коррелирует с конверсией; берите события» (K-dop → bWGCFiqdQ7k).

## 3. Экономика внимания: воронка привлечения

### 3.1 Активация — главная метрика воронки

«Активация — процент людей, которые поняли выгоду от продукта» (М4 → транскрипт). Это ограничение снизу для всех остальных метрик: конверсии, повторных покупок, LTV.

Логика цикла деградации продукта (антипаттерн):
```
Добавляем фичи → продукт усложняется → активация новых падает
→ конверсия падает → CPL/CAC растёт → маркетинг сокращают
→ выручка падает → новая стратсессия → снова фичи
```
(М4 → транскрипт)

### 3.2 Воронка как «минное поле»

«Каждый экран, шаг, форма в воронке — потенциальная «мина», на которой пользователь теряется» (М4 → транскрипт).

**Критическая ошибка:** оптимизировать начало воронки, когда мина — в конце. 40 A/B-тестов не помогут, если 97% пользователей отваливаются на экране привязки карты (кейс Playki).

Кейс Playki (стриминг игр):
- 40 A/B-тестов за 3 месяца: конверсия с 0,2% до 0,4% — несущественно.
- Обнаружена мина: экран привязки карты. Новые пользователи: 97% отваливались. Старые: 93% отваливались.
- После подключения нормального эквайринга и устранения «фродового» фильтра: конверсия органика 6%, платные каналы 5–5,5%.
(М4 → транскрипт)

Алгоритм: сначала найти и устранить мины в конце воронки, потом работать с серединой и верхом.

### 3.3 Расчёт потерь от конверсионной проблемы

```
Потери в рублях = (Целевая конверсия% − Текущая конверсия%) / Текущая конверсия% × Текущая выручка
```
Пример: разница 1,5 п.п. при текущей конверсии 0,3% и выручке 4 млн → 1,5 / 0,3 × 4 = 20 млн руб. потеряно из-за непонимания пользователей (М4 → транскрипт).

### 3.4 Язык фреона vs. язык пользователя

«Язык фреон» — говорить о продукте техническими терминами (как устроен холодильник: фреон, компрессор). Противоположность — язык пользователя (сверху храню пиво, снизу пельмени) (М4 → транскрипт).

Пример — магазин запчастей: 90%+ требуют VIN-номер, считая, что все знают, что это. Команда общается только с теми, кто знает VIN (confirmation bias). Не-профессиональный сегмент (стажёры в автосервисах, новички) уходит молча (М4 → транскрипт).

Алгоритм написания оффера (из кейса с банком):
1. Записать JTBD-сценарий: «Когда [ситуация/триггер], пользователь хочет [желаемый результат], делает [действие]».
2. Убрать «выгодный налог» — скрыть или объяснить шаги, нужные компании.
3. Перевести в текст выгоды: «Вы получаете [результат] сразу после [минимального действия]».
4. Проверить: есть ли на каждом экране хотя бы одна выгода для пользователя?
(М4 → транскрипт)

Пример: банк, оффер на открытие счёта. Старый лендинг: «Бесплатное открытие счёта за 5 минут» + экраны без выгоды. Новый: «Номер счёта прямо сейчас. Вы получаете номер счёта сразу после заявки. Его уже можно давать контрагентам и подписывать договора.» Результат: конверсия в 2 раза выше (М4 → транскрипт).

### 3.5 Средний чек определяет инструменты привлечения

Таблица соответствия из материала (М4 → транскрипт):

| Средний чек (руб.) | Инструменты продаж |
|---|---|
| До 10 000 | Кнопка на сайте, биллинг, квизы |
| 10 000 – 50 000 | Пуши, рассылки, телемаркетинг |
| 50 000 – 100 000 | «Красная зона» — продавать тяжело (в Штатах $3 000–$10 000) |
| 100 000+ | Личные встречи, сейлзы, B2B |

### 3.6 Два потока и «бассейн»

«Два потока денег в юнит-экономике: новые клиенты и старые клиенты (когорты). Отток = операция вычитания» (М4 → транскрипт).

Метафора бассейна:
```
База пользователей(t) = База(t-1) + Приток новых − Отток старых
```
Если приток < оттока — база сокращается («бизнес-ресетор»). Бизнес, живущий только на новых пользователях: CAC постоянно растёт, экономика ухудшается (М4 → транскрипт).

## 4. Когорты: почему без них маркетинговые выводы неверны

### 4.1 Главный принцип

«Вы не имеете права считать без когорт. Если без когорт — вы на 100% делаете неверный вывод. Это прям факт» (М4 → транскрипт).

P&L показывает приход выручки, но не определяет будущее. «Глядя на P&L, предсказывать план продаж — безумие. План продаж определяют финансовые когорты» (М4 → транскрипт).

### 4.2 Типы когорт

- **Финансовая когорта** — основание: дата первой оплаты. Используется для P&L-прогноза.
- **Коммерческая когорта** — основание: дата первого контакта/заявки. Используется для анализа цикла сделки и работы отдела продаж.
(М4 → транскрипт)

### 4.3 Когорты и диагностика изменений в маркетинге

Кейс интернет-магазин: суммарная выручка ~22, 21, 20 млн руб. — кажется стабильной. При разбивке на новые/старые когорты:
- Январь: 10 млн новые + 10 млн старые.
- Февраль: 10 млн новые + 11 млн старые.
- Март: 7 млн новые + 12 млн старые.

Команда в марте переработала сайт, ухудшив его для новых пользователей. Маркетинг запустил акции → старые когорты дали компенсацию. Через 2–3 месяца спад: компенсация исчерпана, новые когорты слабые. Ошибка марта влияет на P&L до сентября (М4 → транскрипт).

### 4.4 Когортный расчёт повторных покупок

Типичная ошибка: «100 чел. за год сделали 600 покупок → в среднем 6». Реально 90% купят один раз (М1 → транскрипт).

```
APC = Суммарное число платежей когорты / Размер когорты
```
Пример: когорта 6 000 чел. → 7 330–7 495 платежей → APC ≈ 1,22–1,25 (М1 → транскрипт, раздел «Когорта 6000»).

Практические ориентиры по повторным покупкам:
- Если не считали когорты — берите 1 и 2 (самые частотные значения).
- Рекуррентный бизнес (подписка, привязка карты): ~3 покупки/год при retention ~60%.
- B2B с удержанием 90%: ~7 покупок/год.
- 12 покупок/год — редкость, только при годовой предоплате.
(М1 → транскрипт)

**Важно:** нельзя изменить частотность покупок без изменения сценария использования продукта. Если JTBD-сценарий предполагает покупку раз в год, купонами и бонусами частоту принципиально не поменять. Нужен «морфинг бизнес-модели» — добавление соседних работ (М2 → транскрипт, разбор кейса FlowWow).

## 5. Сегментация и работа с engaged/not-engaged

### 5.1 Ключевое разделение пользователей

**Not engaged** — пользователь, у которого не было ни одного целевого события (M-dop → bWGCFiqdQ7k).

```
Все пользователи
├── Engaged (совершили целевые события)
│   ├── Купили → % конверсии (меньшинство)
│   └── Не купили → (1 − конверсия) × engaged — здесь работаем
└── Not Engaged (ни одного целевого события) → 80–90% — проблема привлечения или продукта
```

«Мы работаем не с конверсией — мы работаем с единицей минус конверсия» (K-dop → bWGCFiqdQ7k). Задача — снизить долю не купивших, а не поднять абстрактную конверсию.

Кейс e-commerce: «грязная» конверсия (по всем) 0,5%, «очищенная» (по engaged) — 4,4%. Доля not-engaged коррелирует с конверсией: чем выше not-engaged → тем ниже продажи (K-dop → bWGCFiqdQ7k).

### 5.2 Ошибка выжившего в маркетинге

«Команды общаются с теми, кто купил или оставил заявку, а не с теми, кто ушёл молча» (М4 → транскрипт). Следствие: продукт и коммуникация настраиваются под 0,2–2% купивших, а не под 98–99,8% не купивших.

Лендинг = фильтр: «отсекает всех, кто не понял оффер, оставляет тех, кто понял. Вы неизбежно попадаете на ошибку выжившего» (K-dop → A3vXNpW9r2Y).

### 5.3 Три команды видят разных слонов

Маркетинг смотрит наружу (каналы, офферы, сегменты). Продажи — на конверсию этапов воронки и CRM. Продукт — на фичи и пользователей в своём мире. Все три видят разных «слонов» → локальная оптимизация → системный провал (K-dop → bWGCFiqdQ7k).

Решение: ввести язык перевода = сквозная воронка, построенная на реальных данных продаж.

## 6. Антипаттерны маркетинга через линзу юнит-экономики

Список составлен исключительно из входных выписок.

1. **Сначала лить трафик, потом оптимизировать метрики.** При плохой марже рост CPU вместе с ростом трафика немедленно даёт убыток (М1 → транскрипт).

2. **Скидки без расчёта эффекта на маржу.** Скидка 30% при узкой марже → прибыль уходит в убыток. Скидок не существует — есть сегментация по цене (М1 → транскрипт, раздел «Скидки и маржинальность»):
   ```
   Прибыль со скидкой = (Средний чек × (1 − Скидка%)) − Себестоимость
   ```
   Пример: чек 500 руб., себестоимость 400 руб., скидка 0% → прибыль 100 руб. Скидка 30%: 350 − 400 = убыток −50 руб.

3. **Линейная экстраполяция роста.** Цель «26% в неделю» из линейного деления точки A на точку B → провал через 3–4 недели. Мозг думает линейно, реальность растёт экспоненциально (М1 → транскрипт, кейс доставки еды).

4. **Работа с upsell при плохой базовой экономике.** При AMPPU 36 руб. и конверсии 10%, upsell на 200 руб. даёт ~40 коп. на пользователя = 18 000 руб./мес. за полгода работы команды (М1 → транскрипт).

5. **Неправильные премии сейлзам** — от выручки, а не от когортного LTV → сейлз привлекает клиентов на 1 месяц вместо годовых тарифов (М1 → транскрипт).

6. **Считать CAC вместо CPU.** Выгодно для инвесторов, но неверно для управления маркетинговым каналом (М2 → транскрипт).

7. **Брать конверсию из GA/Метрики, а не из биллинга.** Погрешность аналитики — до 30–40% (М2 → транскрипт).

8. **Компенсировать спад акциями/скидками.** Работает 2–3 месяца, скрывает проблему, после чего спад продолжается: старые когорты исчерпываются, а новые слабые (М4 → транскрипт).

9. **Продавать технологию, а не выгоду.** «Никому не нужны агенты/инструменты; всем нужно снижение издержек или рост доходов» (K-dop → jQnon9yfcCY).

10. **Масштабировать маркетплейс без понимания эффектов.** Рост числа поставщиков → снижение заказов на поставщика → снижение ценности платформы → снижение конверсии и среднего чека. Стратегия крупного маркетплейса и стартапа — противоположны (М2 → транскрипт).

11. **Принимать критерий целевого лида «из головы».** «Почти во всех компаниях критерий целевого лида никак не коррелирует с реальными данными» (K-dop → bWGCFiqdQ7k).

## 7. Что дальше

**Приоритет действий:**

1. Посчитать юнит-экономику (AMPPU, CPU, конверсия по сегментам) → проверить кросс-чеками.
2. Определить, на каком из трёх уровней сходимости есть проблема.
3. Найти «плечо метрик»: что меняет прибыль больше всего при изменении на X%.
4. Работать в порядке: маржинальность → средний чек → конверсия → поток.
5. Построить когортный треугольник — разделить выручку на «новые» и «старые» когорты.
6. Найти и устранить мины в конце воронки перед оптимизацией верха.
7. Проверить активацию: понимают ли новые пользователи выгоду в первой сессии?

**Что не покрыто входными материалами:** детальные инструкции по работе с когортным треугольником в Excel (анонсировано на Испытании 5 курса); расчёт виральных коэффициентов; методология Retention-анализа за пределами упомянутых фреймворков.
