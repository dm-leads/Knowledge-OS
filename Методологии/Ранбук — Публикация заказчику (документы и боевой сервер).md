# Ранбук — Публикация заказчику (документы и боевой сервер)

## Краткая суть

- **Опубликованный документ — место, где могли появиться чужие правки.** Перед повторной публикацией — прочитать
  их и забрать в исходник. Публикация «на автомате» однажды уже стёрла ручную работу.
- Публикация идёт **в тот же документ:** ссылка у заказчика не меняется. Карта «файл → документ» хранится в git.
- **Код заказчика — отдельный контур:** в его репозиторий попадают только файлы правки. Правка — отдельной веткой
  и запросом на слияние; мерж не равен выкладке.
- **Боевой сервер:** по умолчанию только чтение. Замена файла — после «да» владельца, по процедуре: сверка →
  разница → предпросмотр → бэкап → заливка → проверка хешем → автооткат при расхождении → проверка на живом
  сайте браузером.
- Стоп-лист файлов зашит в скрипт выкладки. Откат — штатное действие: сначала откатить, потом разбираться.

> Для быстрого знакомства человеку может хватить блока выше.
> Ниже начинается полный каноничный текст документа.
> Для агентов, правок, анализа, ревью и разрешения расхождений обязателен полный текст.

## Когда применять

Любая выдача результата заказчику: документы, таблицы и модели (Google Docs и Таблицы или аналоги), правки кода
и файлов на его сайте или сервере.

## А. Документы и таблицы

1. **Всё, что увидит заказчик, — по ссылке,** а не приложением в переписке: он комментирует и правит документ.
2. **Одна команда публикации** (скрипт проекта). Документ руками не создают — иначе его нет в карте, и для
   следующего чата он не существует.
3. **Карта «локальный файл → документ»** хранится в git проекта. Без неё повторная публикация создаст новые
   документы, а старые ссылки у заказчика останутся на устаревшей версии.
4. **Перед публикацией — прочитать, что изменилось в опубликованной копии,** и забрать правки в исходник (`.md`,
   скрипт сборки). Только потом публиковать. Источник правды — исходник, но только после переноса чужих правок.
5. **Стоп-файлы:** документ, в котором вручную ведётся то, чего нет в сборке (сценарии в модели, ручные строки),
   не публикуется без явного разрешения владельца, пока ручная часть не перенесена в скрипт. Снимок ручной
   части — рядом.
6. **Служебное отдельно:** бэклог, журнал, промпты лежат в служебной папке, не в папке заказчика.
7. **Минимальный доступ приложения публикации:** оно видит только созданные им файлы.

## Б. Код и боевой сервер

### Два контура — не смешивать

| | Наш рабочий контур | Контур заказчика |
|---|---|---|
| Что лежит | знания, аналитика, скрипты, экономика | только файлы сайта и ТЗ к правке |
| Владелец | мы | заказчик |
| Где на диске | в проекте канона | отдельная папка вне канона: случайная публикация не уйдёт наружу |

В репозиторий заказчика **не попадают:** наши материалы, секреты и доступы, экономика и ставки, ПДн, тяжёлое
сырьё. Перед каждым запросом на слияние — `git diff --stat` глазами.

### Правка через запрос на слияние

1. Клон заказчика: переводы строк без подмены (`core.autocrlf false`) — иначе любая правка приходит «файлом
   целиком». Подпись коммитов — служебным адресом, заданным локально до первого коммита.
2. **Свежая база:** `git fetch` перед любым выводом о расхождении сервера и репозитория. Расхождение —
   гипотеза, пока не сверено по содержимому.
3. Одна правка — одна ветка — один запрос на слияние. Рядом — ТЗ: что, зачем, где проверить.
4. Отправка в репозиторий заказчика — действие наружу: только после «да» владельца с указанием пути.
5. **Мерж не равен выкладке.** После мержа проверить, что правка на сервере и видна на живом сайте.
6. Ограничения заказчика («не плодить стили») — правило, а не пожелание: сначала переиспользовать
   существующее, новое — с обоснованием в описании.

### Замена файла на боевом сервере

Доступ к серверу по умолчанию — на чтение. Для ночной автоматики — отдельная учётная запись, запертая в своей
папке. Замена файла — только по процедуре и через скрипт, который её держит:

1. **Сверка** сервера с репозиторием по всем файлам правки. Расходится — стоп: править нельзя, правка ляжет на
   устаревшую базу.
2. **Разница** построчно — в правке нет лишнего.
3. **План владельцу** и явное «да» на эту заливку.
4. **Предпросмотр** без записи. Для вёрстки — предпросмотр страницы на своей площадке: живая страница с
   подставленной правкой, помечена «не сайт», закрыта от индексации, формы обезврежены, шрифты проверены.
5. **Заливка:** скрипт скачивает серверную версию в бэкап (нет бэкапа — нет заливки), заливает, сверяет хеш
   того, что реально легло, и при расхождении сам возвращает файл.
6. **Проверка на живом сайте** настоящим браузером, без прокси и мимо кэша: то, что должно было измениться, а не
   «сайт открылся». Браузер видит то, чего не видно в HTML.
7. **Финальная сверка** — дрейфа не создали. Запись в CHANGELOG: что заменили, где бэкап, что проверено.

**Порядок «сначала мерж, потом заливка»** обязателен: залитая из ветки версия, которой нет в основной ветке,
исчезнет при следующей выкладке заказчика.

**Стоп-лист** (конфиги с боевыми доступами, серверные правила редиректов, файлы, правленные прямо на сервере,
каталоги данных и логов) зашит в скрипт: он отказывается их заливать. Список меняется в двух местах сразу —
в ранбуке проекта и в скрипте.

### Откат и сбой

- Откат — штатная команда скрипта из бэкапа. Что-то выглядит не так — сначала откатить, потом разбираться.
- Сервер встал: сначала за минуту снять картину (что отвечает, что нет, процессы, место на диске) — после
  перезапуска следы исчезнут. Лечение — по возрастанию воздействия, самый безопасный шаг первым. Версии
  платформы не менять как «лечение».
- Сервер заказчика чинит тот, у кого есть права: наша роль — картина и порядок действий.

## Результат

Заказчик получает документы по неизменным ссылкам с сохранёнными комментариями и правки кода, которые он видел
до выкладки. Каждая замена на сервере имеет бэкап, проверку хешем и запись в журнале.
