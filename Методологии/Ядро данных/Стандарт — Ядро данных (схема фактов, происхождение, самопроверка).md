# Стандарт — Ядро данных (схема фактов, происхождение, самопроверка)

> Активирован 14.09.2026: ворота этапа 1 первого инстанса пройдены — схема создаётся на файловой и
> серверной СУБД одним кодом, тест границы зелёный, красные случаи К1–К7 и К9 отвергнуты кодом с
> номером правила (75 контрактных тестов на двух СУБД). Требования Я1–Я13 и принципы не
> пересматриваются без ADR.
>
> Дополнен 28.09.2026 уроками этапов 2–6 и переноса на сервер первого инстанса (ADR-0002–0004 контура):
> сырой слой — минимизированная копия, деньги через документы-посредники, покрытие журналом окон, любой отбор —
> параметр модели, снимки своих чисел, К11.

## Краткая суть

- Ядро хранит **факты** — контакт, сделку, изменение поля, оплату, визит, звонок, связь заявки с
  маркером, дневную веб-статистику, расход, спрос, факт диалога, — а не агрегаты чужих отчётов.
  Метрика определяется **один раз** моделью ядра; фильтры контура — параметры модели.
- **Каждая строка несёт происхождение** (система, класс источника, идентификатор загрузки, время
  загрузки), **каждое число наружу** — период, источник `класс:система:запрос`, статус и дату
  съёма. Число без этого не существует; «нет данных» — статус, не ноль.
- **Схема не знает поставщиков**: имена сервисов и их технических полей живут только в
  загрузчиках и конфигурации инстанса; это проверяет тест границы.
- **Персональные данные** — только ключевой хэш инстанса; имена, адреса и тексты не хранятся;
  база вне репозитория; в тестах — синтетика и агрегаты.
- **Самопроверка пятью уровнями** с кодом возврата: загрузка → модели → мосты → известные
  ответы → гейт. Ложный ввод отвергается кодом с номером правила; известный ответ не
  воспроизведён — стоп работы, не «почти».
- Потребители читают **опубликованные числа** (файл публикации или таблицы); агент — SQL только на
  чтение; деньги считает код, агент интерпретирует.
- **Деньги** связываются со сделкой через документы-посредники; выручка — только платежи с
  документом-основанием; возврат — отрицательной суммой. **Полнота периода** доказывается журналом
  окон, а не наличием фактов. **Любой отбор** — параметр модели. Ядро помнит **свои числа на дату**.

## Что нормируется

Устройство любого инстанса Ядра данных: слои и границы между ними, схема фактов, контракт
происхождения строки и числа, обращение с персональными данными, история изменений и дата съёма,
состав самопроверки и красных случаев, интерфейс потребителей. **Не нормируется** выбор продуктов:
СУБД, инструмент загрузки, движок моделей — решение инстанса (Я10), фиксируемое в его
конфигурации и ADR.

Классы источников A–F ядро не переопределяет — берёт из
[Стандарта — Протокол обнаружения источников](<../Движок роста/Стандарт — Протокол обнаружения источников и глубина погружения.md>).

## Требования к результату

### 1. Тринадцать требований

| # | Требование | Как проверяется |
|---|---|---|
| Я1 | Ядро хранит **факты**, не агрегаты чужих систем. Агрегаты — только замороженные снимки: чужие — для мостов и известных ответов, свои — для ответа «что ядро знало на дату»; новые метрики на снимках не строятся | таблицы фактов без колонок-метрик; снимок несёт дату съёма и систему; число на прошлую дату без снимка — отказ (К2) |
| Я2 | Каждая строка несёт **происхождение**: система, класс источника A–F, идентификатор загрузки, время загрузки; каждое число наружу — период, источник `класс:система:запрос`, статус, дата съёма | строка без происхождения не записывается (К1); число без даты съёма отвергается (К2) |
| Я3 | **История изменений**: события сущностей с временем записи; снимки агрегатов — по дате съёма; удаление не физическое | известный перелом истории инстанса воспроизводится запросом; вчерашнее значение поля доступно |
| Я4 | **Единица дедупа — человек** (контакт); сделка ссылается на контакт; бренд — атрибут сделки; сложение по кабинетам и периодам — только доказанное; итог компании — по всем фактам, не суммой брендов | бренды + «без бренда» = компания; метрика с недоказанным дедупом не складывается (К7) |
| Я5 | **Схема не знает поставщиков**: имена систем и полей — только в загрузчиках и конфигурации; тест границы | поиск по схеме и моделям не находит имён сервисов и их технических полей (К9) |
| Я6 | **ПДн**: телефоны и почта — только ключевой хэш инстанса; имена, адреса, тексты не хранятся; база вне репозитория; наружу — агрегаты и идентификаторы | проверка перед записью; тест на образце с телефоном и почтой отвергает запись (К6) |
| Я7 | **Только чтение** источников; белый список эндпоинтов у каждого загрузчика | запрос вне списка не отправляется (К10) |
| Я8 | **Самопроверка пятью уровнями** с кодом возврата; известные ответы обязательны; красные случаи отвергаются кодом с номером правила | команда гейта; файл известных ответов; тест на каждый красный случай |
| Я9 | **Один прогон — один день**; числа разных съёмов не складываются и не делятся | тест на числах разных дат (К7) |
| Я10 | **Продукт хранилища — выбор инстанса**; одни модели на файловой и серверной СУБД | контрактные тесты схемы и моделей на обоих движках |
| Я11 | **Агентный интерфейс**: SQL только на чтение + стандарт ответа со статусом; агент интерпретирует, деньги считает код | интерфейс отвергает запись (К8); ответ несёт период, источник, статус, дату съёма |
| Я12 | **Метрика определяется один раз** моделью ядра, не отчётом сервиса; **любой отбор** — её параметр (набор отбора из конфигурации), включая базовые условия вроде «только первые квалифицированные»; отбор, который не параметр, назван в пояснении числом | одна модель даёт числа всех наборов отбора; пояснение перечисляет зашитые отборы и сколько каждый отсёк |
| Я13 | **Сбор отделён от склейки**: сборщики визитов и звонков заменяемы; склейка визит ↔ заявка ↔ сделка ↔ оплата — в ядре | смена загрузчика визитов не меняет схему и модели |

### 2. Слои и границы

```
serve    агентский интерфейс (SQL только чтение) · публикация чисел · опубликованные таблицы · гейт
metrics  модели: канонические метрики × (бренд, поток, период, разрез, набор отбора) → число
facts    каноническая схема фактов; происхождение в каждой строке
raw      минимизированная копия источника: только ключи из белого списка загрузчика; телефон и почта —
         хэшем, чужой номер в тексте — меткой, всё до записи; журнал загрузок; наружу не публикуется
```

- Потребители читают только опубликованное: файл публикации (контракт числа, снимок на дату съёма,
  только агрегаты) или таблицы `metrics.*` и `facts.*`. Агент — через интерфейс только на чтение;
  внешние системы-потребители — своим адаптером; отчёты — экспортом.
- Точки входа (командная строка, разбор аргументов) живут в `serve`, не в `schema`: слой схемы — ядро
  без интерфейсов, это стережёт тест границы. Модуль без точки входа при запуске молча возвращает 0 —
  успех миграции проверяется версией схемы в базе, а не кодом возврата.
- Модели читают только `facts` (К9). `raw` виден только проверкам загрузки.
- Маппинг имён и полей систем-источников — только в загрузчиках (`loaders`) и конфигурации
  инстанса. `facts` и `metrics` имён систем не содержат (Я5).

### 3. Схема фактов

Имена таблиц и ключей — переносимые идентификаторы; состав полей уточняется на этапе 1
инстанса, обязательные поля ниже не сокращаются.

| Таблица | Ключ | Обязательные поля | Класс |
|---|---|---|---|
| `contact` | `contact_id` | бренд первого касания, `created_at`, заявленный источник, `phone_hash`, `email_hash` | D |
| `deal` | `deal_id` | `contact_id`, бренд, воронка, статус, `created_at`, `first_sql_at`, флаг «новый первый квалифицированный», `closed_at`, `price`, канал входа технический и сводный, ссылка на маркер, `parent_deal_id`, результат квалификации (маршрут, прежний маршрут, причина закрытия — основа MQL) | D |
| `deal_field_change` | `deal_id`, поле, `changed_at` | старое и новое значение (поля белого списка), `recorded_at` | D |
| `payment` | `payment_id`, система | `paid_at`, сумма (возврат — отрицательная), `order_id`, `deal_id` (может быть пуст — оплата вне CRM тоже деньги компании), бренд, признак документа-основания | D |
| `shipment_cogs` | отгрузка, система | дата отгрузки, себестоимость, ссылка на счёт и заказ | D |
| `visit` | `visit_id` | `started_at`, маркер, страница входа, реферер, `client_id`, устройство, гео | C / A |
| `phone_call` | `call_id` | `started_at`, `visit_id`, сценарий, `callee_line` (номер линии компании — только из белого списка инстанса), `caller_hash`, `deal_id` | C |
| `order_marker` | `deal_id` | маркер, `visit_id`, дата заявки по системе | C |
| `web_daily` | дата, страница входа | визиты, посетители, достижения целей | A |
| `spend` | дата, кампания | расход (с указанием, с налогом или без), клики, показы | B |
| `demand` | месяц, фраза, регион | частота | E |
| `dialog_fact` | код факта, значение, канал, период | число наблюдений | F |
| `snapshot_number` | метрика, система, кабинет, период, дата съёма | агрегат внешней системы — только для мостов и известных ответов | любой |
| `exclusion` | сущность, ключ | причина, с какой даты, кто решил | — |

В каждой таблице: `source_system`, `source_class`, `load_id`, `loaded_at`. Журнал загрузок —
таблица `load_log` в служебной схеме; `load_id` строки обязан быть в нём зарегистрирован, и это
проверяет писатель, а не внешний ключ базы: файловые аналитические СУБД не поддерживают ключи
между схемами. Имена таблиц избегают ключевых слов SQL-движков (`phone_call`, `load_log`).
Журнал покрытия — `window_log` в служебной схеме: система, вид данных (колонкой или отдельной записью
системы), окно, строк, время завершения.
Ключи сущностей сбора и денег — вместе с системой-источником: идентификаторы разных кабинетов одного
поставщика пересекаются.

Правила схемы:

- Контакт — единица дедупа; сделка без контакта не записывается (К4).
- Бренд — атрибут контакта и сделки, не структура базы; правило определения бренда — в
  конфигурации инстанса (например, по полю сделки, запасной путь — по воронке; каждый запасной
  путь считается и публикуется как «чего не хватает»).
- Дочерние сделки ссылаются на родительскую через `parent_deal_id`; наследование канала — модель
  ядра, не правка факта.
- Технические и тестовые сущности не удаляются, а исключаются через `exclusion` с причиной.
- Даты и время — с поясом; правая граница любого периода **исключающая**.

### 3а. Деньги

- Связь оплаты со сделкой — по цепочке документов учётной системы: оплата → счёт или отгрузка → заказ →
  сделка. До плана пробой выяснить, через что документы ссылаются друг на друга; прямую ссылку не
  предполагать (пример первого инстанса: напрямую на заказ ссылались около 7 % оплат).
- Заказ бывает старше оплаты на месяцы: заказы и посредники читаются с запасом назад (параметр инстанса);
  недостающий посредник дочитывается по своему номеру, без фильтра дат.
- Двойной счёт: выручка — только платежи с документом-основанием. Признак структурный, не текст
  назначения. Сводные переводы без основания (эквайринг по реестру) лежат в фактах, но не в выручке; их
  сумма — в пояснении.
- Возврат — свой тип документа, в фактах отрицательной суммой: уменьшает выручку, оплатой не считается.
  Похожий по названию исходящий платёж бывает оплатой поставщику — тип подтверждается связью документов,
  не названием (у первого инстанса возврат покупателю и оплата поставщику — разные типы документов учётной
  системы с похожими названиями).
- Платёж, основания которого ведут к разным заказам, к сделке не относится и назван отдельно: явное «не
  знаю» вместо деления суммы.
- Оплата без сделки — деньги компании: в выручке компании есть, в выручке по сделкам нет. Платежи без
  сделки и возвраты без сделки называются раздельно — иначе гасят друг друга.
- Себестоимость — на отгрузке (на платеже она задваивается при авансе и доплате), связь с деньгами —
  через того же посредника. Правило счёта спрашивается у владельца финансового контура до кода: разные
  отчёты учётной системы дают разные ответы.
- Метрики денег фильтруют факты по системе денег: деньги второй учётной системы молча не складываются.
- Загрузка не пишется, если источник не отдал документы связи: число документов-посредников, на которые
  ссылаются оплаты, но которые не пришли, выше порога (объявленная доля с минимумом в штуках). Порог
  считает только неполученное (счёт без заказа — норма); сравнивать долю связанных с прошлым прогоном не
  нужно — это блокирует законные изменения состава оплат. Пример первого инстанса: прогон с кодом 0
  записал почти все оплаты «без сделки» поверх связанных.

### 4. Контракт происхождения

**Строка.** `source_system` — имя системы-источника из конфигурации инстанса (значение в
строке, не элемент структуры схемы); `source_class` — класс A–F по природе факта;
`load_id` — идентификатор загрузки из журнала загрузок; `loaded_at` — время записи в ядро.
Строка без любого из четырёх полей не записывается (К1).

**Число** (`metrics.number` и любой ответ наружу):

| Поле | Значение |
|---|---|
| `metric` | каноническое имя метрики из словаря инстанса |
| `level` | ступень воронки или природа числа (заявка, квалифицированный, оплата, визит, деньги) |
| `scope` | кабинет / бренд / компания |
| `flow` | поток: веб / без визита / офлайн / все |
| `segment` | разрез (канал, страница, кампания) или пусто |
| `period_start`, `period_end` | период, правая граница исключающая |
| `source` | `класс:система:запрос` — класс A–F, система из конфигурации, имя модели или запроса |
| `status` | `факт` · `оценка` · `proxy` · `нет данных` |
| `as_of` | дата съёма — день состояния данных |
| `value` | значение; при `нет данных` — пусто, не ноль |
| `missing` | чего не хватает: запасные пути, исключения, неполные источники |

Класс источника у числа ядра — по природе факта (D для CRM-фактов, C для визитов и маркеров и
так далее); ядро — система, не класс. Операции над числами: сумма и доля — только числа одного
съёма, одной ступени и одного объявленного правила сложения; итог получает самый слабый статус из
входящих. Сравнение съёмов — явная операция, печатающая обе даты.

**Статус и пояснение.**
- «Оценка» — если после последней успешной загрузки обязательной системы была незавершённая. Обрыв до
  успеха перекрыт и статус не понижает; у системы, где успеха не было ни разу, поминается каждый обрыв.
  Правка, «улучшающая» статус до «факта», проверяется тестом на оба случая: ошибка здесь невидима.
- Зашитые отборы (удалённые, технические сущности) статус не понижают — они делают число верным, — но
  названы с числом отсечённого. «Оценка» бережётся для настоящей неопределённости.
- Доля печатает знаменатель числом («0,49 % (12 из 2 450 визитов)»), разрез — в заголовке числа
  («измерение=значение»): два числа с разным отбором не выглядят одинаково.
- Счётчики пояснения считаются тем же отбором, что и число; причины взаимоисключающие.
- Имена кабинетов и систем из конфигурации проверяются по форме до подстановки в запрос.

### 4а. Покрытие

- Полнота периода доказывается журналом покрытия, а не наличием фактов: один дозапрошенный факт не
  доказывает окно.
- Покрытие — объединение окон, а не минимум и максимум времён: разрыв между окнами — «нет данных».
- У каждого вида данных загрузчика своё окно (деньги и себестоимость — разные записи); окно пишется только
  при успешном чтении. Иначе сбой одной части прячется за успехом другой.
- Вне покрытия — «нет данных», частично — «оценка»; ноль — только по покрытому периоду.
- Период запроса закрытый: день съёма входит целиком, позже не читается.
- Источник может молча обрезать период с успешным кодом (скользящая глубина истории): загрузчик сверяет
  фактический период ответа с запрошенным.
- Общее правило покрытия по источникам — в
  [Стандарте — Консистентность метрик](<../Стандарт — Консистентность метрик.md>); здесь — механизм ядра.

### 6. Политика персональных данных

- Телефон и почта хранятся **только** как ключевой хэш инстанса (`phone_hash`, `email_hash`,
  `caller_hash`); ключ — переменная окружения, в документах и конфигурации — её **имя**.
  Одинаковый ключ у всех загрузчиков инстанса — иначе звонок и контакт не склеятся.
- Имена, адреса, свободные тексты, цитаты, записи разговоров **не хранятся**. Факты диалогов
  (класс F) — только агрегаты: код факта, значение, канал, период, число наблюдений.
- База, снимки и файлы известных ответов с идентификаторами сущностей — вне репозитория; в
  репозитории — код, конфигурация с именами переменных, тесты на синтетике и агрегатах.
- Перед записью текстовых колонок — проверка на шаблоны телефона и почты (уровень 1, К6).
- Имена, адреса и тексты не ловятся шаблоном — их не хранит **схема**: в фактах нет свободных
  текстовых колонок, только коды и значения справочников. Барьер от вставки текста в колонку
  значения — предел длины (200 знаков): длиннее — К6.
- Номера линий самой компании (куда звонят клиенты) — не ПДн клиента, но открытого исключения
  нет: колонка `callee_line` принимает только номера из белого списка конфигурации инстанса,
  любой другой номер — К6.
- Наружу (агент, отчёты, потребители) — агрегаты и идентификаторы сущностей; повторный запрос по
  идентификатору идёт в систему-источник по её правилам доступа.
- До `raw` — **белый список** ключей каждого ресурса, а не чёрный: иначе вложенные сущности (теги,
  компании, описания) доезжают до хранилища.
- К6 работает в двух режимах: значение источника с чужим телефоном или почтой заменяется меткой
  «К6:скрыто» до `raw` (число замен — в отчёте загрузки); в колонке фактов — отказ.
- Технические адреса хранятся только в нужной части: маркер — уровни канала, хост — два уровня домена,
  путь страницы — первый сегмент. Цифры меток кликов, поддоменов и UUID совпадают с шаблоном телефона.
- Колонки-идентификаторы объявлены в схеме и проверяются формой кода; любая текстовая колонка `…_id`
  обязана быть объявлена — это стережёт тест.
- Свободный текст ради малой доли покрытия не заносится: риск ПДн дороже нескольких процентов атрибуции.
- Агентское соединение: запрет чтения файлов и серверных файловых функций; запрос нормализуется
  (кавычки, комментарии) до проверки объектов; на сервере — роль только на чтение, проверенная попыткой
  записи.
- Строка подключения к базе — только из окружения: аргументы процесса видит любой пользователь сервера.

### 7. История изменений и дата съёма

- `deal_field_change` хранит изменения полей белого списка: старое и новое значение,
  `changed_at` — время события в источнике, `recorded_at` — время записи в ядро. Белый список — в
  конфигурации инстанса; значения проходят проверку ПДн.
- Удаление сущности в источнике — отметка времени удаления, не физическое удаление.
- `snapshot_number` — замороженное число с датой съёма: агрегат внешней системы (мосты, известные
  ответы) или собственное число ядра (что ядро знало на дату). Метрика на прошлую дату читает снимок того
  дня; снимка нет — отказ (К2). Новые метрики на снимках не строятся (Я1). Решение — ADR-0002 контура.
  Снимок хранит число целиком: значение, **статус, пояснение и дату съёма самого числа** (не дату прогона —
  при упавшем источнике они различаются). Из снимка возвращается тот статус, с которым число снято:
  «оценка» не превращается в «факт» при чтении.
- **Один прогон — один день**: прогон ставит `as_of`. Дата съёма числа — наименьшая из дат последних
  успешных загрузок обязательных систем; отстающая система названа в пояснении. Источник с дозреванием
  грузится с объявленным отставанием (например, расход — по позавчерашний день); упавший источник
  остаётся на прошлой дате со статусом «оценка». Визиты и деньги в источниках меняются задним числом —
  поэтому дата съёма обязательна, а известные ответы берутся только из замороженных снимков.
- Время события в журнале источника ≠ время бизнес-события, если поле проставляли пакетами задним числом.
  Производная дата (например, первой квалификации) действует с даты запуска её писателя — параметр
  конфигурации; раньше — «нет данных». После заполнения новой колонки — проверка согласованности:
  минимум, медиана задержки, пики по дням.
- Одно значение в разных ресурсах источника записано по-разному (журнал событий против полей сущности):
  фикстуры тестов снимаются с живых ответов, не сочиняются.
- Удаления берутся из журнала событий (удаление и восстановление, побеждает последнее): список сущностей
  удалённые не отдаёт.
- Снимки своих чисел: каждый прогон сохраняет числа периодов известных ответов (всех этапов) и последних
  месяцев **отдельным шагом с кодом возврата**, после загрузок, от которых числа зависят; копятся только
  вперёд. Сбой снимка — сбой прогона, а не побочная ошибка. Известный ответ, снятый на другую дату,
  сверяется по допуску моста, вывод печатает обе даты.
- Производное поле, зависящее от поздних данных, пересчитывается после дозагрузки.
- `loaded_at` — время записи пачки, не старта прогона: иначе событие во время долгой загрузки выглядит
  пришедшим из будущего (К5). Документ, датированный будущим по природе (плановая отгрузка),
  откладывается до следующего прогона, а не отвергается.

### 7а. Отбор и модели метрик

- Набор отбора = база (какие сущности берём) + исключения (поле → значения). Поле — только из белого
  списка ядра: конфигурация не должна становиться способом писать SQL.
- Источник обрезает длинные значения — сравнение по началу строки; префикс точный и проверен: ловит ровно
  ожидаемое.
- «Исключение из исключения» — объявленный параметр (группа исключена, но переход с собственной площадки
  компании возвращён).
- Правило контура — в конфигурации (что), коде (как), тестах и справочнике инстанса (почему); все четыре
  совпадают. Описывается механизм, а не настройки поставщика; условия, зависящие от внешней системы,
  помечены с планом замены.
- Исключение канала проверяется распределением признака зачёта: если признак уже отсекает нецелевое,
  исключение канала выбрасывает целевые (пример первого инстанса: канал мессенджера, где продажи и сервис
  вместе).
- Сущности с неизвестным каналом, не исключённые правилом, остаются в зачёте; публикуется диапазон — без
  них нижняя граница.
- База сравнения (baseline) считается тем же набором отбора, что и измеряемое число.
- Ступени воронки между обращением и первым квалифицированным (MQL) — модель ядра с правилом в конфигурации: воронки
  квалификации, статусы, целевой маршрут, настоящие причины отказа. Если внешняя система считает ту же ступень по
  проекту (воронке), ядро показывает её разрезом по воронке — для сверки один к одному, — а бренд берёт из поля сделки.
  Поля квалификации не загружены — «нет данных», не ноль. Добавили поле в белый список загрузчика — историю
  перечитывают из источника отдельным прогоном, не сдвигая курсор ночного.
- Одна сущность видна в двух кабинетах сбора — берётся запись кабинета своего бренда, иначе двойной счёт.
- «Продажи ÷ заявки»: заявка и продажа — обычно разные сделки в разных воронках. Связь через контакт;
  бренд проверяется у обеих сторон; возвраты входят. Это верхняя оценка: оплата могла прийти по заявке
  прошлого периода (у первого инстанса счёт «через сделку» завышал конверсию более чем вдвое).
- Знаменатель конверсии не зависит от отбора сделок: тест «визиты не меняются при любом наборе».
- Тождество может сходиться при двух гасящих друг друга расхождениях: множители сверяются по отдельности
  (доход на лид = конверсия × чек × маржа). Одна метрика может честно иметь два определения (на
  оплаченную сделку и на лид) — тогда это две метрики с разными именами, не одна подогнанная.
- Каждое число проверяется на живых данных дважды — метрикой и прямым запросом к фактам — на нескольких
  периодах; совпадение до единицы.
- Команда разбора числа печатает лестницу отбора: всё → минус каждое условие → число.

### 8. Самопроверка — пять уровней

| Уровень | Что проверяет | Где живёт | Провал |
|---|---|---|---|
| 1. Загрузка | строк в источнике = строк в ядре по дням; свежесть; дрейф схемы (новое поле — сигнал, пропавшее — стоп); дубли по ключу (К3); ссылочная целостность (К4); события из будущего (К5); ПДн в текстах (К6) | журнал загрузок + `checks/load` | код 1, 🟥 |
| 2. Модели | аудиты: не пусто, уникально, допустимые значения; тождества (сумма долей = 1; деньги на единицу = конверсия × чек × маржа); юнит-тесты на фикстурах | реестр метрик инстанса: тесты на фикстурах обоих движков, тождества «метрика = прямой запрос к фактам» на живых данных; движок моделей — по выбору инстанса | код 1 |
| 3. Мосты | одна метрика, два источника, помесячно по кабинетам; допуск с доказательством; систематический перенос между месяцами блокирует даже в допуске | `checks/bridge` | код 1 |
| 4. Известные ответы | замороженные снимки воспроизводятся из фактов, не из агрегатов | `checks/known` + файл известных ответов инстанса | стоп работы |
| 5. Гейт | свежесть источников, объёмы за вчера, уровни 1–4, отсутствие ПДн, имена секретов существуют в окружении | `datacore health` — код 0/1, 🟥 структура / 🟧 покрытие | код ≠ 0 |

Гейт — исполняемая копия этого стандарта. Две тяжести: 🟥 **структура** — число будет ложным
(уровни 1, 2, 4, красные случаи); 🟧 **покрытие** — источник не отвечает, день не загружен, мост
не откалиброван. Обе дают код ≠ 0. Внешняя система-потребитель включает гейт ядра в свой гейт
как пробу источника.

Известные ответы (уровень 4):
- Допуск — для ответов чужих систем (мост) и для своих ответов на дату, на которую снимка нет; свои снимки
  сверяются точно и хранятся неокруглёнными.
- Эталон, разошедшийся с метрикой, сначала пересчитывается его же скриптом на текущих данных: устаревший
  снимок выглядит как расхождение определений.
- Эталон может оставаться красным намеренно, но только **объявленно**: в файле известных ответов у него
  пометка «расхождение объяснено» со ссылкой на разбор. Проверка уровня 4 считает такие ответы отдельной
  строкой отчёта и не валит на них код возврата; необъявленное расхождение — стоп. Подгонка метрики
  запрещена.

До гейта (этап 7) эксплуатацию держит минимум из ADR-0003 контура: коды возврата шагов, сторож тишины,
уведомление о сбое, резервная копия с проверкой восстановления, К11.

### 9. Красные случаи

Заведомо ложный ввод отвергается **кодом** с номером правила. Код, принимающий ложь, сломан,
даже если цифры красивые. На каждый код — тест.

| Код | Случай | Правило | Где ловится |
|---|---|---|---|
| К1 | строка без происхождения (нет системы, класса, загрузки или времени) | Я2 | схема: ограничение `not null`; загрузчик |
| К2 | число без периода, источника, статуса или даты съёма | Я2 | валидатор числа |
| К3 | дубль ключа сущности | Я1 | схема: первичный ключ; уровень 1 |
| К4 | сделка без контакта | Я4 | схема: внешний ключ; уровень 1 |
| К5 | событие позже времени загрузки (визит, звонок, изменение из будущего) | Я3 | уровень 1 |
| К6 | телефон или почта открытым текстом в колонке фактов, кроме хэша; свободный текст длиннее 200 знаков; номер вне белого списка линий компании (в значении источника до `raw` — замена меткой «К6:скрыто», не отказ) | Я6 | проверка перед записью |
| К7 | сумма или доля чисел разных съёмов, разных ступеней или кабинетов без объявленного правила сложения | Я4, Я9 | арифметика числа |
| К8 | запись через агентский интерфейс | Я11 | интерфейс: соединение только на чтение; разбор запроса |
| К9 | модель читает `raw` мимо `facts`; имя поставщика или его технического поля в схеме или модели | Я5 | тест границы |
| К10 | запрос загрузчика к эндпоинту вне белого списка | Я7 | загрузчик — до отправки |
| К11 | миграция удаляет непустую таблицу фактов; осознанное удаление не объявлено в файле миграции | Я3 | исполнитель миграций — до применения |

### 10. Интерфейс потребителей

| Потребитель | Интерфейс | Что получает |
|---|---|---|
| Агент (любой чат) | команда `ask`: вопрос или SQL, только чтение, лимит строк; позже — протокол инструментов только на чтение | число по контракту раздела 4 плюс «чего не хватает» |
| Внешняя система-потребитель (движок гипотез, отчёты, конвейеры) | свой адаптер к опубликованным числам — файлу публикации (снимок на дату съёма, только агрегаты, без строк фактов и идентификаторов клиентов) или таблицам `metrics.*`; кода ядра не импортирует | те же канонические метрики; совпадение полей числа — контрактный тест адаптера на стороне потребителя |
| Люди | экспорт опубликованных таблиц; на сервере — инструмент BI по выбору инстанса | таблица с известными ответами |

Правила ответа, общие с речевой аналитикой: доказательства строит код, агент называет
идентификаторы найденных строк, ссылку собирает код; при малой базе — «предварительно»;
причинные формулировки запрещены; молчаливое допущение запрещено — подставленный период, кабинет
или поток показывается в ответе.

## Способ проверки

- **Гейт** запускается одной командой из репозитория инстанса и печатает воронку: источники →
  загрузка → модели → мосты → известные ответы → ПДн → секреты. Каждая непройденная проверка
  помечена уровнем и кодом красного случая. Код 0 — только при чистом прогоне.
- **Файл известных ответов** инстанса обязателен: метрика, период, кабинет, значение, откуда,
  дата съёма. Тест воспроизводит каждый ответ из фактов; расхождение — стоп.
- **Тест границы**: список запрещённых имён (сервисы, технические поля) из конфигурации
  инстанса; поиск по `schema` и `models` пуст.
- **Контрактные тесты** схемы и моделей проходят на файловой и серверной СУБД одним кодом (Я10).
- **Красные случаи**: по тесту на каждый код К1–К11; тест подсовывает ложь и ждёт код ≠ 0 с
  номером правила.
- **Трассировка**: у любого числа наружу видны период, источник, статус, дата съёма; повторный
  запрос даёт то же число.
- Перед словом «готово» — зелёный гейт, не описание проделанного.

## Исключения

- Цитаты диалогов, сырые тексты, записи — остаются в системах-источниках; ядро берёт только
  агрегаты класса F.
- Снимки агрегатов допустимы только в `snapshot_number` — чужие для мостов и известных ответов, свои
  для ответа на прошлую дату; не как основание новых метрик.
- Сложение по кабинетам и периодам — только для метрик с доказанным дедупом, объявленных в
  конфигурации инстанса со ссылкой на проверку.
- Инстанс вправе не хранить хэши ПДн; тогда связь звонок ↔ контакт не строится и публикуется
  как «нет данных», не как ноль.
- Пока живёт прежняя система правды, ядро грузит из неё сущности как из любого источника; её
  агрегаты — мост, не истина. Переключение потребителей на ядро — после мостов с доказательством.
