# ADR-0002 — Числа на дату: снимки своих чисел и публикация файлом

- **Статус:** Accepted (решение владельца 16.09.2026 в первом инстансе; перенесено в канон 28.09.2026)
- **Дата:** 2026-09-28

## Контекст

Источники дописывают данные задним числом: визиты и деньги прошлого месяца меняются неделями. Пересчёт
прошлого на сегодняшних фактах даёт другое число, чем то, на котором принимали решение (пример первого
инстанса: визиты одного месяца в трёх съёмах дали три разных числа). Стандарт от 14.09 разрешал в
`snapshot_number` только агрегаты чужих систем для мостов и известных ответов.

Второе: потребителю (движку гипотез, отчётам) нужен доступ к числам без доступа к базе и без зависимостей
ядра — база живёт на сервере компании, потребитель может быть в другом контуре.

## Решение

1. `snapshot_number` хранит и **собственные числа ядра** на каждую дату съёма: каждый прогон сохраняет числа
   периодов известных ответов и последних месяцев; снимки копятся только вперёд.
2. Метрика на прошлую дату читает снимок того дня; снимка нет — отказ К2. Новые метрики на снимках не
   строятся (Я1).
3. Потребитель читает **файл публикации**: контракт числа (раздел 4 стандарта), снимок на дату съёма, только
   агрегаты — без строк фактов и идентификаторов клиентов. Таблицы `metrics.*` остаются допустимым
   интерфейсом для потребителя с доступом к базе.

## Рассмотренные альтернативы

- **Версионировать факты** (история каждой строки, запрос «как было на дату» по фактам). Точнее, но дороже
  по объёму и сложности моделей. Отложено: снимков чисел хватает на вопросы решений.
- **Пересчитывать прошлое каждый раз.** Отклонено: число решения не воспроизводится.
- **Потребитель ходит в базу.** Отклонено: доступ к серверу компании и зависимости ядра у каждого
  потребителя.

## Последствия

- Известный ответ, снятый на другую дату, сверяется по допуску моста, вывод печатает обе даты; свои снимки
  сверяются точно и хранятся неокруглёнными.
- Потеря снимков — потеря истории решений: снимки входят в резервную копию.
