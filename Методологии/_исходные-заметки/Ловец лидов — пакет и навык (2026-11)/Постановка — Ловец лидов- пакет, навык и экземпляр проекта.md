# Постановка — Ловец лидов: пакет, навык и экземпляр проекта

Автор: Claude по словам Дмитрия в чате 21.11.2026. Методология — [Методология — Подбор лидов в открытых
сообществах (ловец лидов)](<../../Методология — Подбор лидов в открытых сообществах (ловец лидов).md>), её этапы
0–8, стоп-правила аккаунта и раздел «Касание» не повторяются здесь, а исполняются кодом.
Решение владельца: **принята 21.11.2026**, ответы на вопросы раздела 6 — по умолчанию («Принято, по умолчанию
подходит. Делай»).

## 1. Проблема

Ловец лидов работает в одном контуре: скрипты Telethon с зашитыми путями, одна пара ключей, одна сессия. Для
другого проекта его приходится копировать и переписывать пути; запасные ключи и аккаунты подключить некуда.
21.11 ключи второй пары лежали в другом файле секретов, и рабочий механизм их не видел.

Слова Дмитрия: «для каждого проекта свои ключи и папки», «когда я добавляю новые ключи — чтобы они либо
заменялись, если с теми что-то случится, чтобы это работало», «перенести в базу знаний, скорее всего как навык:
нужно будет только переменные менять или добавлять новые».

## 2. Нужный результат

Новый проект подключается к ловцу лидов одной командой навыка: появляется экземпляр со своим профилем, папками
данных и списком аккаунтов. Новая пара ключей добавляется строками в файл секретов проекта и номером в профиле,
без правки кода. Команда статуса показывает по каждому номеру: приняты ли ключи, есть ли вход, жива ли сессия.

## 4. Спецификация

### 4.1. Три слоя

1. **Пакет канона `lead_catcher`** — `_Движок/Пакеты/lead_catcher/`, код нейтрален (ADR-0003): ни имён проектов,
   ни путей, ни ключей. Читает профиль экземпляра. Команды: `status`, `login N`, `check N`,
   `find-chats`, `search-groups`, `read-sample`, `use N`. Общие части: аккаунт по номеру, прокси, обезличивание
   текста, журнал стоп-сигналов, темп запросов.
2. **Навык `lead-catcher`** — `_Движок/Исходники скиллов/lead-catcher/`, ссылкой в навыки агента. Подключает
   проект (`onboard`: профиль, папки, `.gitignore`), ведёт этапы методологии, знает стоп-правила, называет цену
   разметки до прогона, переносы между версиями профиля.
3. **Экземпляр проекта** — папка `lead_catcher_instance/` в репозитории проекта. В git — профиль и данные без ПДн;
   секреты и сессии — вне git, в месте, которое задаёт профиль.

### 4.2. Профиль экземпляра (`profile.yaml`, без секретов)

```yaml
schema: 1
secrets_env: "<путь к .env проекта>"
sessions_dir: "<папка вне git>"
proxy_env: [TG_READER_PROXY_URL, HTTP_PROXY]      # первый заданный выигрывает; у аккаунта может быть свой
active: 2                                          # какой номер читает сейчас
accounts:
  1: {api_id: TG_API_MAIN_KEY,   api_hash: TG_API_MAIN_SECRET,   session: tg_reader_1, proxy: null}
  2: {api_id: TG_API_MAIN_KEY_2, api_hash: TG_API_MAIN_SECRET_2, session: tg_reader_2, proxy: null}
data_dir: "data/"
allowed_chats: "allowed_chats.txt"
questions: "вопросы.json"
pace: {seconds_between_requests: 3, messages_per_day_to_model: 500}
```

В профиле — только **имена** переменных; значения читает код из `secrets_env` и никогда не печатает.

### 4.3. Аккаунты и замена ключей

- Номер = пара ключей + своя сессия + свой прокси (необязательно). Новый номер: две строки в `.env`, строка в
  `accounts`, затем `login N` — код вводит человек в терминале.
- `accounts status` по каждому номеру: ключи приняты (QR-проба без входа), сессия есть, сессия жива
  (`get_me` без печати номера), последний стоп-сигнал. Печатает только номера и статусы.
- **Переключение — по команде человека** (`use N`), не само. Стоп-сигнал (PeerFlood, FloodWait дольше 5 минут,
  бан, отозванная сессия, жалоба админа) останавливает сбор, пишет причину в журнал и называет готовые номера.
  Почему не автоматически: переход на следующий аккаунт после ограничения — обход ограничений Telegram, за который
  блокируют связку аккаунтов; методология требует возобновления только решением человека.
- Сессия привязана к номеру: ключи одного номера с сессией другого не смешиваются.

### 4.4. Ограничения

Только чтение: ни сообщений, ни реакций, ни вступлений без отдельного «да» на конкретный чат. Персональные данные
отрезаются кодом до записи и до модели; в отчётах — «житель», ссылка, текст без телефона. Файл сессии и ключи —
секреты: вне git и облака. Платная разметка — цена до прогона.

## 5. Критерии приёмки

1. В пакете нет путей, имён и ключей проектов (проверка `grep` по тестам пакета).
2. Экземпляр Бризекса: `accounts status` показывает номера 1 и 2 с «ключи приняты»; секреты в выводе не
   встречаются (тест подставляет известные значения и ищет их в выводе).
3. Номер 3 добавлен только строками `.env` и профиля — без правки кода; `status` его видит.
4. Стоп-сигнал в тесте (подменённая ошибка) останавливает сбор и не переключает номер сам.
5. После входа по номеру 2 (код вводит Дмитрий) `check 2` — «сессия жива»; пробное чтение одного разрешённого
   чата пишет данные без телефонов и ников.
6. Навык подключает пустой тестовый проект `onboard` → профиль и папки созданы, `.gitignore` закрывает сессии.
7. Рабочий ловец «Учебного центра» после переноса на пакет даёт тот же результат на том же чате (до/после).

## 7. План (после «принята»)

1. Пакет: вынести общие части из рабочих скриптов в `lead_catcher` с профилем; тесты на критерии 1–4.
2. Навык `lead-catcher`: `onboard`, статус, вход, этапы, стоп-правила; ссылка в навыки агента.
3. Экземпляр Бризекса: профиль, папки, `accounts status` (критерии 2–3).
4. Вход по паре 2 — Дмитрий; `check 2`, пробное чтение одного чата (критерий 5).
5. Приёмка чистым агентом (`maker-checker`), строка CHANGELOG канона, пакет в `_manifest` пакетов.
6. Перенос «Учебного центра» — отдельным шагом, сверка до/после (критерий 7).

Что может сломаться: рабочий ловец — поэтому его не трогаем до шага 6. Самый рискованный шаг — вход по новой
паре: новый вход с нового приложения Telegram может проверить строже; делаем один раз, без повторов подряд.
Отброшено: автоматическая ротация аккаунтов (см. 4.3); второй движок на Bun (вопрос 2).
