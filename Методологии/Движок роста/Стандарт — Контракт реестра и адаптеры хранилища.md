# Стандарт — Контракт реестра и адаптеры хранилища

## Краткая суть

- Реестр — не одна таблица, а **семь связанных артефактов** с общим контрактом: карта
  источников, модель экономики, дерево цели, маршрут цикла, реестр гипотез, карта знаний
  о рынке, журнал решений.
- Канон описывает **поля и операции**; где они физически лежат — решает адаптер хранилища.
  При установке агент задаёт один вопрос: «где ведём реестр?» — с умолчанием в универсальном
  табличном процессоре.
- У гипотезы поля заполняются в **три момента**: при заведении, до запуска, после замера.
  Перевод в «в тесте» невозможен без владельца и порога.
- Каждый вывод цикла оставляет строку в карте знаний — так накапливается понимание рынка.
- ⛔ Ни один документ ядра не называет конкретный продукт хранилища или источника.

## Что нормируется

Слой 5 [методологии](<Методология — Движок роста (цикл, ворота, маршрутизатор).md>):
состав артефактов инстанса, схема реестра гипотез, статусы, операции и требования к адаптерам.

## Требования к результату

### 1. Семь артефактов инстанса

| Артефакт | Что хранит | Ритм | Кто пишет |
|---|---|---|---|
| **Карта источников** | классы, статусы, глубина, точки истины, ловушки ([стандарт](<Стандарт — Протокол обнаружения источников и глубина погружения.md>)) | установка, инкрементально | шаг 0 |
| **Модель экономики** | снимки по периодам: воронка, деньги, юнит; у каждого числа период, источник, статус; кросс-чеки; плечи; сценарии | месячно | шаг 2 |
| **Дерево цели** | цель → ветки → потолок ветки в единицах цели → привязанные гипотезы; разрыв между суммой потолков и целью виден | на цель | шаги 1, 3 |
| **Маршрут цикла** | шаги, классы данных на каждом, заменители, что пропущено и почему, ожидаемая уверенность | на цикл, **до** исполнения | маршрутизатор |
| **Реестр гипотез** | см. §2 | постоянно | шаги 6–10 |
| **Карта знаний о рынке** | утверждения о сегментах, работах, каналах, сезоне — `подтверждено / опровергнуто / открыто`, дата, источник, гипотеза-основание | после каждого вывода | шаг 10 |
| **Журнал решений** | что решили, почему, что убрали (вычитание), отброшенные альтернативы | на цикл | шаги 1, 10 |

Модель экономики держится **в том же хранилище**, что и реестр: эффект гипотезы считается
ссылкой на модель, а межкнижные ссылки хрупки.

### 2. Реестр гипотез — поля по моменту заполнения

| Момент | Поля |
|---|---|
| **заведение** | `id` · формулировка «если — то — потому что» · бизнес-задача · ветка дерева · рычаг модели · **единица действия** (сегмент / страница / блок / этап диалога) · факт-основание (период, источник, статус) · эффект в **единицах цели** · эффект в **₽** (из модели) · механика · статус |
| **до запуска** | **владелец** · зона (`своя` / `вне маркетинга → пакет`) · что именно меняем · дата старта · окно замера · главная метрика · ожидаемый N · **порог ± заранее** · критерий провала · дата отложенного замера · RAT-допущения с приоритетом |
| **после** | факт метрики · попал ли в порог · решение `scale / iterate / kill / research` · вывод одной строкой · **что узнали о рынке** → карта знаний · что убрали → журнал решений |

Эффект в единицах цели обязателен: гипотеза, у которой эффект выражен только деньгами,
не встаёт в дерево цели и не складывается с соседями.

### 3. Статусы

Основной маршрут: `идея → research → candidate → в тесте → замер → вывод → архив`.

Дополнительные: `ждёт владельца` (пакет вне маркетинга передан, ответа нет) ·
`blocked: нет данных` (с указанием класса источника) · `отложенный замер` (с датой).

Переходы:

- `идея → research` — свободно.
- `research → candidate` — требуется факт-основание со статусом и единица действия.
- `candidate → в тесте` — требуются владелец, порог, окно, метрика, RAT.
- `в тесте → замер → вывод` — замер только по объявленному порогу; вывод — одно из четырёх решений.
- `iterate` возвращает в `candidate` с новой формулировкой, не перезаписывая старую.

### 4. Шесть операций контракта хранилища

Адаптер обязан реализовать все шесть; иначе он не адаптер этого контракта:

`создать запись · прочитать по фильтру · обновить статус · добавить замер · связать с деревом · экспортировать снимок`

Операции идемпотентны по `id`. Запись без обязательных полей момента отвергается адаптером
(валидатор — часть контракта, а не промпта). Успех отчитывается количеством записанных строк,
не словом «готово».

### 5. Адаптеры хранилища

| Адаптер | Когда | Требования |
|---|---|---|
| **Универсальный табличный процессор** (умолчание) | любой проект, команда работает в таблицах | листы по артефактам; формулы модели живы; валидация списками для статусов |
| Корпоративный табличный процессор компании | если у компании свой, в котором живёт команда | тот же контракт; выбирается в конфигурации инстанса |
| **Реляционная база** (встроенная файловая → серверная СУБД) | серверный режим; объём или история переросли таблицу | миграции; гейт целостности; экспорт снимка в таблицу для людей |
| **Файл Markdown** | аварийный или офлайн режим | всегда доступен; формул нет — модель считается скриптом |

Смена адаптера не меняет ни одного документа ядра: переезжают данные через `экспортировать
снимок → создать запись`.

## Способ проверки

- Валидатор реестра: запись каждого момента проходит проверку обязательных полей; статус
  `в тесте` при пустом пороге невозможен.
- Гейт инстанса: все семь артефактов существуют; у каждой гипотезы в `в тесте` есть владелец;
  у каждого `вывод` есть строка в карте знаний.
- Ревью: канон не содержит имён продуктов хранилища (`grep` по каталогу ядра).

## Исключения

- Если компания не имеет права держать данные во внешнем облаке — адаптер реляционной базы
  становится умолчанием; фиксируется в конфигурации инстанса.
- Карта знаний ведётся даже при `kill`: опровергнутое утверждение о рынке — тоже знание.
