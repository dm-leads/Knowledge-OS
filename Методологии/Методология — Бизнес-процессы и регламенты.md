# Методология — Бизнес-процессы и регламенты

## Краткая суть

- **Процесс — объект управления, а не схема**: повторяемая работа с результатом для конкретного потребителя плюс
  управление ею — план, выполнение, учёт, контроль, решение. Хуже всего обычно описано звено «решение».
- **Регламент без показателей — не управление.** Регламент задаёт способ, показатель делает процесс управляемым.
- **Описывать только то, что будут улучшать или регламентировать.** Сначала дерево процессов таблицей, схемы — только
  на уровне операций. Тотальное описание уходит «в корзину».
- **У процесса один владелец** с ресурсами и полномочиями; границы — события; результат готов, когда потребитель его
  принял.
- **Документ пишет тот, кто отвечает за исполнение, и проверяет его новичок**: человек «с улицы» выполняет работу по
  тексту без пояснений. Это же — тест инструкции для ИИ-агента с чистым контекстом.
- **Проблема — сигнал менять систему, а не искать виноватого**: устранить последствия, изменить причину, записать
  изменение в метод.
- **Где не окупается**: среда меняется быстрее, чем процесс успевает стабилизироваться; нет участия первого лица; редкие
  и творческие задачи.

Пометки: **Репин** (обе книги), **Карпентер** — правило из книги; **[вывод]** — наш перенос. Адреса страниц — в
выжимке `_исходные-заметки\Книги — управление (2026-11)\`.

## 1. Где регламентировать, а где нет

**Экономика регламентации** (Репин): τ — время, за которое процесс приводят к стабильному состоянию; T — время до
существенного изменения среды. Окупается, если затраты на оптимизацию и управление плюс операционные затраты
стабильного процесса за T меньше операционных затрат нестабильного.

Отношение τ/T — **предварительный фильтр, а не решение** **[вывод]**: решение по конкретному процессу — по его
экономике и рискам; устойчивые участки выделяются отдельно даже в меняющейся среде.

| Среда | Ориентир |
|---|---|
| Стабильная (τ много меньше T) | регламентация скорее окупится — проверить расчётом |
| Меняется медленно (τ < T) | окупится позже |
| Меняется так же быстро (τ ≈ T) | решают скорость внедрения и гибкость; регламентировать устойчивое ядро |
| Меняется быстрее (τ > T) | эффекта может не быть; регламентировать «процессы изменений» (запуск направления, проект) и устойчивые участки |

**Не писать метод** для редких и нестандартных ситуаций — хватит цели и принципов компании (Карпентер); 10 %
нетипового — сразу эскалировать уровнем выше (Репин). **Не начинать** без участия первого лица (Репин). Творческая
работа — регламентировать только нетворческую часть вокруг неё.

## 2. Какие документы нужны компании на 5–50 человек

Минимальный набор **[вывод]**, собран из обеих книг:

1. **Цель компании** — 1 страница; пишет руководитель лично: кто мы, что делаем и для кого, от чего зависит успех,
   кто за что отвечает и кто кого заменяет (Карпентер).
2. **Принципы работы** — 2–4 страницы: как решать в нестандартной ситуации. Примеры Карпентера: проблема — повод
   улучшить систему; повторяющуюся проблему решает система, для редкой метод не пишем; «просто не делайте этого» —
   закрыть лишнее; о задержке сообщать заранее; задача руководителя — не делать работу, а строить систему.
3. **Дерево процессов** — таблица на 3 уровня: процесс, владелец, участники, начальное и конечное событие, вход,
   выход, потребитель (Репин). Верхний уровень — до 10–12 процессов.
4. **Метод (регламент) на каждый повторяющийся проблемный процесс** — 1–3 страницы: таблица операций и ветки
   отклонений (раздел 3).
5. **Карточка роли** — обязанности по периодичности, ответственность, права, кому что передаёт (раздел 4).
6. **3–5 показателей на процесс** с паспортом и еженедельный обзор (раздел 5).
7. **Журнал отклонений** с правилом «потери против затрат» (раздел 6).
8. **Дата пересмотра и ответственный** у каждого документа.

Не нужны: отдел оргразвития, среда моделирования, многоуровневые нотации, методика проекта на 100 страниц,
сертификация. Для управления небольшой компанией достаточно одного «регламента управления» для руководителя (Репин).

**Порядок** **[вывод]**, наша сборка из обеих книг: цель → принципы → дерево процессов → самый проблемный процесс →
**результат, исходные показатели и критерий успеха до изменения** → анализ и правка процесса → метод → тест новичком
→ пилот и проверка эффекта против исходных показателей → закрепить → следующий процесс. Опора: у Карпентера —
начинать с самого проблемного; у Репина — показатели раньше регламентации, сначала оптимизация, потом регламент. Документирование — первым делом в дне, 1–2 часа; «на досуге» — провал через
неделю (Карпентер).

## 3. Процесс: границы, описание, регламент

**Границы — события**, а не действия: «поступило распоряжение», «заявка зарегистрирована в CRM», «прошло 2 рабочих дня
после заказа». «Отправлено» не равно «получено». Начальное и конечное событие согласуют владельцы соседних процессов
одной формулировкой (Репин).

**Вход и выход.** У каждого выхода есть потребитель, иначе процесс работает вхолостую; требования к выходу задаёт
потребитель, к входу — получатель. Ни один вход не остаётся без ответственного. Требования к результату — через
**операционное определение**: эталон, бинарная проверка или образец, по которым двое людей одинаково решат, принят ли
результат («отливки приемлемо чистые» — не определение) (Репин).

**Проверка описания по реальной работе** (Репин): документ, который исполнитель или агент выполняет без вопросов,
может описывать не тот процесс. Перед утверждением — входы и выходы подтверждены обеими сторонами передачи; описание
проверено на реальном случае; факты отделены от предложений; владелец и исполнители прочитали и подтвердили. Для
совместного описания — общий справочник названий ролей, документов и систем, иначе один объект получает разные имена.

**Описание.** Нотация — средство; для регламента — простая схема без обучения, информация в таблице и тексте; BPMN —
только под автоматизацию (Репин). Правила схемы: 3–12 операций на лист; операция — «глагол + существительное»;
стрелки и события конкретны; на схеме обязательно место руководителя (где он планирует, проверяет, решает) и ветки
отклонений — плохой вход, брак, нештатная ситуация, учёт факта (Репин).

**Регламент процесса** — разделы (Репин, упрощено):

1. Назначение; кто обязан знать (должности и роли, включая агентов).
2. Владелец, начальное событие, результат, сроки.
3. Схема.
4. Таблица операций: №, операция, исполнитель, начальное событие, входящие документы, содержание, результат,
   исходящие документы, срок.
5. Действия при отклонениях: что исполнитель решает сам, что передаёт владельцу.
6. Цели и показатели: показатель, единица, способ расчёта, периодичность.
7. Методы контроля: что проверяем, кто, как часто, где запись.
8. Порядок изменений: срок пересмотра, ответственный.

**Метод работы исполнителя** (Карпентер): заголовок по теме («Заявка на продажу»), краткое описание (предмет, цель,
кому, когда применять), нумерованные шаги, «никаких предположений, каждый шаг очевиден».

**Восемь правил написания** (Репин):

1. Коротко и понятно исполнителю; лучше всего пишет сам исполнитель по шаблону.
2. Без возвратной частицы «-ся» («передаётся», «формируется») — всегда кто делает.
3. Без неоднозначности; документ доступен на рабочем месте; смежные документы не противоречат.
4. Не экономить на согласовании со смежниками.
5. Утверждает владелец или его прямой руководитель, а не «все наверху».
6. Не утверждать документ, не согласованный с соисполнителями, — иначе «тихий саботаж».
7. **Тест: новичок после прочтения выполняет работу без пояснений**; иначе менять документ.
8. Вводить с обучением, а не рассылкой.

**Скорость изменений**: мелкая правка, которая явно улучшает, — сразу, с уведомлением затронутых (Карпентер, «правка
за 5 минут»); новый или сквозной документ — согласование со смежниками за 3, максимум 4 итерации и пилот (Репин).
Вопрос исполнителя к автору метода — признак, что метод надо улучшить (Карпентер).

**Версии** **[вывод]**, по Карпентеру и Репину, с поправкой на git: мелкая правка — уточнение формулировки без
изменения прав, приёмки и контроля; такие изменения — только через согласование и тест. У документа видны действующая
версия и дата вступления в силу; при новой версии — ознакомление людей (git его не фиксирует — отметка в журнале
проекта) и **обновление источника, из которого агенты берут инструкции**; старая версия исключается из исполнения и
уходит в архив. Агент, исполняющий отменённую инструкцию, — тот же сбой, что устаревший экземпляр на рабочем месте.

## 4. Владелец и роли

**Владелец процесса** (Репин) — тот, кто определяет состав и порядок работ, распоряжается ресурсами и информацией,
организует сбор данных о ходе и отвечает за улучшение. Один на процесс; обычно руководитель подразделения, отдельная
иерархия владельцев не создаётся. **В малой компании владелец процессов — собственник или директор.** Его работа —
планировать, смотреть показатели, анализировать, решать.

**Сквозной процесс** (участники из разных подразделений) — масштаб такой, чтобы один руководитель управлял без новой
иерархии. Практичный способ: владелец мониторит показатели и исполнение регламентов, при отклонении решает с
участниками или эскалирует (Репин). Большинство проблем — на границах между подразделениями.

**Матрица О/У/И** — кто отвечает, участвует, информируется; в каждой строке одна «О». Раздел «передаёт / получает»: у
смежников формулировки совпадают дословно, при несогласии решает общий руководитель (Репин).

**Карточка роли** (должностная инструкция по Репину): подчинённость и замещающий; обязанности — операции процессов,
сгруппированные по периодичности (ежедневно, еженедельно, ежемесячно, по событию) с ролью в процессе; отвечает за /
участвует в (по матрице); права — какие вопросы решает сам, какие ресурсы и данные доступны; что получает и кому
передаёт; показатели; график («до 5 числа — отчёт по форме…»).

**Делегирование через регламент**: типовые решения по типовым отклонениям записаны в инструкции исполнителя — он
действует сам; нетиповое и критическое — сразу владельцу (Репин). «Если подписываете документ автоматически после
проверки подчинённым — отдайте ему право подписи».

## 5. Управление процессом по показателям

**Четыре категории показателей** (Репин): результат, затраты ресурсов, время, дефекты. Одна категория без других ведёт к
«псевдооптимизации»: снизили затраты — выросли сроки, ускорили — выросли дефекты.

**Паспорт показателя**: название; кто получает — **если получатель не принимает по нему решений, показатель убрать
из его отчёта** (прекращать ли расчёт и хранение данных — отдельное решение: показатель может быть нужен другому
уровню или для проверки); границы зон и направление улучшения; действия при переходе в жёлтую и красную зону;
владелец целевого значения; кто считает; периодичность и срок; определение; единица (одна во всех документах);
формула и источники; форма отчёта. Методику не менять, иначе нельзя сравнить с прошлым (Репин). Совпадает со
[Стандартом консистентности метрик](<Стандарт — Консистентность метрик.md>).

**Зоны**: зелёная — не реагировать на каждое колебание; приближение к жёлтой — разобрать причины; красная — срочная
коррекция, возможна остановка процесса (Репин). Границы зон задаются в паспорте показателя от требований потребителя,
нормативов и опыта, чтобы два владельца назначили их одинаково.

**Ритм владельца** (Репин, контуры): ежедневно — мониторинг и оперативные решения; еженедельно — разбор недели и
выборочная проверка входов и выходов; ежемесячно — справка владельца (не больше 10–12 показателей, отклонения и
меры, претензии к другим процессам) и решения руководителя с исполнителем и сроком. Между встречами кто-то
контролирует исполнение решений — иначе цикл «план — выполнение — проверка — решение» разрывается.

**Самопроверка процесса** (Репин, 42 требования по 0/1/2 балла) — сокращённо: один владелец с полномочиями; границы
определены; документы есть **и выполняются**; входы, выходы, ресурсы определены и закреплены; показатели **существуют
и используются**; критерии нештатной ситуации есть и используются; корректирующие действия делаются и проверяются.
Это сокращённый список для самопроверки; полный — 42 требования в выжимке (Репин-ПП, стр. 265–266, 368–372), оценка =
сумма баллов ÷ 84. Пороги автора (до 0,3 — наводить порядок, 0,3–0,7 — перестраивать, 0,7–0,95 — автоматизировать
управление) — без данных; оценка **не является допуском к автоматизации**, только ориентиром.

## 6. Отклонения и улучшения

**Двухшаговое правило** (Карпентер): устранить последствия → найти подсистему-причину и изменить её, записать изменение
в метод. Ошибка при соблюдении метода — вина метода, а не человека. Санкции — только за нарушение актуального,
понятного и обученного стандарта **[вывод]** (Репин сам признаёт несправедливость штрафа за устаревший регламент).

**Выбор корректирующего действия по экономике** (Репин): оценить потери от отклонения → варианты мер и их цену →
если потери существенно ниже затрат — не делать и записать анализ → иначе план, ресурсы, выполнение, **проверка, что
причина устранена**. Последний шаг чаще всего забывают. Уточнения **[вывод]**: потери — ожидаемые за заданный период с
учётом повторения и тяжести, а не только уже понесённые; затраты — все затраты на меру. **Обязательные требования
(закон, безопасность людей, данные клиентов) экономическому фильтру не подлежат** — экономика выбирает только способ.
Инцидент без ущерба разбирается по худшему сценарию (Карпентер: отключение света → генератор и регулярная проверка).
Неопределённый риск — решение владельца с записанным обоснованием.

**Протокол отклонения** (Репин) — поля, которые стоит добавить в базу инцидентов проекта **[вывод]**: что, где, когда;
**аналогичные случаи**; причина; нужны ли меры (потери против затрат); меры — ответственный, срок; **проверка
эффективности — дата, способ, ответственный**; результат проверки.

**Убирать лишнее**: таблица «документ или отчёт — кто создаёт — кто использует»; отчёт, который никто не использует,
— убрать; вопрос к функции «что будет, если её исключить?» (Репин). Перед удалением документа — проверить, не
является ли он записью (свидетельством того, что произошло): записи хранятся по своим правилам, даже если к ним не
обращаются. «Просто не делайте этого» (Карпентер).

**Автоматизация — конечный этап делегирования** (Карпентер): сначала стабильный процесс, потом автомат. Кейс: ручную
оплату счетов отдали бухгалтеру — появились двойные платежи; автоплатёж через банк — 15 часов разово, дальше до 2
часов в месяц без ошибок.

## 7. Процессы с ИИ-агентами

В книгах агентов нет; ниже — перенос механик **[вывод]**, у каждой есть опора в книгах.

| Механика книги | Для агента |
|---|---|
| Тест новичком «с улицы» | Инструкцию проверяет агент с чистым контекстом: выполняет задачу по документу без вопросов; вопрос агента — повод улучшить документ |
| Должностная инструкция | Карточка роли агента: что делает и с какой периодичностью, какие решения принимает сам, к каким данным и системам доступ, что получает и кому передаёт, показатели |
| Инструкция рабочего места с действиями при отклонениях | Инструкция агенту: вход, порядок, требования к результату, **ветки — плохой вход, ошибка, нештатная ситуация, эскалация владельцу**, что записать |
| Типовое решение — исполнителю, нетиповое — вверх | Типовые отклонения агент решает по инструкции; нетиповые — к человеку-владельцу. Показатель процесса — число эскалаций |
| Место руководителя на схеме | В процессе с агентами явно указано, где человек планирует, проверяет и решает |
| Результат готов, когда потребитель принял | Агент сам доставляет результат и уведомляет; «сделал» — не «готово» |
| Верификация, валидация и специальный процесс | Свойства результата агента, которые проверяются сразу (расчёты, источники, полнота, соответствие заданию), проверяются в каждом результате; пригодность для задачи потребителя — отдельно; там, где результат полностью проверить нельзя, дополнительно валидируется сам процесс — утверждённая инструкция, выборочная проверка человеком, записи, пересмотр |
| Ошибки накапливаются по шагам | В конвейере из независимых шагов вероятность, что все шаги без ошибки, — произведение вероятностей успеха шагов: чем длиннее цепочка, тем ниже. Отсюда контроль на стыках и независимый проверяющий (навык `maker-checker`, вторая модель) — снижают риск, но не гарантируют безошибочности |
| Показатель без получателя убрать | Отчёты агента, которые никто не читает, — потери |
| Доля автоматизированных функций = автоматизированные функции / все функции | Показатель охвата автоматизацией при едином уровне выделения функций; это не доля труда агентов и не сэкономленное время — их, как и время людей на проверку, мерить отдельно. Автоматизировать после стабилизации процесса |

Правила [модели риска автономии](<Методология — Модель риска автономии агента.md>) (что агенту можно без человека)
остаются в силе: этот раздел отвечает, как описать процесс с агентом, а не что ему разрешено.

## Чего методология не покрывает

- Нотации для автоматизации (BPMN-исполнение), системы управления процессами, сертификацию по ИСО.
- Процессы отдела продаж — источник готовит владелец.
- Юридическую силу документов (приказы, трудовое право).

## Анти-паттерны

1. Описать всё сразу и подробно.
2. Описывают аналитики без руководителей — в моделях нет управления и отклонений.
3. Регламент без показателей и без пересмотра.
4. Утвердить документ без соисполнителей; 26–40 версий согласования.
5. Методы для редких проблем.
6. Искать виноватого вместо правки метода.
7. Делегировать рутину человеку или агенту без контроля и показателя.
8. Агрегированный показатель с весами, который повторяет один доминирующий.
