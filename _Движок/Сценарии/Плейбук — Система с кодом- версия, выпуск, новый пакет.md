# Плейбук — Система с кодом: версия, выпуск, новый пакет

> id: `code-system`. Решение, на котором стоит сценарий, —
> [ADR-0003](<../0 — System Docs/ADR-log/0003-code-systems-source-in-canon-releases-in-projects.md>).

## Краткая суть

- Код системы правится **только в каноне** — `_Движок/Пакеты/<пакет>/`. В проекте компании лежит выпуск с
  паспортом; руками он не правится, тест краснеет.
- Проект на этом устройстве подключает пакет **ссылкой** (`pip install -e`), компания, которой код нужен в своём
  репозитории и на своём сервере, получает **выпуск** (`kos_release.py issue`).
- Новая версия: правка и тесты в каноне → номер в `pyproject.toml` → CHANGELOG → коммит → метка
  `<пакет>-v<версия>` → выпуск в проекты, где он есть.
- Новый пакет из первого инстанса: нейтральный код — в канон, всё про компанию — в каталог инстанса рядом с
  выпуском; граница проверяется тестом пакета.
- Ключ `--package` у `kos_release.py` — **путь к папке пакета**, не имя.

> Для быстрого знакомства человеку может хватить блока выше.
> Ниже начинается полный каноничный текст документа.
> Для агентов, правок, анализа, ревью и разрешения расхождений обязателен полный текст.

## Обозначения

- `<канон>` — `D:\Knowledge-OS`.
- `<папка пакета>` — `<канон>\_Движок\Пакеты\<пакет>` (там `pyproject.toml`).
- `<выпуск>` — каталог кода пакета в проекте компании (у первого инстанса —
  `…\AI Digital Marketing — Growth\Скрипты\growth_engine`).
- `kos_release` — `py -3 "<канон>\_Движок\Инструменты\kos_release.py"`.

## 1. Подключить пакет к проекту

Сначала выбрать способ:

| Вопрос | Да | Нет |
|---|---|---|
| Код обязан лежать в репозитории проекта (сервер компании ставится из него, коллеги без канона)? | Выпуск | Ссылка |

**Ссылка:** `py -3 -m pip install -e "<папка пакета>" --no-deps --no-build-isolation` (зависимости ставятся
отдельно, если их нет). Правка в каноне сразу видна проекту. В паспорте проекта (`CLAUDE.md`, раздел о проекте)
— строка «система <пакет>: ссылкой на канон».

**Выпуск:**
1. `git status` в проекте; чужие незакоммиченные правки не трогать.
2. `kos_release issue --package "<папка пакета>" --into "<выпуск>"`. Если в `<выпуск>` уже лежит код без паспорта
   (первый выпуск поверх перенесённого кода) — ключ `--first`, и только после сверки, что код совпадает с каноном.
3. Рядом с выпуском — каталог инстанса компании (конфигурация, данные, модули и тесты компании).
4. Тесты проекта, включая тест паспорта выпуска.
5. Коммит проекта своими путями; публикация — по правилам проекта.

⚠️ Режим ссылки и выпуск на одном устройстве: из папки, где лежит выпуск, Python импортирует выпуск, из других
папок — канон. Проверять, что именно импортировано: `py -3 -c "import <пакет>; print(<пакет>.__file__)"`.

## 2. Выпустить новую версию пакета

1. **Правка в каноне**, тест сначала. Тесты пакета: из `<папка пакета>` — `py -3 -m pytest <пакет>/tests`.
   Тест границы (`test_package_boundary.py` и аналоги) должен остаться зелёным: в коде пакета нет имён, данных и
   конфигурации компаний.
2. **Номер версии** в `pyproject.toml`:
   - исправление без изменения поведения для пользователя — третья цифра (`1.0.0 → 1.0.1`);
   - новая возможность, старые вызовы работают — вторая (`1.0.1 → 1.1.0`);
   - меняются команды, формат хранения или конфигурации инстанса — первая (`1.1.0 → 2.0.0`), плюс в CHANGELOG
     — что сделать в каждом инстансе.
3. **CHANGELOG движка** — строка: пакет, версия, что изменилось.
4. **Коммит канона** своими путями.
5. **Метка:** `git -C "<канон>" tag -a <пакет>-v<версия> -m "<пакет> <версия> — <суть>"`. Метка ставится на
   коммит, с которого делаются выпуски.
6. **Push канона** — после изменений разрешён (решение владельца 28.09.2026), с метками:
   `git -C "<канон>" push --follow-tags`. Перед ним — проверка новых файлов на секреты и ПДн.

## 3. Обновить выпуск в проекте компании

1. Отставание: `kos_release check --into "<выпуск>" --package "<папка пакета>"`. Вывод «выпуск свежий» — делать
   нечего; «отстаёт на N коммитов» — обновить.
2. Если `check` нашёл изменённые, пропавшие или лишние файлы — **стоп**: кто-то правил выпуск руками. Правку
   перенести в канон (раздел 2), затем обновлять. Поверх ручных правок `issue` не ложится.
3. `kos_release issue --package "<папка пакета>" --into "<выпуск>"`.
4. Тесты проекта: пакет и инстанс. Для мажорной версии — шаги из CHANGELOG в инстансе.
5. Коммит проекта: `update: <пакет> <версия> из канона (<короткий коммит канона>)`. Публикация — по правилам
   проекта; сервер компании ставится из репозитория компании.

## 4. Завести новый пакет из первого инстанса

Системы растут внутри проектов; в канон переходят, когда код стабилизировался.

1. **Разметка.** Пройти код инстанса и разделить на два списка: нейтральное ядро (формулы, хранилища, команды,
   проверки) и привязанное к компании (имена, идентификаторы полей CRM, адреса, токены, пороги, данные, тесты на
   данных компании). Сомнительное — в инстанс.
2. **Пакет в каноне:** `_Движок/Пакеты/<пакет>/` с `pyproject.toml` (имя, версия `1.0.0`, зависимости) и
   каталогом `<пакет>/`. Скопировать нейтральное ядро; в инстансе компании переписать импорты на пакет.
3. **Тест границы в пакете:** грепом по коду пакета — ни одного имени компании, домена, идентификатора. Список
   запретов — в самом тесте. Переносимость утекает и через комментарии и строки документации: имя компании в них
   тоже запрещено, в пояснениях писать роль («CRM», «склад»), а не имя. Проверять ли в пояснениях имена
   поставщиков — решение пакета, записанное в строке документации теста (у `growth_engine` — не проверяются, у
   Ядра данных граница строже).
4. **Тест паспорта выпуска** — скопировать `tests/test_release_passport.py` из `growth_engine` (в каноне он
   пропускается, в выпуске проверяет паспорт).
5. Тесты пакета зелёные в каноне; манифест `_Движок/Пакеты/_manifest.md` — строка пакета; CHANGELOG; коммит;
   метка `<пакет>-v1.0.0`.
6. **Первый выпуск** в проект компании — `issue … --first` поверх перенесённого кода (раздел 1). Тесты проекта
   зелёные на выпуске + инстансе — пакет состоялся.
7. Методология системы — в `Методологии/` канона; ссылка на неё — в строке манифеста пакетов.

Очередь: Ядро данных — вторым пакетом, тем же порядком.

## Стоп-условия

- Тест границы красный — в пакет попало привязанное к компании; вернуть в инстанс.
- `check` показывает ручные правки выпуска — не выпускать, сначала перенести правку в канон.
- В `<выпуск>` лежит паспорт другого пакета — `issue` остановится сам; проверить путь.
- Канон с незакоммиченными правками пакета — `issue` не выпускает: выпуск делается только с коммита.
