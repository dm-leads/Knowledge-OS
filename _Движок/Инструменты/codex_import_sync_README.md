# Разовое восстановление импортированного чата Codex на Windows

В сборке Codex 26.928.1915.0 (app-server 0.159.0) обновление уже импортированного
Claude Code сеанса пропускается для `history_mode=paginated`. Штатный append
обращается к внутреннему чтению полной истории, которое отказывает этому режиму;
результат импорта остаётся пустым без зарегистрированной ошибки.

`codex_import_sync.py` проверяет обход на отдельной копии, сохраняет исходный
rollout и целевую строку metadata, согласует режим `legacy` в rollout и SQLite,
затем запускает штатный импорт для одного источника. ID чата сохраняется.
Исходные файлы Claude Code не изменяются. Старое содержимое после первой строки
сохраняется побайтно. Результат сравнивается с изолированным импортом, повторный
импорт проверяется на отсутствие дубликатов.

Перед `repair` полностью завершить desktop Codex и Codex CLI, приостановить
исходный сеанс Claude Code. Не открывать их до результата `completed` либо
разбора `stopped_requires_inspection`. Единственный worker. Файловая блокировка
защищает запись выбранного чата, но не заменяет это эксплуатационное условие.

Проверка выхода учитывает также `codex.exe` из расширения Codex в Cursor.
Если расширение работает, ожидание продолжится даже после закрытия desktop.
Текущий этап выводится в консоль; при ожидании каждые 15 секунд выводится
оставшееся время. Таймаут и Ctrl+C во время ожидания не меняют историю.
Предпочтительный сценарий пользователя — разовое обновление перед переносом
работы из Claude Code. Запрос в чате может запустить подготовленный worker,
но до применения обхода процессы Codex должны завершиться.

Аргументы: `--home <Codex home> --exe <native codex.exe> --thread <imported ID>
--output <NEW backup directory outside home>`. Команды:

- `probe`: только изолированные копии, исходник читается. Источник может
  меняться во время диагностики; несовпадение хешей прерывает проверку.
- `repair`: ждёт полного выхода Codex, затем проверяет копию и применяет обход.
- `arm`: скрыто запускает `repair`, возвращает PID и фактический статус отчёта.
- `recover`: с существующим output согласует SQL с узнаваемым по хешу rollout
  только при сбое переключения metadata до начала native import. Новые записи
  или изменённый ledger вызывают отказ. После начала import нужен ручной разбор.
  `recovered_metadata_consistency_import_pending` не означает импорт сообщений.

Отчёт `report.json` и резервная переписка содержат личные данные: хранить локально,
не добавлять в Git. При ошибке не удалять backup, не выполнять слепой откат.
Восстановление после сбоя процесса проверено синтетическими тестами; защита от
внезапного отключения питания не доказана.

Полный `repair` проверен на изолированной копии настоящего сеанса: 5908→6010
response items, повтор без дублей, совпадение всех payloads и сохранение старых
байтов. Настоящая переписка при проверке неизменна. Применение к оригиналу,
отображение в desktop UI и следующий прирост исходной истории — отдельные
этапы приёмки. Регулярную синхронизацию этот результат пока не подтверждает:
desktop может вновь мигрировать историю в paginated.

Проверка кода: `python -m unittest test_codex_import_sync -v` из этой папки.
