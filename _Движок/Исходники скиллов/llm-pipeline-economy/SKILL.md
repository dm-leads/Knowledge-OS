# Экономный конвейер с нейросетью

Навык для случаев, когда модель вызывается не один раз, а по сотням и тысячам записей. Там цена и надёжность решаются архитектурой, а не промптом. Решения — в этом порядке: каждое следующее дороже предыдущего.

## 1. Можно ли кодом

Если у текста повторяющийся формат (поля формы, номера, даты, суммы, адреса, заголовки разделов, шаблонные письма), начинай с регулярок и правил. Обычно они закрывают подавляющую часть записей бесплатно и одинаково при каждом запуске.

Модель подключай только к тому, что код разобрал неуверенно. Уверенность считает код, по наблюдаемым признакам: поле не найдено, значение вне ожидаемого диапазона, слишком короткий фрагмент, несколько кандидатов вместо одного.

```
текст → разбор кодом → оценка уверенности
                          ├─ уверенно → результат
                          └─ неуверенно → модель → проверка кодом → результат
```

Свободный текст без устойчивого формата (смысл разговора, тональность, причины отказа) — сразу модели, регулярки там будут ломаться.

Разделение работы, которое уже себя оправдало: модель **находит** (возвращает фрагменты, спаны, категории), а **меняет и записывает** код. Так модель не может испортить текст вокруг найденного, и результат проверяем.

## 2. Какая модель

Бери самую дешёвую модель, которая проходит проверку на выборке, а не самую сильную «на всякий случай».

1. Собери эталон: 20–50 записей с правильными ответами, включая трудные.
2. Прогони две-три модели от дешёвой к дорогой, посчитай совпадение с эталоном.
3. Если дешёвая проигрывает только на определённом типе записей — маршрутизируй: этот тип (длинный текст, много сущностей) — к модели сильнее, остальное — к дешёвой. Порог бери из прогона, а не на глаз.

Низкое согласие с эталоном не всегда вина модели — сначала проверь словарь меток. Если в одном списке смешаны уровни (узел изделия, симптом, процесс), модель выбирает между несравнимым, и согласие низкое при любом её качестве. Сначала правило применимости («есть ли здесь жалоба?»), потом выбор значения из списка одного уровня. Словарь фиксируй: без фиксации он разрастается, и рост совпадения перестаёт значить рост точности.

У моделей с рассуждением скрытое мышление расходует лимит длины ответа: при маленьком `max_tokens` ответ обрывается или приходит пустым. Для простых задач мышление уменьши или отключи, для остальных — оставь запас.

### С чего начинать новую задачу (решение владельца, 11.10.2026)

Для новой задачи извлечения или классификации, у которой ещё нет накопленной разметки, первый кандидат — `deepseek/deepseek-v4-flash-0731` через OpenRouter с выключенным рассуждением:

```python
body = {
    "model": "deepseek/deepseek-v4-flash-0731",
    "reasoning": {"enabled": False},
    "provider": {
        "data_collection": "deny",   # провайдеры, которые учатся на запросах, отсекаются
        "order": ["wafer/fast"],     # быстрый; самый дешёвый из проверенных — "inceptron/fp4"
        "allow_fallbacks": False,    # иначе маршрутизатор подставит другого провайдера
    },
    "usage": {"include": True},      # фактическая цена и токены приходят в ответе
}
```

Основание — замер 09–10.10.2026: извлечение 19 полей из русских разговоров в JSON, 400 записей. Ни одного неразбираемого ответа из 600; у `wafer/fast` 5 с и 0,0003 $ на запись, у `inceptron/fp4` 14 с и 0,00002 $; результаты двух провайдеров совпали между собой на 91 %. Провайдер закреплён один: если он недоступен, запрос падает, и конвейер доспрашивает позже (раздел 4).

Это отправная точка, а не замена шагов выше: проверка на своей выборке обязательна. Идентификатор модели и список провайдеров сверяй с каталогом в день работы (`GET /api/v1/models/<id>/endpoints`) — они устаревают за месяцы.

### Не меняй модель в работающем конвейере ради новизны или цены

Смена модели меняет определение метрики: новая модель размечает те же записи иначе, и ряд перестаёт сравниваться с историей. Прежде чем менять:

1. Прогони нынешнюю модель повторно на её же записях — это шум разметки. В замере 10.10.2026 модель совпала сама с собой на 87 %, кандидаты — на 64–73 %, причём более новые модели того же семейства совпали хуже, чем модели других семейств.
2. Сравнивай по внешнему факту (оплата, исход), а не по согласию моделей, и считай интервал. На 400 записях различия всех кандидатов оказались внутри шума.
3. Экономию считай в деньгах за месяц: при расходе в десятки рублей менять модель ради цены незачем.

### Провайдер у агрегатора

Одну модель у агрегатора (OpenRouter) держат десятки провайдеров с разной ценой, скоростью и сжатием весов.

- Цена в шапке страницы модели — у самого дешёвого провайдера, в поле `pricing` каталога — прейскурантная. Спишут по тому, кто ответил; без закрепления маршрутизатор выбирает сам и меняет провайдера от запроса к запросу.
- Самого дешёвого не бери вслепую: в замере он на рассуждающей модели думал две-три минуты и вернул пустой ответ. Сначала проба на одной записи — формат, цена, время.
- Рассуждение на извлечении выключай: с ним ответ в 5–20 раз длиннее, а цена записи у разных провайдеров одной модели расходилась до 16 раз.
- Запрет на обучение ставь в запросе (`data_collection: "deny"`), а не галочкой в кабинете: галочку снимут и не заметят. Большинство бесплатных вариантов моделей с этим запретом не работают, а часть отдаётся только приложениям-агентам из списка агрегатора и из скрипта недоступна.
- Записывай в журнал прогона, кто ответил и сколько списали: без этого нельзя сказать, что именно замерили.

## 3. Цена до запуска

1. Прогони выборку, сними фактический расход токенов на запись из ответа API.
2. Умножь на объём. Цены бери со страницы тарифов провайдера в день расчёта — по памяти они устаревают за месяцы.
3. Назови человеку цену полного прогона до запуска: платный внешний вызов на этом устройстве запускается после его «да».
4. Поставь потолок бюджета в коде: скрипт считает накопленную стоимость и останавливается при превышении, а не после. Запрет в коде срабатывает всегда, а просьба в промпте — не всегда.

Проверь, с чьего счёта идёт прогон: у проекта может быть правило, какой провайдер для чего (например, корпоративный ключ для работы компании и запрет на личный).

## 4. Повторы и тихие сбои

- Повторяй только временные ошибки — обрыв сети, 429, 5xx — с растущей паузой, 3–5 попыток.
- Ошибку ключа, прав или формата запроса не повторяй: она не пройдёт и сожжёт бюджет. Остановись и сообщи.
- Пустой ответ, ноль найденного, ноль записанных строк — это не успех. Скрипт проверяет, сколько реально записано, и считает расхождение с ожидаемым сбоем.
- Долгий прогон пишет результат по мере работы и умеет продолжить с места остановки, а не начинать заново.

## 5. Кэш и пакеты

- Длинная повторяющаяся часть промпта (инструкция, справочник, примеры) — кэшируй: провайдеры берут за кэшированный ввод в разы меньше.
- Не срочно — пакетный режим: у крупных провайдеров он заметно дешевле обычных вызовов, результат приходит в течение часов.
- Не пересчитывай уже обработанное: храни хеш входа и результат, повторный запуск берёт готовое.

Рабочие рецепты кэширования и пакетов для Claude API — навык `anthropic-cookbook`.

## 6. Журнал

Каждый прогон пишет итог: сколько записей, доля разобранных кодом и моделью, доля неуверенных, число вызовов, токены и стоимость, число ошибок. Рост доли неуверенных — первый признак, что формат источника поменялся и правила пора обновить.
