# Maker-Checker — независимая приёмка

Своя версия навыка команды Бризекса (07.2026) под Claude Code. Идея: автор (основной агент) сделал работу,
проверяющий — агент с **чистым контекстом**, не видевший истории разговора, — ищет то, к чему автор «замылен».

## Когда

- Автор объявил работу готовой; перед коммитом, запросом на слияние, публикацией, выкладкой.
- После рефакторинга, миграции, изменения архитектуры.
- План `build-plan` дошёл до приёмки.
- Человек просит проверить.

## Жёсткое правило: проверяющий только читает

Проверяющий **не** правит, не создаёт и не удаляет файлы проекта; **не** запускает изменяющие команды (коммит, push,
выкладка, миграция, установка пакетов, отправка сообщений, записи во внешние системы); **не** чинит найденное.
Он читает файлы и разницу, запускает проверки только на чтение (тесты, линтер, типы, сборка — в свои временные
папки) и пишет отчёт с предложениями. Чинит автор.

## Кого запускать

- **Агент с доступом к командам** (Agent, тип general-purpose) — если нужны тесты и линтер. Агент-ревьюер без
  доступа к оболочке тесты не запустит и честно напишет «не проверял» — такая приёмка неполная.
- **Вторая модель** (навык `second-agent`, Codex) — для независимого взгляда на код, план или расчёт; её вывод —
  мнение, разбирается по пунктам.
- Лимит: не более 5 субагентов на задачу, не более 3 одновременно; в промпте — «субагентов не запускай».
- Модель — параметр `model` у Agent; по умолчанию та же сильная модель, для текстов допустима `sonnet`.
- Каждая приёмка — **новый запуск**. Продолжать прежнего проверяющего нельзя: потащится старый контекст.

## Что передать проверяющему

Он ничего не знает из разговора — всё явно в промпте:
1. **Цель** — одна-две фразы, что должно было получиться (не история).
2. **Критерии готовности** — из плана или от человека.
3. **Что изменено** — пути, коммиты или команда для разницы (`git -C "<корень>" diff <база>..HEAD`).
4. **Команды проверок** — тесты, линтер, типы; не знаете — пусть определит по структуре проекта.
5. **Рабочий контекст** — корень репозитория, ветка, папка.
6. **Тип работы** — код, документ, план, миграция — и соответствующий список проверок ниже.

Не рассказывать, что автор уже сделал и почему: проверяющий читает сам. Данные из MCP и памяти, если нужны, —
передать в промпте: у субагента их может не быть.

### Шаблон промпта

```
Ты — независимый проверяющий с чистым контекстом. Автор объявил работу готовой; твоя задача — найти недоделки, а
не подтвердить, что всё хорошо. Лучше ложная тревога, чем пропущенная ошибка. Отвечай по-русски. Субагентов не
запускай.

## Только чтение (без исключений)
Не правь, не создавай, не удаляй файлы проекта. Не запускай изменяющие команды (commit, push, deploy, migrate,
install, отправка). Не чини. Только читай, запускай проверки на чтение и пиши отчёт — чинит автор.

## Цель
<одна-две фразы>

## Критерии готовности
- [ ] <критерий>

## Тип работы
<код | документ | план | миграция> — примени список ниже.

## Что проверить
1. Разница: <команда>. Затронутые файлы прочитай целиком.
2. Тесты: <команда> — приложи итог.
3. Линтер, типы, сборка: <команды или «определи сам»>.
4. Список по типу работы — по пунктам.
5. Восстанови требования по готовому результату и сравни с критериями: расхождение — провал.

## Рабочий контекст
Репозиторий: <путь>; ветка: <имя>; папка: <путь>

## Формат отчёта
### Критерии готовности
- [✓/✗] <критерий> — почему
### 🔴 Блокирует приёмку
- <файл:строка> — <что не так> — <как воспроизвести> — <как исправить>
### 🟡 Стоит поправить
- <файл:строка> — <что>
### Что запускал
- Тесты / линтер / сборка — итог
### Что не смог проверить и почему
### Вердикт
ГОТОВО / НЕ ГОТОВО — одна фраза
```

## Списки по типу работы

**Код:** логика и граничные случаи; гонки; необработанные ошибки и тихие отказы (успех при нуле записанных строк —
ошибка); мёртвый код, забытые отладочные выводы; сломанные импорты и пути; соглашения проекта; тесты действительно
проверяют новое поведение, а не только удачный путь; сломанный публичный контракт; секреты в разнице.

**Документ (канон Knowledge-OS или проект):** структура по шаблону типа; ссылки ведут на существующие файлы;
термины согласованы; нет противоречий с соседними документами; манифест, CHANGELOG, ADR обновлены, если правка их
касается; имя и метаданные по конвенциям; «Краткая суть» собрана из итогового текста; нет копий того, что живёт в
другом месте; нет данных компаний в переносимом каноне.

**План:** каждая задача проходит критерий «агент с нуля» (точные пути, файлы контекста, шаги, проверяемая
готовность); нет задач вида «улучшить X»; замысел есть; граф зависимостей и структура результата есть, синтаксис
mermaid верен; хэши отката и границы исполнения записаны.

**Миграция:** план отката есть и проверен (или честно помечен непроверенным); повторный запуск ничего не удваивает;
снимок исходного состояния сохранён, путь записан; карта соответствия полей полная; нет пути потери данных; порядок
переключения верен; проверочный запрос после миграции определён и исполним.

## Что автор делает с отчётом

1. Не защищаться: разобрать каждое замечание по существу.
2. 🔴 — исправить обязательно. Если замечание ложное — отклонить вслух с доказательством.
3. 🟡 — исправить, если согласны; не согласны — объяснить человеку.
4. Отчёт показать человеку полностью или честно пересказать с вердиктом.
5. «Не готово» — исправить и запустить новую приёмку. После двух «не готово» — к человеку с отчётами.
6. Всё, что проверяющий не смог проверить (не было доступа к командам, к данным), — проверить самому и сказать об этом.
