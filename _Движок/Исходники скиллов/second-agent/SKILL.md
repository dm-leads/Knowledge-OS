# second-agent — когда звать Codex (вторую модель)

Дмитрий не обязан знать, когда нужен второй агент. **Решение — на мне.** Этот навык описывает, когда
привлечение Codex даёт реальный выигрыш, а когда это просто удвоение стоимости и времени.

## Принцип

«Два агента лучше» — **миф**. Выигрыш возникает только там, где вторая модель приносит то, чего у первой
структурно нет: **независимые слепые пятна**. Субагент той же модели разделяет мои ошибки — Codex нет.

## Три паттерна, где звать ОБЯЗАТЕЛЬНО

| Паттерн | Когда | Что даёт |
|---|---|---|
| **1. Независимое ревью** | работа закончена и вот-вот уйдёт «в бой»: код, план, аналитический документ, стартер, промпт, расчёт с цифрами | ловит фактические ошибки и пропуски, которые я не вижу, потому что сам их и написал |
| **2. Rescue при застревании** | **≥2 неудачных попытки** одним подходом, или чувство «долблюсь в стену» | заходит с другой стороны. Историческая аналогия: я чинил картинку заплаткой 6 итераций вместо смены инструмента |
| **3. Состязательная проверка фактов** | цена ошибки высока: деньги, публичные цифры, необратимые действия | расхождение двух независимых расчётов = сигнал ошибки |

## Когда НЕ звать

- Рутина с очевидным ответом — трата денег и времени.
- Тексты под наш ToV, брендовые формулировки — у нас свой канон, Codex его не знает.
- Задачи, требующие **нашего контекста**: память, Lark MCP, Roistat, наши навыки. У `codex:codex-rescue`
  из инструментов только `Bash` — он видит файлы, но не нашу память и не наши MCP.
- Данные с ПДн/секретами — уходит во внешнего провайдера.

## Как вызывать

**Способ 1 — напрямую (предпочтительно для ревью, read-only):**

```bash
cd "<рабочая папка>" && codex exec --sandbox read-only --skip-git-repo-check "<prompt>" < /dev/null
```

- `--skip-git-repo-check` **обязателен** для не-git папок (Breezeks-Git таковой не является), иначе:
  `Not inside a trusted directory`.
- `< /dev/null` **обязателен**, иначе CLI ждёт stdin и висит.
- `--sandbox read-only` по умолчанию. `workspace-write` — только когда правки Codex осознанно нужны.
- Шум в stderr про `rmcp::transport::worker` (Linear/Figma без авторизации) — безвредно, фильтровать:
  `2>&1 | grep -v "ERROR rmcp"`.
- Кириллица в stdout Windows может прийти кракозябрами — смотреть на суть, при необходимости писать вывод в файл.
- ⚠️ **«0 находок» с кодом 0 ещё не ревью.** На Windows песочница `read-only` может не запустить ни одной команды
  (`CreateProcessAsUserW: Отказано в доступе`), а при исчерпанном лимите приходит `usage limit` — обёртка в обоих
  случаях выходит с кодом 0. Итог читать целиком и искать `usage limit`, `CreateProcessAsUserW`, «не могу
  выполнить».
- **Обход без снятия песочницы — пакет через stdin:** инструкция + `git show <коммит>:<путь> | cat -n` по нужным
  файлам + нужные разделы документов — одним файлом, запуск `codex exec --sandbox read-only
  --skip-git-repo-check - < пакет`. Пакет в ~3 100 строк (≈220 КБ) проходит; аргументом командной строки такой
  объём не передать (предел длины на Windows). Перед отправкой — поиск по пакету `API_KEY|SECRET|PASSWORD|TOKEN`:
  в пакете только имена переменных, не значения. `--dangerously-bypass-approvals-and-sandbox` не использовать —
  ревью остаётся только на чтение.
- **Ответ забирать ключом `-o <файл>`:** в stdout Codex повторяет весь входной пакет, и ответ в журнале тонет.
  Журнал писать отдельно и искать в нём отказ: `usage limit`, `is not supported`, пустой файл ответа.
- **Что давать читать, когда команд нет.** Проверено 10.10.2026 на пяти пакетах по 80–105 КБ (13 минут, 216 тыс.
  токенов): модель без оболочки не пересчитает ни одного числа, зато прочтёт подряд две тысячи строк и найдёт
  то, что не ловит правило. Поэтому числа сверять кодом, а модели отдавать смысл: полный список объектов с
  определением «что считается ошибкой», код правил, итоговый документ. Большой список резать на пакеты по
  700–800 строк — один пакет на всё читается поверхностно.
- **Модель видит только то, что в пакете.** Из 19 замечаний по коду пять оказались неверными: она судила о
  трёх файлах из семи («ветка мёртвая», «функция не вызывается», «отказ можно отменить» — всё это решалось в
  соседних файлах). Либо класть в пакет всю цепочку, либо прямо писать, чего в пакете нет, — и каждое
  замечание проверять по данным.
- Лимиты Codex общие с владельцем: если они на исходе, ревью по умолчанию — агент Claude с чистым контекстом.

**Способ 2 — через субагент** `codex:codex-rescue` (Agent tool): для крупной задачи с правками. Он форвардер —
передаёт задачу один раз и возвращает вывод как есть.

## Проверка перед вызовом (обязательно)

Связка может быть не установлена или не авторизована. Перед первым вызовом в сессии:

```bash
command -v codex >/dev/null 2>&1 && codex --version || echo "codex недоступен"
```

Если недоступен — **не падать и не выдумывать**: сказать Дмитрию, что второй агент недоступен, и продолжить
самому. Навык `codex:setup` проверяет готовность CLI.

## Модель

Модель берётся из `~/.codex/config.toml` (`model = ...`). **Не задавать `--model` без явной просьбы.**
Проверено 03.09.2026: там стоит `gpt-5.6-terra`. Название навыка плагина `gpt-5-4-prompting` — это гайд по
стилю промптов, **а не выбор модели**; путать не надо.

**Модель из настроек может быть недоступна этому входу.** Проверено 10.10.2026: в настройках стоит
`gpt-6.1-sol`, а сервер отвечает ошибкой 400 `The 'gpt-6.1-sol' model is not supported when using Codex with a
ChatGPT account` — и в CLI, и через плагин (`codex-companion.mjs task`): это одна и та же обёртка над тем же
входом. Пока настройки не исправлены, любой вызов без `-m` падает. Что делать:

- список моделей, известных этому входу, — `~/.codex/models_cache.json` (поле `slug`; видимые — `visibility: list`);
- взять старшую из видимых на один запуск: `codex exec -m <модель> …`. На 10.10.2026 рабочая — `gpt-5.6-sol`;
- настройки владельца не менять и сказать ему, какая модель отвечала на самом деле и почему не та, что он назвал.

## Как писать промпт для Codex

- Роль + конкретная задача + **формат вывода** (число пунктов, структура).
- Явно: `Do not praise` — иначе тратит вывод на комплименты.
- Для ревью: указать **файл(ы) и источники**, с чем сверять.
- Просить **доказательство** на каждый пункт (цитата/строка), иначе не отличить факт от догадки.
- Язык ответа задавать явно (`Answer in Russian`).

## ⚠️ Главное правило работы с результатом

**Вывод Codex — это мнение, а не истина.** Проверять каждый пункт перед принятием.

Проверено на практике 03.09.2026 (ревью стартера юнит-экономики): из 4 заявленных «ошибок»
**3 оказались ложными** — не понял «48 КБ» как размер и посчитал строки; принял артефакт кодировки за
неверные пути; цитировал устаревший документ как актуальный, не учтя более свежий источник.
Но 2 замечания были **точными и ценными** — их я пропустил.

Итого: разбирать по пунктам, обоснованные принимать, ложные отклонять **вслух и с объяснением**.
Не принимать пачкой и не отвергать пачкой.

## Стоимость

Каждый вызов — отдельные токены у OpenAI (тот прогон: ~60 тыс. токенов). Для дорогих/длинных прогонов
предупреждать Дмитрия. Для короткого ревью — просто делать.
