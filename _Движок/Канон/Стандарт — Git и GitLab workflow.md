# Стандарт — Git и GitLab workflow

## Краткая суть

GitLab — облачное хранилище контуров (свой инстанс, свои проекты заводишь сам). Работа описана **четырьмя
человеческими командами**, без терминов git. Git **опционален**: знания и память ценны и локально; git/
GitLab добавляют историю, бэкап и обмен.

## Четыре команды

| Команда | Смысл | Под капотом |
|---|---|---|
| `обнови` | взять свежую версию контура | `git pull` |
| `сохрани черновик` | локально зафиксировать, никому не видно | локальный commit / просто сохранение |
| `опубликуй` | выложить готовое в облако | `git push` с авто-сообщением о сути изменений |
| `откати` | вернуть прошлое состояние / показать историю | `git revert` / `git log` |

## Модель осознанной публикации

- Коллеги/другая машина видят изменения **только после** `опубликуй`. Никаких тихих авто-перезаписей.
- Каждая публикация фиксирует: кто, когда, что именно.
- Порядок: сначала **обновить каноничный документ** → `опубликуй` → потом анонс/сообщение. «Не в системе =
  не существует».

## Сам канон — репозиторий (с 23.09.2026)

- Корень `D:\Knowledge-OS\` — git-репозиторий **слоя канона**: `.gitignore` пропускает только `_Движок`,
  `Методологии`, `Экосистема инструментов`, `CLAUDE.md` и сам `.gitignore`. Проекты внутри KOS в него не
  входят — у них свои репозитории или никаких.
- Удалённый репозиторий канона — личный закрытый GitHub владельца: резерв и перенос на другое устройство.
  Отправка — **сам после блока изменений** (разрешение владельца 28.09.2026, только для репозитория канона): перед
  каждой отправкой — скан добавленных строк на секреты и ПДн, отправка с метками (`--follow-tags`).
- В канон пишут чаты любых подключённых проектов (подъём уроков, выпуски, подключение). Поэтому перед записью —
  `git status`, коммит **только своих путей**, чужие незакоммиченные правки не трогать.
- Переводы строк в каноне — LF (`core.autocrlf=false`). Файл правится инструментом правки или Python с
  `newline=''`, иначе меняются переводы строк во всём файле.

## Границы и безопасность

- **Push-allowlist:** `опубликуй` разрешён только для репозиториев внутри `D:\Knowledge-OS\`: корень канона —
  сам после блока изменений (см. выше), остальные — по команде владельца. Путь вне — СТОП и явное подтверждение
  конкретного абсолютного пути.
- Границу репо определять по затронутому файлу: `git -C "<путь>" rev-parse --show-toplevel`. Корень KOS и
  проекты внутри — разные репозитории.
- **Проекты вне KOS** публикуются своим процессом: он записан в разделе «Git проекта» их `CLAUDE.md`. Слово
  «опубликуй» в таком проекте запускает его процесс, а не этот стандарт. В репозиториях компании Бризекс свой
  навык `git-workflow-breezeks` — у него своё значение этих команд.
- Запреты: force-push без явной просьбы, массовый push без подтверждения per-repo, коммиты с секретами.
- **Секреты (PAT/токены) — никогда в git и никогда в чат.** Только в локальном конфиге MCP (вне репо).

## Подключение нового репозитория (runbook)

1. Создаёшь пустой проект в **своём** GitLab (имя = латинский слаг контура).
2. Прописываешь URL/токен в `06 — Инструменты/mcp.template.json` → свой локальный `mcp.json` (по образцу,
   с реальным токеном, файл не коммитится).
3. В нужном контуре: `сохрани черновик` → `опубликуй`. Дальше — обычный цикл обнови/опубликуй.
