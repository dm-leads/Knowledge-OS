# ADR-0002 — Стандарт извлечения знаний из обучающих материалов

- **Статус:** Accepted
- **Дата:** 2026-06-30

## Контекст

Курсы и авторские материалы практиков — источник знания, которого **нет в общем вебе и в модели**:
прикладная механика, пороги, формулы, анти-паттерны, специфика Яндекса. Для направлений (Директ, SEO)
это основной способ добрать экспертизу.

Практика показала три устойчивые проблемы:

1. **Неполное чтение.** Материал читался «по первым строкам» + домысел → выводы не опирались на источник.
   Ограничение Дмитрия «материалы читать ПОЛНОСТЬЮ» повторялось из чата в чат.
2. **Процесс жил в чатах, а не в каноне.** Волны изучения (SEO: NeuroSEO, Rush operations, инструменты,
   Rush Senior) работали хорошо, но нигде не зафиксированы → не воспроизводятся и не переносятся на
   другой проект/курс.
3. **Дублирование вместо дельты.** По одной теме накапливались параллельные пересказы
   (`NOTE-SRC-Yandex-Direct-2025`, `NOTE-SRC-Professional-Direct-VIP-2025`, `NOTE-SRC-Direct-Strategies`)
   без сверки: что совпадает, что противоречит, что реально нового.

## Решение

1. Ввести в канон **[Стандарт — Извлечение знаний из обучающих материалов](<../../Канон/Стандарт — Извлечение знаний из обучающих материалов.md>)**
   — единый пайплайн для **любого** источника: инвентаризация → план волн → полное чтение с **реестром
   покрытия** → дистилляция с адресами → сверка с имеющимся → применение → критик.
2. **Реестр покрытия — обязателен.** Источник считается изученным только при 100% покрытии либо явном
   списке непрочитанного с причиной. Это механизм принуждения против проблемы №1.
3. **Маршрутизация выходов** фиксируется стандартом: сырьё (вне git) → дистилляция первоисточника →
   **переносимое ядро** в `D:\Knowledge-OS\Методологии\` → **проектная дельта** в направлении проекта.
   Переносимое ядро пишется один раз, проекты ссылаются (SSOT/DRY).
4. **Гейт на саб-агентов:** волновое чтение через флот агентов запускается только после явного
   подтверждения Дмитрия (действующее правило проекта).
5. **Скилл — после обкатки.** Автоматизация процесса скиллом (`_Движок\Исходники скиллов\`) вводится
   только после прогона стандарта на живом курсе, чтобы не закреплять сырой процесс.

Новый тип документа не вводится — стандарт использует существующий `standard` из закрытого списка типов.

## Рассмотренные альтернативы

- **Оставить как есть (ad-hoc по чатам):** отвергнуто — не воспроизводится, боль неполного чтения
  возвращается в каждом новом чате.
- **Сразу сделать скилл без стандарта:** отвергнуто — скилл зафиксировал бы непроверенный процесс;
  правило должно быть первичным, автоматизация — вторичной.
- **Держать стандарт в проекте (viklimat), а не в каноне:** отвергнуто — материал приходит по всем
  направлениям и проектам, правило обязано быть кросс-проектным.
- **Хранить переносимое ядро в каждом проекте:** отвергнуто — расхождение копий, нарушение SSOT.

## Последствия

- (+) Любой курс обрабатывается одинаково и **проверяемо** (покрытие доказывается, а не декларируется).
- (+) Переносимое знание копится в одном месте — новый проект стартует с готовой методобазой.
- (+) Дельта вместо дубля: новый источник сверяется с уже имеющимися.
- (−) Процесс дороже, чем «просто прочитать»: инвентаризация, реестр покрытия, сверка, критик —
  осознанная цена за достоверность (материал используется в реальных решениях по деньгам).
- Первый прогон — курс «Адекватный Директ» (Строков, 2025); по его итогам решается вопрос скилла.
