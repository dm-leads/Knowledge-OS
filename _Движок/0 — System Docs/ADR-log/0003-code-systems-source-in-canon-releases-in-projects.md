# ADR-0003 — Системы с кодом: исходник в каноне, у компаний — выпуск с паспортом

- **Статус:** Accepted
- **Дата:** 2026-09-28
- **Решение принял:** Дмитрий

## Контекст

Канон собирает переносимое: методологии, правила, навыки. Часть переносимого — это код: Движок роста
(юнит-экономика и growth hacking как цикл), Ядро данных, дальше — другие системы. Первый инстанс каждой
системы вырос внутри проекта компании (Бризекс): код лежит в её репозитории GitLab, работает на её сервере
(Lorentz), и компания хочет, чтобы так и оставалось.

Одновременно система — личная методология владельца и должна подключаться к любому новому проекту без
переноса кода руками. Две копии кода, которые правятся независимо, расходятся за недели. Так уже бывало с
копиями навыков, поэтому навыки стоят ссылками.

## Решение

1. **Исходник системы с кодом — пакет в каноне:** `_Движок/Пакеты/<пакет>/` с `pyproject.toml` (имя и версия)
   и каталогом кода `<пакет>/`. Код пакета нейтрален: в нём нет имён, данных и конфигурации компаний.
   Граница проверяется тестом пакета.
2. **Проекты на устройстве подключают пакет ссылкой:** `py -3 -m pip install -e <пакет>`. Правка в каноне
   сразу видна во всех таких проектах, без коммитов в каждом.
3. **Компании, которой код нужен в своём репозитории и на своём сервере, достаётся выпуск**
   (`_Движок/Инструменты/kos_release.py issue`): копия каталога кода одной закоммиченной версии канона и
   паспорт `_паспорт_выпуска.json` рядом с кодом. В паспорте — пакет, версия, коммит канона и отпечаток
   каждого файла.
4. **Выпуск не правится руками.** Тест пакета `tests/test_release_passport.py` и `kos_release.py check`
   находят изменённый, пропавший или лишний файл. Правка идёт в канон и приходит новым выпуском. Поверх
   ручных правок новый выпуск не ложится.
5. **Отставание выпуска от канона видно одной командой:** `check --package …` выдаёт число коммитов канона,
   менявших пакет после выпуска. Отставание — сигнал обновить выпуск, а не ошибка.
6. **Инстанс компании** — конфигурация, данные, модули и тесты, привязанные к компании, — живёт в проекте
   рядом с выпуском, отдельным каталогом (у Бризекса — `growth_instance/`). В пакет он не идёт.
7. **Сервер компании ставится из репозитория компании** — из выпуска, а не из канона. Канон — личный
   репозиторий владельца, компания от него не зависит.
8. **Знания и навыки выпусков не имеют — всегда ссылкой.** Выпуск нужен только коду, который компания
   обязана держать у себя.

## Рассмотренные альтернативы

- **Отдельный репозиторий каждой системы в GitLab компании, канон на него ссылается.** Копий нет, но
  исходник личной методологии живёт у компании, и новые проекты вне компании зависят от её репозитория.
  Отклонено.
- **Код остаётся только в репозиториях компаний, в канон идут методологии.** Новые проекты кода не
  получают, каждую систему пришлось бы собирать заново. Отклонено.
- **Git submodule или subtree из канона в репозиторий компании.** GitLab компании ссылался бы на личный
  GitHub, серверу компании нужен был бы доступ к нему. Subtree на путях с кириллицей в Git for Windows
  хрупок. Паспорт даёт ту же связку проще. Отклонено.

## Последствия

- Код пакета правится в каноне. В проекте компании правка выпуска руками краснит набор тестов.
- Для компании цикл изменения такой: коммит в каноне → `issue` в проект → тесты проекта → коммит
  и публикация проекта. Это два коммита вместо одного, зато код компании всегда соответствует
  известной версии канона.
- Первый пакет — Движок роста 1.0.0 (28.09.2026). Ядро данных переносится тем же механизмом вторым
  заходом, после проверки механизма на движке.
- Новые правила подключения проекта к канону (сценарий «Подключить проект к канону») опираются на это
  решение для систем с кодом.
