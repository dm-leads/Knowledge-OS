## 2026-11-21 — `lead_catcher` 1.3.0: ошибки видны, вход в два шага, диагностика входа

- Любая ошибка команды печатается одной строкой «ОШИБКА …» (через маску секретов). До этого исключения терялись в
  обёртке вывода: вход падал молча, человек думал «код не приходит».
- Вход в два шага для входа вместе с агентом: `login N --phone <номер>` (запрос кода, способ доставки),
  `--code <код>`, `--resend`, `--password` (облачный пароль — только интерактивно у человека). Номер и
  `phone_code_hash` — в `<сессия>.pending` в хранилище устройства (вне git), после входа файл удаляется.
- Диагностика: `--keys M` (ключи другого номера) и `--direct` (без прокси) — отличить свежий `api_id` от прокси. 27 тестов.

## 2026-11-11 — content_engine 1.5.4: title и description страницы — из шапки текста

- Сборка (`assemble build`: страница, разметка, манифест) брала title и description из брифа, а гейт статьи — из шапки
  текста. Описание, уточнённое на вычитке фактов, жило только в шапке (правка брифа снимает утверждение), поэтому в
  пакет и в эталон «доехало» уходило старое описание из брифа: `publish verify` падал на верной странице. Теперь
  сборщики `html` и `markdown` и разметка берут оба поля одним правилом с гейтом статьи — шапка текста, чего в ней нет —
  бриф (`schema.page_fields`).
- Сборщик проекта (`assemble.adapter: module:…`) мог остаться на брифе — правка встроенных сборщиков его не задевает.
  Поэтому `assemble build` после сборщика сверяет title и description манифеста с `page_fields` и при расхождении
  отказывает (пакет не собирается), а `assemble contract` ловит это на синтетической статье: в её шапке теперь своё
  описание, отличное от брифа. Найдено независимой проверкой правки до выпуска: у первого проекта свой сборщик,
  и без сверки выпуск 1.5.4 сбой 418 не чинил бы.
- Проверка брифа (`prepare check`, переутверждение) видела в уже вставленной странице своей темы дубль самой себя
  («почти дублирует»). Теперь страница исключается, если её выпустила эта тема: запись «доехало» или собранный пакет
  темы с тем же slug. Чужая страница с тем же slug по-прежнему даёт ошибку; битый манифест исключения не даёт.
  Известная граница (как у гейта статьи и карты спроса): свободен ли slug на сайте, пакет не проверяет.
- Тесты `test_page_fields.py` (5: оба сборщика, title и description, защита сборки и контракт, обе ветки «своей
  страницы»); 832 теста, 1 пропущен. Каталог операций не изменился (снимок 1.5.4 = 1.5.3).

## 2026-10-22 — growth_engine 1.5.0: рамка цели и сверка систем по сумме кабинетов

- **Рамка цели.** Окно цели можно считать не в денежной системе, а в своей: `goal.system`, `goal.scope`,
  `goal.segment` в конфигурации инстанса (например, хранилище фактов, кабинет компании, узкий контур). Без них всё
  как раньше. Нужна, когда правило цели владельца сменило определение метрики, а денежная модель осталась на прежней
  системе: иначе база сравнивается с числом другой рамки. Конфигурация проверяет, что система объявлена, кабинет
  задан, разрез — вида «измерение=значение».
- **Адаптер хранилища фактов подключён** к списку систем (`adapters.FACTORIES["datacore"]`): читает файл публикации
  или собственную базу, секретов не берёт.
- **Мост систем по сумме кабинетов** с месяца `sum_scopes_from` (`economy.bridges.<мост>.sum_scopes_from: "ГГГГ-ММ"`).
  Раньше месяца — сверка по каждому кабинету, как прежде. Нужен, когда системы начинают делить кабинеты по-разному
  (одна — по кабинету учёта, другая — по полю бренда): итог совпадает, а покабинетная сверка навсегда закрывает
  прогон. Сумма — по правилам стража 3.
- «Требуется в следующем месяце» (`required_last_month`) переносит разрез окна: без этого число рамки с разрезом
  читалось как число целиком. Окно цели берёт из ответа системы цели только число нужного разреза и требует ровно
  одно — адаптер с разрезом-измерением иначе отдал бы первый попавшийся сегмент (оба — по независимому ревью).
- Обратно совместимо: старые конфигурации работают без правок. Тесты: `test_config.py` (рамка цели),
  `test_adapters_registry.py`, `test_goal_noise_shift.py` (разрез); поведение прогона — тестами инстанса.
- Урок: правило цели у владельца может смениться отдельно от денежной модели. Рамка метрики цели — свойство
  конфигурации, а не следствие выбора денежной системы.

  Ф6 критик. Маршрутизация выходов: сырьё (вне git) / дистилляция / **переносимое ядро в
